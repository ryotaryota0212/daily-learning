# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPは「とりあえず動くもの」ではなく、「最小コストで最大の学びを得るための実験装置」。個人開発者にとっては特に重要で、間違ったものを3ヶ月かけて作り込むリスクを防ぐ。「何を作るか」より「何を検証するか」を先に決めるのが核心。コードを書く前に、そのプロダクトが成立する前提条件を列挙し、最もリスクの高い仮説を最も安く検証する方法を考える。

---

## 核となる考え方

- **MVPの目的は販売ではなく学習**。売れなくても「なぜ売れないか」がわかればOK
- **リスクの高い仮説から潰す**。「このペインは実在するか？」が先で「技術的に実現できるか」は後
- **Viable（実用可能）の基準を下げる**。完璧でなくていい。ユーザーが1回でも使えれば検証できる
- **最小 = 機能数ではなく、検証に必要な最低限**。1機能でも過剰になることがある
- **捨てることを前提に作る**。MVPのコードは本番と別物でよい

### MVPの種類（コスト低→高順）

| タイプ | 内容 | 適した検証内容 |
|--------|------|--------------|
| コンシェルジュMVP | 人手で全部やる（自動化なし） | ニーズの実在確認 |
| ランディングページMVP | 説明ページ＋メール登録のみ | 需要と集客チャネル |
| ウィザード・オブ・オズ | 裏でManual処理、ユーザーには自動に見える | UXとフロー検証 |
| プロトタイプ（Figma等） | 動かないUIのデモ | UXとコンセプト |
| 機能限定プロダクト | コア機能1つだけ実装 | 実際の使用行動 |

## 実践フレームワーク：5ステップ

### Step 1：前提仮説を書き出す（10分）
```
仮説チェックリスト：
□ ユーザーXはペインYを持っている
□ 既存解決策に不満がある
□ 私の解決策でペインが解消できる
□ ユーザーはお金を払う意思がある
□ 私がそのユーザーにリーチできる
```

### Step 2：最もリスクの高い仮説を1つ選ぶ
- 「これが外れたらプロダクトが成立しない」仮説を特定
- 通常は「ペインの実在」か「支払い意思」が最重要

### Step 3：最安の検証方法を選ぶ
```
費用：¥0  → SNS投稿・DM・既存ユーザーへのヒアリング
費用：¥1〜3万 → LP作成（Carrd/Notion）＋広告テスト
費用：¥3〜10万 → Nocode/プロトタイプ
費用：¥10万〜 → コーディング（最後の手段）
```

### Step 4：成功基準を事前に決める
- 「◯人がメール登録したら需要あり」
- 「3人中2人が『いくら払う？』に答えたら前進」
- 基準は検証前に決める（後付けはNG）

### Step 5：期限を設けて実行し、学びを記録
- MVPの期限：1〜2週間が理想
- 記録すべきこと：仮説・結果・気づき・次のアクション

## 事例

### 成功：Dropbox（コンシェルジュ→ランディングページ）
- 実際にシステムを作る前に「デモ動画LP」だけ公開
- メール登録数75,000件 → 需要確認後に本開発
- 学び：コードゼロで大規模な需要検証が可能

### 成功：個人開発者Aさんのケース
- 「エンジニア向け請求書テンプレート」の需要検証
- NotionテンプレートをTwitterで無料配布 → 300DL
- 有料版（¥2,000）を告知 → 初日50本販売
- コードを一行も書かずに月10万円の収益モデルを確認

### 失敗：作り込みすぎMVP
- 3ヶ月かけてSaaSを開発 → ローンチ後にユーザーゼロ
- 原因：「ペインの実在」を検証せずにソリューションを作り込んだ
- 対策：最初の1週間でコンシェルジュMVPで5人から反応を得るべきだった

---

## アンチパターン

- **「もう少し機能を足してから公開」症候群**：完成待ちのMVPは機能するMVPより価値がゼロ
- **検証ではなくデモになるMVP**：投資家向けのピカピカなデモを作っても、ユーザーの行動データは得られない
- **仮説を持たない公開**：「とりあえず出してみる」は学びが少ない。何を検証したいかを事前に決める
- **成功基準を後から変える**：「登録は少なかったが熱狂ユーザーがいたからOK」は都合のいい解釈になりがち
- **MVPを捨てられない**：技術的負債を抱えたMVPコードを本番に持ち込む。MVPは実験用と割り切る

---

## 明日から試せるアクション（3つ）

1. **仮説リストを作る**：今作ろうとしているプロダクトの前提仮説を5つ書き出し、最もリスクの高いものを1つ特定する
2. **コンシェルジュで検証する**：コードを書く前に、ターゲットユーザー3〜5人に「もし◯◯があったら使いますか？いくら払いますか？」とDMする
3. **成功基準を先に決める**：「1週間以内に◯◯という結果が出たら次に進む」という基準を書いておき、期限を守る
