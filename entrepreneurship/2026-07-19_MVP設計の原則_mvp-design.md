# MVP設計の原則 — 何を作らないかを決める技術

## 概要

MVPとは「最小限の機能で仮説を検証するプロダクト」だが、個人開発者が最も犯しやすい失敗は「作りすぎ」だ。技術が書ける分だけ機能を詰め込んでしまい、誰にも使われないまま時間と体力を消耗する。MVP設計のコアは「何を作るか」ではなく「何を作らないか」を決めること。検証したい仮説を1つに絞り、最速で答えを得る手段を選ぶ技術が求められる。

---

## 核となる考え方

- **MVPの目的は「売ること」ではなく「学ぶこと」**。最初から収益化を狙うと機能が増える
- **仮説は1つ**。「このユーザーはこの課題を持ち、このソリューションにお金を払う」を分解して最も不確かな部分だけを検証する
- **ビルドよりも早い検証手段が常に存在する**。LP、手動オペ、デモ動画、スプレッドシートなど
- **完成形ではなくシグナルを求める**。10人の熱狂的なユーザーが1000人の「まあいいね」より価値が高い（Paul Graham）
- **機能は後から足せるが、方向性ミスの時間は取り戻せない**

---

## 実践フレームワーク

### Step 1: リスクの列挙（5分）
検証していない前提を全部書き出す。
```
課題リスク：そのユーザーは本当にその課題を持っているか？
ソリューションリスク：自分の解決策で課題が解けるか？
市場リスク：十分な数のユーザーが存在するか？
収益リスク：お金を払うか？いくら払うか？
```

### Step 2: 最もリスクの高い仮説を選ぶ（10分）
「これが外れたら事業が成立しない」仮説を1つ選ぶ。それだけを検証する。

### Step 3: 最小コストの検証手段を選ぶ

| 検証したい仮説 | 推奨手段 | 目安コスト |
|---|---|---|
| 課題の存在 | ユーザーインタビュー5〜10人 | 0円・1週間 |
| ソリューション有効性 | Figmaプロトタイプ + テスト | 0円・2〜3日 |
| 支払い意欲 | LP + 決済ボタン（仮） | 数千円・3日 |
| リテンション | 手動オペMVP（自分が人力対応） | 0円・即日 |
| スケール | 実装MVP + 10人ユーザー | 数週間 |

### Step 4: 成功基準を先に決める（重要）
実験前に「この数値が出たら仮説確認、出なければ否定」を決める。
- 例：「LPを100人に見せて10人がメール登録したら需要あり」
- 感触でなく数字で判断することで、バイアスを防ぐ

### Step 5: タイムボックスを設定する
- ユーザーインタビュー型：2週間以内
- LP型：1週間以内
- 手動MVPオペ型：1ヶ月以内
- 期限がないと「もう少し準備してから」ループに入る

## 成功・失敗の事例

### 成功例：Dropboxの「動画MVP」
コードを書く前に製品デモ動画を公開 → 1夜でウェイトリスト75,000人。開発前に需要を証明した。

### 成功例：Zapierの手動オペMVP
最初のIntegration接続は全部手動でやっていた。自動化なし。ユーザーが本当に使うか確認してから自動化を実装。

### 失敗例（個人開発あるある）
3ヶ月かけて作り込んだSaaSツールをリリース → ユーザー0人。後から分かったのは「そのユーザーはExcelで十分だった」。2週間のインタビューで判明できた事実だった。

## アンチパターン

- **「もう少し機能を足してから公開」** → 公開を先延ばしにするほど市場の反応から遠ざかる
- **「友人・家族でテスト」** → 本音を言ってくれない。ターゲットユーザーでなければデータにならない
- **成功基準を後から決める** → 「なんとなく手応えあった」でピボットできなくなる
- **競合を意識して機能を増やす** → 競合との差別化は仮説検証後の話。MVPフェーズには不要
- **技術的完成度にこだわる** → MVPに本番品質のコードは必要ない

1. **今作っているプロダクトの「検証できていない仮説」を3つ書き出す** → その中で最もリスクが高いものに集中する
2. **「コードを書かずに仮説を検証する方法」を考える** → LP、Google Form、手動対応など。最小コストの手段を選ぶ
3. **成功基準を数値で先に決める** → 「〇〇日以内に△△件のサインアップ」という形で実験設計を完成させる
