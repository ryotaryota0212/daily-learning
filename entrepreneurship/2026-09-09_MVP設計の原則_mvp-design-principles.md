# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPとは「最小限の価値を持つプロダクト」ではなく「最小限のコストで最大の学びを得るための実験装置」。個人開発者が陥りがちな罠は「完成度を上げてからリリースしようとすること」。リソースが限られているからこそ、何を**作らないか**の判断が事業の生死を分ける。

---

## 核となる考え方

- **MVPの目的は販売ではなく検証**。収益は副産物
- 「ユーザーが欲しいと言ったもの」と「ユーザーが実際にお金を払うもの」は別物
- 1つの仮説だけを検証する。複数の機能を同時に試すと何が効いたか分からない
- **作ることより捨てることが難しい**。機能を追加するたびに検証が複雑になる
- フィードバックが早く来るほど良い。6ヶ月後より6日後に間違いを知りたい

---

## 実践フレームワーク：MVP設計の3ステップ

### Step 1｜核心仮説を1行で書く

```
「[ターゲット] は [課題] を解決するために [解決策] に [金額/行動] を払う」
```

例：「フリーランスエンジニアは請求書作成の手間を減らすために自動化ツールに月500円払う」

この仮説の「最もリスクが高い部分」だけを検証するのがMVP。

### Step 2｜機能リストを作り、全部消す

1. やりたい機能を全部書き出す
2. 「これがなくても仮説は検証できるか？」と問い、Yesなら消す
3. 残った機能だけ作る（通常、最初のリストの10〜20%）

**残すべきもの：** 仮説の核心に触れる1つの行動（支払い・登録・共有など）
**消すべきもの：** ダッシュボード、管理画面、通知、カスタマイズ機能

### Step 3｜検証方法を選ぶ（コードを書かないMVPを優先）

| 手法 | 所要時間 | 向いている検証 |
|------|---------|--------------|
| LP + ウェイトリスト | 1日 | 需要の存在確認 |
| LP + 決済ボタン（即購入） | 1〜2日 | 支払い意欲の確認 |
| スプレッドシート手動運用 | 数時間 | ワークフローの検証 |
| Notion/Tally フォーム | 数時間 | 情報収集・インタビュー誘導 |
| コード実装MVP | 1〜2週間 | 上記で需要確認後のみ |

## 事例

### 成功：Dropboxのビデオデモ
コードを書く前にYouTube動画1本で需要を検証。一夜でウェイトリストが7万5000人に。
→ **学び：製品ゼロでも意図の検証はできる**

### 個人開発の実例：Twitterで「作ってほしい？」とツイート
「〇〇ができるツール、月1000円で使いますか？」とDMを30人に送る。
10人以上が「使う」と言ったら作り始める。0〜2人なら仮説を変える。
→ **学び：コードより先に人間に聞く**

### 失敗：フル機能で3ヶ月開発してリリース
「全部揃えてから出そう」と決めて完成させたが、誰も課題を感じていなかった。
3ヶ月 × 毎日4時間 = 失った時間と機会。
→ **学び：完成度と市場ニーズは別問題**

---

## アンチパターン

- **「あと1機能追加したらリリースする」を繰り返す** → 永遠にリリースしない
- **「自分が欲しいから作る」だけで進める** → 市場が小さすぎる可能性を検証していない
- **無料で配って使われない→「有料なら使う」と思う** → 逆。無料でも使われないなら有料はさらに厳しい
- **技術的に面白いものを作る** → ユーザーは技術に感動しない、解決に感動する
- **フィードバックをもらわずに改善する** → 自分の思い込みで進化する
