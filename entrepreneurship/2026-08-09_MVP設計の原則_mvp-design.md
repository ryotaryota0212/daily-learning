# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVP（Minimum Viable Product）は「最小限の機能で最大限の学びを得るもの」だ。多くの個人開発者が陥る罠は、完璧なプロダクトを6ヶ月かけて作り、誰にも使われないことに気づくパターン。MVPの本質は「速く学ぶ」ことであり、「速く作る」ことではない。ソロファウンダーにとって時間とお金は有限だからこそ、何を作らないかを決める力が生死を分ける。

---

## 核となる考え方

- **MVPはプロダクトではなく「実験」**：仮説を検証するための最小単位
- **Viable（実用的）が重要**：動かないモックやLP単体はMVPではない。ユーザーが実際に価値を受け取れること
- **Minimum（最小）の判断基準**：「これがなければ価値の本質が伝わらないか？」でYesなら残す、Noなら削る
- **作る前に売る（Pre-sell）**：コードを書く前に課金意思を確認できれば最強の検証
- **1つの課題、1つのユーザーセグメント、1つのチャネル**に絞る

---

## 実践フレームワーク・ステップ

### Step 1：検証すべき最重要仮説を特定する（30分）

```
リスク仮説マトリクス
┌─────────────────────────────────┐
│ 仮説              │ 検証コスト  │
├─────────────────────────────────┤
│ 課題は本当に存在するか  │ 低（インタビュー）│
│ 解決策に価値があるか   │ 中（LP/プロト）   │
│ 課金してもらえるか    │ 中（先払い）      │
│ スケールできるか     │ 高（後回しでよい） │
└─────────────────────────────────┘
```

**やること**：最もリスクが高く、最も安く検証できる仮説から着手する

### Step 2：MVP形式を選ぶ（作る前に考える）

| 形式 | コスト | 向いているケース |
|------|--------|-----------------|
| Wizard of Oz（手動対応） | 極小 | バックエンドが複雑な場合 |
| LP + 問い合わせフォーム | 極小 | 需要の有無を確認したい |
| Concierge MVP（個別対応） | 小 | サービス系、マーケット系 |
| プロトタイプ（Figma等） | 小 | UI/UXの確認 |
| ワーキングプロトタイプ | 中 | 核機能のみ実装 |

### Step 3：「削る」判断のチェックリスト

機能を追加する前に問う：
- [ ] この機能がなければ、ターゲットユーザーはプロダクトを使えないか？
- [ ] この機能は仮説検証に必要か、それとも「あったら良い」か？
- [ ] 実装コストと学習価値のトレードオフは妥当か？
- [ ] 手動でも代替できないか？

### Step 4：成功指標を先に決める

作り始める前に「何が証明されたらMVPは成功か」を定義する。

- **定量**：10人が継続利用 / 3人が課金 / 離脱率30%以下
- **定性**：「これなしでは困る」という発言がインタビューで出る

## 成功・失敗の事例

### 成功例：Dropbox（動画MVP）
- コードを1行も書く前に、動作を説明する2分動画を公開
- 一晩でウェイティングリストが7万5千人
- 「需要がある」を証明してから本開発へ

### 成功例：個人開発者の典型パターン
- 「Notionテンプレート販売」：Notion + Gumroad = 開発ゼロでMVP
- 「有料Slackコミュニティ」：プロダクト前にコミュニティで課題を検証
- 「手動マッチングサービス」：マッチングアルゴリズム前にスプレッドシートで運用

### 失敗例：機能過多MVP
- 個人開発者がSNS × タスク管理 × ポートフォリオを1プロダクトに詰め込む
- 8ヶ月かけてリリース → 誰にも刺さらず → 撤退
- **教訓**：「全部入り」は「誰のためでもない」と同義

---

## アンチパターン

- **「もう少し作ってからリリース」症候群**：完璧を求めて一生リリースしない
- **MVPをスモールプロダクトと混同**：機能を減らすのではなく、検証の範囲を絞ることが本質
- **仮説なしのMVP**：「とりあえず作ってみた」は検証ではなく賭け
- **成功指標を後付けで決める**：好都合な指標に合わせてしまう
- **ユーザーに聞かずに作る**：「こんな機能が欲しいはず」という思い込みで開発

## 明日から試せるアクション

1. **今作っているもの（または作ろうとしているもの）の最重要仮説を1文で書き出す**
   　例：「フリーランスエンジニアは請求書作成に毎月30分以上かけて困っている」

2. **その仮説をコードなしで検証できる方法を1つ考える**
   　例：ツイートで問い合わせ → DM対応 → 手動で請求書作成代行 → 課金意思を確認

3. **「削るリスト」を作る**：今のスコープから「なくても最初のユーザーは困らない機能」を3つ書いてみる
