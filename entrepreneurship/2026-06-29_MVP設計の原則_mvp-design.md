# MVP設計の原則 — 何を作らないかを決める技術

## 概要

MVPを「最低限の機能セット」と誤解すると、作りすぎて時間とお金を浪費する。
MVP（Minimum Viable Product）の本質は「最小の投資で最大の学びを得る手段」。
1人の個人開発者にとって、作らない決断こそが最も高価値なスキルになる。
何を削るかが決まらないと、3ヶ月後も「もう少し作ったら」と言い続けることになる。

---

## 核となる考え方

- **MVPは製品ではなく実験**：ユーザーに届けるためではなく、仮説を検証するために存在する
- **価値 ≠ 機能数**：機能を増やすほど「何のサービスか」が薄まる
- **削れるかどうかは「学べるか」で判断**：その機能がなくても仮説が検証できるなら削る
- **完成度より回転速度**：70点のものを3回改善する方が、100点を1回作るより速く正解に近づく
- **Fake it before you build it**：自動化前に手動でやれないか常に問う

---

## 実践フレームワーク

### ステップ1: 検証したい仮説を1行で書く

```
「[ターゲット] は [問題] を抱えており、[解決策] にお金を払う」
```

例：「副業フリーランサーは請求書作成に30分かけており、自動化ツールに月額1,000円払う」

### ステップ2: 仮説ごとに「最小の証拠」を定義する

| 仮説 | 最小の証拠 | MVPの形 |
|------|-----------|---------|
| 問題が存在する | 5人がインタビューで「困っている」と言う | インタビュー（コードなし） |
| 解決策が刺さる | 3人がLP見て「今すぐ欲しい」と言う | LPのみ（メール収集） |
| お金を払う | 1人が事前決済する | Stripe + 手動対応 |
| 継続して使う | 週1回以上ログインが2週間続く | 最小機能版アプリ |

### ステップ3: 機能リストに「削除フィルター」をかける

各機能に対して以下を問う：
- この機能がなければ、仮説が検証できないか？ → **Yes → 残す / No → 削る**
- この機能は「あったら便利」か「ないと使えない」か → **前者は削る**
- 手動でも同じ体験を提供できるか → **Yesなら自動化は後回し**

### ステップ4: MVPの4段階を使い分ける

```
Lv1 コンシェルジュMVP  : 全部手動。エクセル+メール+Zoom
Lv2 ウィザード of Oz   : 裏で人間が動く（自動化に見せかける）
Lv3 ランディングページ  : 機能は作らず申し込みだけ受ける
Lv4 シングルフィーチャー: 機能1つだけ動くプロダクト
```

コードを書く前にLv1〜Lv3で検証できないか考える。

## 事例

### 成功例：Dropbox（ウィザード of Oz MVP）
- 実際のファイル同期システムを作る前に、デモ動画だけ公開
- 2万人のウェイトリスト → 需要があることを証明してから開発

### 個人開発者の成功例
- Twitterで「こんなツール作ろうと思うんですが欲しい人いますか？」とツイート → 反応見てから開発
- ノーコードツール（Notion + Zapier）で手動サービスを先に作り、有料ユーザーが10人できてからコード化

### 失敗例（よくあるパターン）
- 6ヶ月かけてフル機能を作る → リリース後ユーザーが誰も使わない機能がほとんど
- 「あったら便利な機能」をどんどん追加 → コアの価値が伝わらなくなる

---

## アンチパターン

| アンチパターン | なぜ危険か |
|-------------|----------|
| 「もう少し磨いてからリリース」の先延ばし | 市場の反応なしで磨いても方向が間違っている可能性 |
| 競合の機能を全部入れようとする | 差別化がなくなり、大手に勝てない |
| ユーザーの「あったらいいな」を全部作る | ユーザーは欲しいものを言語化できない（ジョブ理論参照） |
| 技術的に面白いものを優先する | 作りたいものとユーザーが求めるものがズレる |
| MVP = バグだらけでいい、と解釈する | 信頼を損ねる。UXは最低限保つ |

## 明日から試せるアクション

1. **今作っているものの機能リストを書き出し、各機能に「これがなければ使えないか？」を問う**
   → Noのものをすべて「v2以降」に移動する

2. **LPを先に作る**
   → 機能を作る前に、サービスの説明と申し込みボタンだけのページを公開し、クリック率を見る

3. **手動でできないか考える**
   → 自動化したい処理を1週間だけ手動でやり、そこで学んだことを仕様に反映する
