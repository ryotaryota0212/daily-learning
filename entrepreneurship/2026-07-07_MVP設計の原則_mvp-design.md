# MVP設計の原則 ── 何を作らないか、最小限の検証方法

## 概要

MVPとは「最小限の検証ツール」であり、製品ではない。個人開発者が陥りやすい罠は、「完成させてからリリース」という思考だ。しかし市場に出してみるまで、何が本当に価値を持つかは誰にも分からない。MVP設計の本質は「作る前に何を削るか」の判断力にある。リソースが限られるソロファウンダーにとって、これは生存戦略そのものだ。

---

## 核となる考え方

- **MVPの目的は「売ること」ではなく「学ぶこと」**
  - 検証したい仮説が1つあれば、それだけを確かめる最小単位がMVP
  - 「これが課題か？」「この解決策か？」「この価格か？」── 仮説ごとにMVPは違う

- **価値仮説 vs. 成長仮説を分けて考える**
  - 価値仮説：ユーザーがそもそも価値を感じるか？
  - 成長仮説：ユーザーが増え続けるか？
  - 最初は価値仮説だけを検証すれば十分

- **「恥ずかしいと思わないなら、出すのが遅すぎる」（Reid Hoffman）**
  - 完成度への執着は自己満足。ユーザーは完成品ではなく問題解決を求めている

- **削れるものリスト**
  - ユーザー管理・認証（最初はGoogle OAuth or 手動招待で代替）
  - ダッシュボード（最初はSlackやスプレッドシートで代替）
  - 課金システム（最初はPayPay/Stripeの手動請求で代替）
  - モバイル対応（デスクトップだけで検証できるか？）
  - 管理画面（手動オペレーションで代替できるか？）

## 実践フレームワーク・ステップ

### ステップ1：検証したい仮説を1文で書く

```
「〇〇という課題を抱えている△△は、□□という方法で解決できる」
```

例：「毎日の支出管理が面倒なフリーランスは、LINEに送るだけで自動仕分けされるツールで解決できる」

### ステップ2：検証に必要な最小機能を洗い出す

| 機能 | 仮説検証に必要？ | 削れる代替手段 |
|---|---|---|
| ユーザー登録 | No | 招待制で1対1でOK |
| LINEで入力受付 | Yes | LINE Bot（無料枠あり） |
| 自動仕分けAI | Yes | 最初は手動で代替 |
| グラフ表示 | No | スプレッドシートで代替 |
| エクスポート | No | CSV手動送付 |

### ステップ3：MVPの種類を選ぶ

| タイプ | 概要 | 向いている場面 |
|---|---|---|
| **コンシェルジュMVP** | 手動で価値を提供し、需要を確認 | BtoB、高単価、少人数 |
| **ランディングページMVP** | 作る前に申し込みを募る | 需要の存在確認 |
| **プロトタイプMVP** | Figma等の非動作画面を見せる | UIへの反応確認 |
| **コード最小MVP** | 核心機能だけ動く | 技術的課題の検証 |
| **既存ツール組み合わせ** | NoCodeで仮実装 | スピード最優先 |

### ステップ4：成功基準を数字で決める（作る前に）

- 「10人が使ったら成功」ではなく「10人中7人が翌週も使ったら成功」
- 曖昧な基準はあとから都合よく解釈されるため、事前に設定必須

## 成功/失敗の事例

### 成功例：Dropboxのランディングページ MVP
- コードを書く前に動画1本で需要を確認
- 登録者7万5千人 → 作る価値があると判断してから開発開始

### 成功例：個人開発者 @levelsio のNomad List
- 最初はGoogleスプレッドシートを公開しただけ
- 反応があってから、Webアプリとして構築
- 現在MRR数十万ドル規模に成長

### 失敗例：「完璧な初期版」を作りすぎたケース
- 6ヶ月かけてフル機能のSaaSを個人開発
- リリース後、ユーザーが使うのはたった1つの機能だけだった
- 残り5つの機能開発は完全に無駄

---

## アンチパターン

- **「もう少し磨いてからリリース」の繰り返し** → 市場の反応なしに品質判断はできない
- **機能を増やすことで差別化しようとする** → MVPに機能は要らない。核心的な価値1つに集中
- **「誰でも使えるように」設計する** → 最初のターゲットは5人。その5人が喜ぶか？だけ考える
- **仮説を決めずに作り始める** → 何を検証するか不明なまま作ると、何が分かったかも分からない
- **失敗を隠す** → 「使ってもらえなかった」は最高の学習データ。記録して次へ

## 明日から試せるアクション

1. **今作ろうとしているものを書き出し、「仮説は何か？」を1文で答える** ── 答えられなければ設計を止めて仮説定義から始める

2. **機能リストを作り、各機能に「削れる代替手段」を書く** ── 代替手段がない機能だけがMVPに入る

3. **成功基準を数字で1つ決める（例：1週間後に3人がリピート利用）** ── 作る前に書いておき、リリース後に答え合わせする
