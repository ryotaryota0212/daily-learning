# MVP設計の原則 — 何を作らないか、最小限の検証方法

## 概要

個人開発者がプロダクト開発で最もよくやる失敗は「誰も使わない完璧なものを3ヶ月かけて作る」こと。MVPの本質は「作ること」ではなく「学ぶこと」。最速で仮説を検証するために、何を作らないかを決める技術が必要。

## 核となる考え方

- **MVPとは最小限の「製品」ではなく最小限の「検証」** — コードなしで検証できるなら書くな
- **Build → Measure → Learn のループを最速で回す** — 1回のループに数週間以上かけない
- **価値仮説と成長仮説を分けて考える** — まず「誰かが使うか」、次に「広がるか」
- **捨てる前提で作る** — MVPのコードは本番コードではない。恥ずかしいくらいがちょうどいい
- **制約が創造性を生む** — 「ランディングページ1枚」「手動オペレーション」「既存ツールの組み合わせ」で十分

## 実践フレームワーク：MVP設計の3ステップ

### Step 1: 検証したい仮説を1つ特定する

```
「[ターゲット]は[課題]を解決するために[解決策]に[対価]を払う」
```

例：「副業フリーランサーは確定申告の複雑さを解消するためにAIツールに月980円払う」

仮説の構成要素を分解：
- **誰の課題か** — セグメントを絞る（全員向けは誰向けでもない）
- **本当に痛みか** — お金か時間を既に使っているか
- **解決策は届くか** — その人に届く配布経路があるか

### Step 2: 最低コストの検証手段を選ぶ

| 検証したいこと | MVPの形 | コスト目安 |
|---|---|---|
| 課題が存在するか | ユーザーインタビュー5件 | 0円・1週間 |
| 解決策に需要があるか | ランディングページ + メール登録 | 0円・2日 |
| お金を払うか | 先払いで注文を取る（Stripe） | 0円・3日 |
| 使い続けるか | 手動オペレーション（コンシェルジュMVP） | 工数のみ・1週間 |
| スケールするか | 実装版プロトタイプ | 数万円・1ヶ月 |

### Step 3: 「作らないもの」リストを明示する

設計の際に以下を明示的に除外する：
- 認証・ログイン機能（最初はメアドだけでいい）
- 管理画面・ダッシュボード（Notionやスプレッドシートで代替）
- 自動化・バッチ処理（手動で動かせるうちは書かない）
- エラーハンドリング・ログ（1人ユーザーなら電話で対応）
- スケール対応（100人以上来てから考える）

## 成功/失敗の事例

**成功例：Dropboxのスモークテスト**
- 実装前にデモ動画1本だけ公開 → 一晩で7万5000件のメール登録
- 「作れるか」ではなく「欲しがるか」だけを検証した

**成功例：Zapierの手動MVP**
- 最初はAPIを人間が手動でつないでいた
- 「自動化」は後から。まず「価値があるか」を検証

**失敗例（個人開発の典型）**
- 「AI家計簿アプリ」を3ヶ月かけてフル実装 → リリース後5人しか使わず
- 事前に「LINE DM経由の手動家計簿サービス」で10人試すべきだった

## アンチパターン（よくある間違い）

- **「もう少し完成させてから見せる」症候群** — 恥ずかしくなければMVPじゃない
- **フィードバックを無視してピボットしない** — 数字が示すサインを「まだ早い」と見て見ぬふり
- **全員に使ってもらおうとする** — 最初の10人は自分で見つけてきた熱狂的なユーザーでいい
- **MVPと言いながら機能を盛る** — 「最小限」の定義をチームで合意しないまま進める
- **技術的な難しさで仮説を選ぶ** — 「面白い技術」ではなく「検証が必要な仮説」を軸にする

## 明日から試せるアクション

1. **仮説を1文で書く** — 今作っているもの（または作りたいもの）の仮説を「[誰]は[課題]のために[解決策]に[対価]を払う」形式で書く
2. **「作らないリスト」を作る** — 機能リストの横に「これはMVPで不要」列を追加し、上記除外基準で仕分ける
3. **最速の検証方法を1つ選ぶ** — コードを書く前に「ランディングページだけで登録が取れるか」試す
