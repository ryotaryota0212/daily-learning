# MVP設計の原則——何を作らないか、最小限の検証方法

## 概要

MVPを「小さい版のプロダクト」と誤解すると失敗する。MVPの本質は「最速で学ぶための実験装置」だ。ソロファウンダーにとって時間とお金は有限。コードを書く前に「何を作らないか」を決めることが、サバイバルの核心になる。

---

## 核となる考え方

- **MVPとはMinimum Viable Productではなく、Minimum Validated Product**
  - 「動くもの」ではなく「仮説を検証できるもの」を作る
- **捨てる前提で作る**
  - MVPのコードは捨てることが多い。綺麗に作らない。技術的負債を恐れない
- **最大の質問は1つ**
  - 「このMVPで検証したい仮説は何か？」が答えられないなら作るな
- **ユーザーの行動がデータ、言葉はノイズ**
  - 「使いたい」と言う人が実際に使うとは限らない。実際の行動を見る
- **スコープは削ぎ落とすもの**
  - 最初のスコープから70%削ぎ落として、ようやくMVPになる感覚

---

## 実践フレームワーク・ステップ

### Step 1: 最重要仮説を1つ特定する

```
仮説テンプレート:
「[ユーザー]は[課題]があるから、[解決策]に[金額/行動]を払う」

例：「フリーランサーは請求書作成に毎月2時間かけているから、
     自動生成ツールに月1,000円払う」
```

### Step 2: 検証方法を選ぶ（コードを書く前に）

| 検証したいこと | 最速の手段 | コード不要度 |
|---|---|---|
| 課題が存在するか | ユーザーインタビュー5件 | ★★★ |
| 解決策の需要 | LP + 事前登録フォーム | ★★☆ |
| 支払意向 | LP + 決済ボタン（仮） | ★★☆ |
| 使いやすさ | Figmaプロトタイプ | ★★★ |
| 継続利用 | 手動で代替（コンシェルジュMVP） | ★★☆ |

**コンシェルジュMVPとは：** プロダクトの代わりに自分が手動で作業してユーザーに提供する。Zapierの初期版はスクリプトを手動で動かしていた。

### Step 3: 成功の定義を先に決める

```
例：
- LP訪問者の20%が事前登録する → 検証成功
- インタビュー10人中7人が「月2,000円まで払える」と言う → 検証成功
- 1週間で3人の有料ユーザーを獲得 → 検証成功
```

### Step 4: 何を作らないかリストを作る

```
「次のバージョン」リストに退避するもの:
- ダッシュボードの詳細グラフ
- 通知設定のカスタマイズ
- チーム機能・権限管理
- API連携（最初は手動でOK）
- モバイルアプリ（Webから始める）
```

## 成功・失敗の事例

### 成功例：Dropboxのスモークテストアプローチ
- 実際のプロダクトを作る前にデモ動画だけを公開
- ベータ登録が1夜で75,000件
- 「欲しいか」を動くプロダクトなしで検証した

### 個人開発の成功例：コンシェルジュMVP
- あるソロ開発者がSEOレポートツールを作る前に、まずクラウドワークスで手動レポートを5件受注
- 受注できたこと・顧客が何を求めているかを把握してからコードを書いた
- 自動化したら同じ価格で利益率90%に

### 失敗例：機能を盛りすぎたMVP
- 「最初から完璧に作ろう」として6ヶ月開発
- リリース後、ユーザーが使う機能は1つだけだと判明
- 作り直しに4ヶ月かかった

## アンチパターン（よくある間違い）

- **「UIが汚いと恥ずかしい」症候群**
  → 初期ユーザーはUIより課題解決を求めている。恥ずかしくなければMVPではない

- **仮説なしに「とりあえず作る」**
  → 検証できないMVPはただの趣味のプロダクト

- **フィードバックを「言葉」で集める**
  → 「良かった」「使いたい」は信用しない。お金を払ったか・毎日使ったかを見る

- **スコープを削れない**
  → 「これは必要」「あれも必要」で肥大化する。削るたびに「本当に今必要か？」と問う

- **MVPを完成形だと思う**
  → MVPは学ぶための道具。学んだら次のMVPを作る。リリースがゴールではない
