# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPとは「最小限の機能で仮説を検証するプロダクト」のこと。個人開発者にとって、これは「何を作るか」より「何を作らないか」を決める技術だ。時間・予算・人手がない1人起業家が最も犯しやすいミスは、「全部作ってから出す」という発想。MVPの核心は、仮説を最速・最安で壊すことで、無駄な開発をゼロにすることにある。

---

## 核となる考え方

- **MVPはプロダクトではなく「実験」** — 検証したい仮説を1つ絞り込み、それだけを確かめる
- **完成度は関係ない** — 見た目が雑でも、仮説が検証できればMVPとして成立
- **最も危険な仮説から潰す** — 「そもそもユーザーはこれを欲しいのか」が一番重要
- **80%の機能は使われない** — ユーザーが本当に使うのは核心機能の20%だけ
- **作る前に売る** — ランディングページへの反応、予約注文、事前登録でニーズを確認できる

### MVPのスペクトラム（低コスト順）

```
コンシェルジュMVP  →  手動MVP  →  LP+メール収集  →  プロトタイプ  →  機能限定版
（人力で代替）      （仕組みなし）  （作らず反応確認）  （UI先行）     （実際に動く）
```

## 実践フレームワーク：5ステップ

### Step 1: 仮説リストを書き出す（15分）
```
- 課題仮説: ○○な人は△△に困っている
- ソリューション仮説: □□を提供すれば解決できる
- 価値仮説: 月額○円払ってもらえる
- 成長仮説: SNS経由で口コミが広がる
```
最も不確かなものに丸をつける。それだけを検証する。

### Step 2: 検証方法を選ぶ

| 検証したいこと | 最安の方法 | コスト目安 |
|---|---|---|
| 課題の深刻さ | ユーザーインタビュー5件 | 0円 |
| 需要の有無 | LP + 事前登録フォーム | 数時間 |
| 支払い意欲 | 「今すぐ買う」ボタンのCTR | 0円（計測のみ） |
| 使い続けるか | 手動でサービス提供 | 自分の時間のみ |
| 競合より優れているか | ユーザーに比較してもらう | インタビュー費 |

### Step 3: 成功基準を先に決める（Goodhart's Law回避）
```
「◯◯が△△%になったら仮説検証済み」
例: 「事前登録20人中15人が1週間後も連絡に返信したら需要あり」
```
始める前に決める。結果を見てから基準を変えるのは無意味。

### Step 4: 1週間で出す
- 1ヶ月以上かかるMVPはMVPではない
- 恥ずかしいと思うくらいが適切（Reid Hoffmanの言葉）
- 出せない理由があれば、それ自体がボトルネック

### Step 5: 学びを記録し次の仮説へ
- 検証結果（数値）
- 外れた仮説とその理由
- 次に検証すべき仮説

## 事例

### 成功例：Dropboxのビデオデモ MVP
- 実際のプロダクトを作る前に、仕組みを説明する3分動画をYouTubeに投稿
- 翌朝ベータ待機リストが75,000人に → 需要確認完了
- **学び**: 動くものがなくても需要は測れる

### 成功例：個人開発SaaSの手動MVP
- 自動化ツールを作る前に、同じ処理を手作業でGoogleスプレッドシートで実施
- 3人の顧客から月5,000円×3件 → 収益確認後にコードを書いた
- **学び**: コードを書く前に「手動で稼ぐ」が最速の検証

### 失敗例：6ヶ月かけて作った誰も使わないアプリ
- 想定ユーザーへのインタビューをせず、「絶対需要がある」と確信して開発
- リリース後のDAU: 3人（全員友達）
- **学び**: 確信は仮説。検証なき開発は全て無駄になるリスクがある

---

## アンチパターン

- **完璧主義MVP**: デザインを磨き続けて3ヶ月後にリリース → 仮説検証が遅れるだけ
- **機能盛り込みMVP**: 「これも必要、あれも必要」と全部作る → どの機能が効いたか不明になる
- **友達だけに見せるMVP**: 忖度された「いいね」を信用する → 本当のユーザーの反応が分からない
- **数値なしのMVP**: 「反応が良かった」だけで次に進む → 再現性がない
- **競合を見ないMVP**: 既にある解決策を無視して作る → 差別化できない

## 明日から試せるアクション（3つ）

1. **今取り組んでいるアイデアの「最も危険な仮説」を1つ書き出す**
   → 「これが外れたらプロダクト全体が成立しない」という仮説を特定する

2. **LP（ランディングページ）だけを1日で作って公開する**
   → Notionページ、Google Form、Twitterスレッドでも代替可能。反応を見る

3. **次の開発タスクに「これは何の仮説検証か？」を書く**
   → 仮説と紐づかない機能は実装しない習慣をつける
