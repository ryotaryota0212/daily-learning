# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPとは「Minimum Viable Product（実用最小限のプロダクト）」のこと。
多くの個人開発者が「フル機能を作ってからリリース」して失敗する。
MVPの本質は「作らない決断」と「最速で仮説を検証する手段を選ぶこと」にある。
予算・時間・人手が限られるソロファウンダーにとって、MVPの設計力は生死を分けるスキル。

---

## 核となる考え方

- **MVPは製品ではなく実験**：売れるかを確かめるための最小コスト手段
- **「最小（Minimum）」は機能数ではなく「検証コスト」を最小化すること**
- **「実用（Viable）」はユーザーが価値を感じられる最低ライン**
- リリース前に「この機能で検証したい仮説は何か？」を1つ明確にする
- 機能追加の誘惑は常にある。追加しないことを意思決定として扱う

### MVPの3つのレベル

| レベル | 手段 | コード量 |
|--------|------|----------|
| Smoke Test | LP + 購入ボタン（404でOK）| ほぼゼロ |
| Wizard of Oz | 手動でやる（ツールは本物に見せる）| 最小限 |
| Concierge | 1対1で人力提供 → のちに自動化 | ゼロ〜小 |

## 実践フレームワーク・ステップ

### Step 1: 検証したい仮説を1つ決める

```
「○○という課題を持つ△△が、□□という方法で解決できるなら、
XXX円払う」
```

この文章が書けなければMVPを作り始めてはいけない。

### Step 2: 仮説を検証する最小手段を選ぶ

- **課題の存在確認** → ユーザーインタビュー5人（コードゼロ）
- **解決策への需要確認** → LP作成 + 事前登録フォーム
- **支払い意思の確認** → 決済フォーム + 手動納品
- **継続利用の確認** → 1機能だけのプロトタイプ

### Step 3: 「作らないリスト」を明示する

MVP設計では何を作るかより**何を作らないか**を決める。

| 作る | 作らない |
|------|----------|
| コア機能1つ | 管理画面 |
| 手動運用で代替できるもの | 自動化・通知 |
| 最低限のUI | デザインの磨き込み |
| 決済（Stripeで最速） | マルチプラン |

### Step 4: 成功条件を数字で設定する

「良い反応があれば続ける」は失敗する。

- ✅ 「10人中7人が問題を認識する → 課題仮説OK」
- ✅ 「LPのCVR 5%以上 → 需要仮説OK」
- ✅ 「3人が5,000円払う → 支払意思OK」

## 成功・失敗事例

### 成功例：Dropbox（Smoke Test）

実際にファイル同期機能を作る前に、**動くデモ動画だけ**をHacker Newsに投稿。
一晩で7万人が登録 → 需要を確認してから開発開始。

### 成功例：個人開発SaaS（Wizard of Oz）

Notion + Zapier + スプレッドシートで「AIが自動分析します」と見せかけて手動対応。
10人が月額3,000円を支払ったのを確認してから自動化を実装。

### 失敗例：機能過多で沈む個人開発

「どうせ必要になるから」とログイン・管理画面・通知・マルチユーザーを最初から実装。
3ヶ月後にリリースしたが誰も使わず。問題：誰のためのどの課題を解くのか不明だった。

## アンチパターン

- **「いつか使われるかもしれない機能」を作る** → YAGNIを徹底せよ
- **競合と同等の機能数を目指す** → 1点突破でよい。10点満点より1点100点
- **完成させてからフィードバックを得る** → 最初の1日目にユーザーに見せる
- **MVP = バグだらけでもいい** → 雑なUXは検証ノイズになる。最低限の品質は守る
- **「無料で出して反応見る」を繰り返す** → 支払い意思の確認なしに本当の需要は測れない

## 明日から試せるアクション（3つ）

1. **今作っているもの（または作ろうとしているもの）の「検証したい仮説」を1文で書く**
   → 書けなければ設計を止めて仮説を先に作る

2. **機能リストを作り、「コードゼロで代替できるもの」に線を引く**
   → Notion・Googleフォーム・Calendly・Stripeで代替できる機能は全部後回し

3. **「成功条件」を数字で決めてから作業を始める**
   → 例：「1週間以内に3人の知人に見せて、2人が『使いたい』と言ったら続ける」
