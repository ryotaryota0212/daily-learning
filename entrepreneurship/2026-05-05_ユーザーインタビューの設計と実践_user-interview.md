# ユーザーインタビューの設計と実践

## 概要

プロダクトを作る前に「誰の、どんな問題を解くか」を確かめる最も重要な手段がユーザーインタビューだ。
コードは書けるが「何を作るべきか」が分からない状態は、個人開発者が最も陥りやすい罠。
仮説ドリブンで質問を設計し、定性情報を構造化することで、無駄な開発を回避できる。
PMFを見つける前に数百時間かけてフルプロダクトを作ることを防ぐための武器。

---

## 核となる考え方

- **インタビューの目的は「検証」ではなく「発見」**：仮説が正しいか確認するのではなく、知らない事実を掘り起こす
- **過去の行動を聞く、未来の意図は聞かない**：「使いますか？」は嘘になる。「最後にそれで困ったのはいつですか？」が本物
- **ソリューションを語らない**：インタビュー中に自分のプロダクトを説明すると回答が汚染される
- **沈黙は武器**：答えが出た後に黙ると、相手は深掘りした本音を話す
- **「なぜ」を3回掘る**：表面の答えの奥に本当のジョブ（動機）がある

## 実践フレームワーク・ステップ

### 1. 仮説シートを作る（インタビュー前）

| 項目 | 内容 |
|------|------|
| ターゲット | どんな人？（職種、状況、行動特性） |
| 想定課題 | この人が困っていると仮説する問題 |
| 検証したい問い | インタビューで明らかにしたいこと |

### 2. 質問の設計（5〜7問に絞る）

**良い質問の型：**
- 「〇〇するとき、今どうやっていますか？」（現在のワークフロー）
- 「最後に〇〇で困ったのはいつですか？その時何が起きましたか？」（具体的エピソード）
- 「それを解決しようとしたことはありますか？何を試しましたか？」（代替手段の把握）
- 「その問題、どれくらい深刻ですか？スケール1〜10で」（深刻度の定量化）

**避ける質問：**
- 「〇〇という機能があったら使いたいですか？」→ Yes/Noで終わる、かつ嘘が多い
- 「〜だと思いませんか？」→ 誘導尋問

### 3. インタビューの実施（30〜45分/人）

1. アイスブレイク：相手の仕事・日常を聞く（5分）
2. コアな問題領域を探る（20分）
3. 現在の解決策・ツールを聞く（10分）
4. 最後に自由回答「他に伝えたいことは？」（5分）

### 4. インタビュー後の分析

- **発言の記録**：直接引用を残す（解釈ではなく言葉そのまま）
- **アフィニティマッピング**：付箋（FigJamやMiro）でパターンを見つける
- **Jobs to be Done抽出**：「〜するとき、〜したい（機能的ジョブ）」の形式で整理

## 成功・失敗の事例

### 成功例：Superhuman（メールクライアント）
- 創業者Rahul Vohra は初期ユーザー数百人に個別インタビューを実施
- 「非常に残念に思うか」という質問でPMFスコアを定量化（40%以上が指標）
- インタビューで明らかになった「スピード感」という本質的ジョブに絞って開発

### 失敗例：個人開発者あるある
- 「友達に話したら良いと言われた」→ 友達は傷つけたくないから否定しない
- X（Twitter）でアンケートを取って「需要あり」と判断 → フォロワーは知人・同業者バイアス
- インタビューせず6ヶ月開発、ローンチ後ユーザーゼロ

## アンチパターン

- **母に聞く（Mom Test違反）**：近しい人は肯定的に答えがち → 知らない人・実際の見込みユーザーに聞く
- **自分のプロダクトを売り込む**：インタビューをデモに変えてしまい、本音が消える
- **n=3で結論を出す**：最低10〜15人は話す。ただし同じパターンが繰り返されたら打ち切りOK
- **メモを後で取る**：記憶は変質する。リアルタイムか録音を使う（許可を取る）
- **定量アンケートだけで済ます**：なぜそう答えたかが分からない
