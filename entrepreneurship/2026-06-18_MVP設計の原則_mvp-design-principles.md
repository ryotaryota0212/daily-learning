# MVP設計の原則 — 何を作らないかで勝負が決まる

## 概要

個人開発者が陥る最大の罠は「完璧なプロダクトを作り込んでからリリースする」こと。
MVPとは"最小限の製品"ではなく**"最速で学べる実験"**だ。
リソースが乏しいソロファウンダーほど、作る前に「これは本当に必要か？」を問い続ける必要がある。
MVPの本質はコード量を減らすことではなく、**検証コストを下げながら学習速度を上げること**にある。

---

## 核となる考え方

- **MVPのMはMinimum、VはViable（実行可能）** — 動かないモックは「Viable」ではない
- **作らないことがデフォルト** — 機能追加の理由は「ユーザーが困っている証拠」であるべき
- **仮説→検証のサイクルが最重要** — 正しいものを速く作るより、正しいかを速く知ることが先
- **価値仮説と成長仮説を分けて考える**
  - 価値仮説：「このプロダクトはユーザーに価値を届けられるか？」
  - 成長仮説：「ユーザーは増えていくか？」
- **Fake it before you make it** — 手動で代替できることはコードを書かなくていい

---

## 実践フレームワーク

### ステップ1：「最もリスクの高い仮説」を1つ特定する

```
仮説例：「フリーランスエンジニアは請求書作成に毎月1時間以上かけており、自動化に月3,000円払う」
```

- 仮説を「誰が」「何に困っていて」「どれだけ払うか」の3つに分解する
- 最も不確かな部分＝最初に検証すべき仮説

### ステップ2：MVP類型から選ぶ

| 類型 | 概要 | 向くフェーズ |
|------|------|------------|
| **ランディングページ型** | 機能の説明＋事前登録ボタン | 需要の有無を調べたい |
| **コンシェルジュ型** | 裏は手動、表はプロダクト風 | 業務フローを理解したい |
| **ウィザード・オブ・オズ型** | AIのふりをして人間が処理 | 自動化の価値を検証したい |
| **プロトタイプ型** | Figmaやnotionで疑似体験 | UXのアイデアを素早くテスト |
| **スモークテスト型** | 存在しない商品の決済ページ | 購入意欲を測りたい |

### ステップ3：「作らない機能リスト」を先に書く

```
今回のMVPでは作らない：
- ユーザー管理・認証（最初はメールで手動招待）
- 通知機能（最初はSlack DMで代替）
- 管理画面（最初はDBを直接見る）
- モバイル対応（最初はPC限定）
```

作らない理由を書いておくと、後の誘惑に流されにくい。

### ステップ4：成功条件を先に定義する

- **検証する前に「何があれば仮説が正しいと判断するか」を決める**
- 例：「2週間以内に10人が事前登録 → 需要ありとみなす」
- 数字が曖昧だと、結果を自分の都合よく解釈してしまう

## 成功・失敗の事例

### 成功例：Dropboxのスモークテスト型MVP
- コードをほぼ書かずに、機能の動画デモを公開
- 1本の動画で7万5000人が登録 → 需要を確認してから開発開始
- **学び**：動くプロダクトより「ユーザーが欲しいと感じる瞬間」を先に作る

### 成功例：個人開発のコンシェルジュ型
- 「AIで議事録を要約」アプリをリリース前にDM受付で手動サービスとして試験
- 10人の無料モニターに毎日手動で要約を送り、フィードバックを収集
- 有料化した際の継続率と改善点が明確になってから自動化に着手

### 失敗例：完璧を追い求めた個人開発
- 6ヶ月かけてフル機能のSaaSを開発 → リリース後ユーザー0人
- 「作っている間に市場が変わった」「そもそも誰も困っていなかった」
- **学び**：開発期間と検証できない期間は比例する

## アンチパターン

- **「もう少し作ってからリリース」の無限ループ** — 完成度への固執が最大の敵
- **技術的に面白いものを作る** — 自分が作りたいものとユーザーが必要なものは別
- **1つのMVPで複数の仮説を同時検証** — 何が効いたか・効かなかったかが判断できなくなる
- **友人へのヒアリングで「需要あり」と判断** — 気を遣って「良いね」と言うだけのケースが多い
- **MVPをリリースして終わり** — MVPはリリースが始まりであり、学習サイクルを回し続けることが目的

## 明日から試せるアクション

1. **今取り組んでいるプロダクトの機能リストを作り、半分を「作らない」欄に移す**
   - 「これがないと使えない」ではなく「これがなくても核心の価値は届くか？」で判断

2. **最もリスクの高い仮説を1文で書き、「何があれば検証完了か」を数字で定義する**
   - 例：「○○ユーザーが○週間以内に○回○する → 仮説：正」

3. **次のMVPの着地点を「ランディングページ型」「コンシェルジュ型」のどちらかで先に動かす**
   - コードを書く前に、メールかDMで10人に手動でサービスを届けてみる
