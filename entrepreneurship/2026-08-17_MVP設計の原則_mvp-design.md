# MVP設計の原則 ― 何を作らないか、最小限の検証方法

## 概要

MVPとは「Minimum Viable Product（実用最小限のプロダクト）」。多くの個人開発者はここで誤解する――MVPは「機能を削ったプロダクト」ではなく、「仮説を検証するための最小限の実験装置」だ。コードを書く前に「何を証明したいのか」を定義しなければ、誰も使わないプロダクトに数ヶ月を費やすことになる。1人・少ない予算で戦うソロファウンダーには、最小単位で学び、最速で方向修正する力が生死を分ける。

---

## 核となる考え方

- **仮説ファーストで考える**: プロダクトを作る前に「○○な課題を持つ人は、△△という解決策に□□円払う」という仮説を言語化する
- **ビルドトラップを避ける**: 作ることが目的化し、学びが生まれない状態。機能追加 ≠ 前進
- **最小とは「ユーザーが価値を受け取れる最低限」**: 見た目が粗くても、ユーザーが目的を達成できれば合格
- **検証したいリスクの優先順位をつける**: 技術リスクより先に「欲しいと思う人がいるか」を確かめる
- **スピードが競争優位**: 大企業より速く学び、速く修正できることが個人開発者の唯一の武器

## 実践フレームワーク・ステップ

### Step 1: 最大リスクの特定（着手前5分で書く）

| リスクの種類 | 問い |
|---|---|
| 欲求リスク | そもそも課題を感じている人はいるか |
| 利用リスク | 解決策を使ってくれるか |
| 支払リスク | お金を払ってくれるか |
| 技術リスク | 実際に作れるか |

→ 欲求・利用・支払を先に検証し、技術は最後に解決する

### Step 2: 検証方法を選ぶ（コードを書かない選択肢から）

1. **フェイクドア**: ランディングページだけ作り、購入ボタンを押した数を計測（例：Dropboxの動画MVP）
2. **手動代替（コンシェルジュ型）**: 自動化せず手作業で価値を届ける。ロードを確認してから自動化（例：Zapierの初期）
3. **ウィザード・オブ・オズ型**: 裏でAIを手動で動かす、機械に見せかけた人間オペレーション
4. **既存ツール組み合わせ**: Notion + Typeform + Stripe で仮の商品ページを作る

### Step 3: 成功条件を数値で決める（作る前に）

- 「LP訪問者の○%がメルマガ登録」「5人中3人が試用版を継続」など
- 「反応が良かった」という主観判断を避ける

### Step 4: 学習ループを回す

```
仮説を立てる → 最小限で実験 → データを計測 → 学ぶ → 次の仮説へ
（2週間以内に1サイクル回す）
```

## 事例

### 成功例: Superhuman（メールクライアント）

- いきなりアプリを作らず、創業者が手動でユーザーの設定を代行するオンボーディングを実施
- 実際に使う姿を観察することでUXを磨き、PMFを確認してから本開発へ

### 個人開発者の失敗例（典型）

- SaaS管理ツールを6ヶ月かけてフル機能で作った
- ローンチ後のユーザー数：0
- 原因：「課題があるか」を確かめずにコードを書き始めた

### 成功例: IndieHackerで見るパターン

- LP + Gumrodで販売ページだけ作成 → 購入者が出たらプロダクト開発開始
- Twitterで「こんなツール欲しい人いる？」と聞いて10人手挙げ → 手動で提供 → 自動化

## アンチパターン

- **「とりあえず完璧に作ってからリリース」**: 完璧なプロダクトより1件の顧客の声が価値がある
- **「フィードバックが来ないから改善できない」**: MVPは自分から使い方を観察しに行く
- **「まず技術スタックを決める」**: 技術選定より先に課題の検証。Notionで代替できる機能を実装するな
- **「既存ユーザーへのインタビューをMVPと呼ぶ」**: インタビューは仮説収集、MVPは仮説検証
- **「小さいから恥ずかしい」**: 恥ずかしくないと感じるなら出しすぎ（Reid Hoffmanの言葉）

1. **今のアイデアの「最大リスク」を1つ書き出す** ― 欲求・利用・支払・技術のどれか？ そこだけを2週間で検証する実験を設計する

3. **成功条件を数値で決める** ― 「5人が使い続けたらプロトタイプを作る」など、次のステップに進む条件を先に明文化する
