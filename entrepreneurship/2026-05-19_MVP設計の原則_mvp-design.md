# MVP設計の原則 — 何を作らないかが勝負

## 概要

MVP（Minimum Viable Product）は「最小限の機能で最大限の学習を得るもの」。
多くの個人開発者が陥る罠は「完成度の高い製品を作ってからリリース」すること。
しかし市場に出るまで何が本当に必要かは誰にもわからない。
MVPの本質は「作る量を絞り、早く仮説を検証し、学習サイクルを回す」こと。
1人・少予算でも、正しいMVPなら数週間で市場の反応を得られる。

---

## 核となる考え方

- **MVPはプロダクトではなく「実験装置」** → 目的は学習、販売ではない
- **「最小限」は機能数ではなく「仮説を検証できる最小コスト」**
- **削るものを先に決める** → リストアップ後、下位70%をすべて捨てる
- **コアバリューは1つに絞る** → 「〇〇ができる」だけでいい
- **完璧なUXは後でいい** → Doorkeyなどは最初Excelとメールで運営していた
- **偽物MVPも有効** → Zapierは最初スプレッドシート＋手作業で動いていた

---

## 実践フレームワーク：MVPを設計する5ステップ

### Step 1｜検証したい仮説を1文で書く
```
「[ターゲット]は[問題]を解決するために[ソリューション]に[金額/時間]を払う」
```
例：「フリーランスエンジニアは請求書管理の手間を省くためにSaaS月額1000円を払う」

### Step 2｜仮説を検証するための「最小の問い」を定める
- 「本当に課題が存在するか？」（需要検証）
- 「解決策を使うか？」（解決策検証）
- 「お金を払うか？」（支払意欲検証）

### Step 3｜検証方法を選ぶ（安い順）

| コスト | 方法 | 期間 |
|-------|------|------|
| ゼロ | インタビュー10人 | 1週間 |
| 低 | ランディングページ＋メール登録 | 3日 |
| 低 | Notionで疑似サービス運用 | 1週間 |
| 中 | ノーコードで動くプロトタイプ | 2週間 |
| 高 | コーディングしてβ版リリース | 1ヶ月〜 |

→ **できる限り上から試す。コーディングは最後の手段**

### Step 4｜「作らないリスト」を明示する
```
【今回作らない】
- 管理画面
- 複数ユーザー対応
- APIインテグレーション
- モバイルアプリ
- 通知機能
```

### Step 5｜成功の定義を数値で決めてから始める
- 例：「2週間でLP登録者30人、またはインタビュー5人中3人が『使いたい』と答える」
- この数値に達しなければピボット or 中止

## 事例

### 成功事例：Dropbox（ビデオMVP）
- 実際のプロダクトを作る前にデモ動画を公開
- 一晩でベータ登録者が5万人→需要を確認してから開発
- **コスト：動画制作のみ**

### 個人開発者の事例
- 「AIで議事録自動化」→まずGPT APIとGoogleフォームで手動テスト
- 5人が「これ毎週使いたい」と言ったのを確認してから開発
- 初月から有料ユーザー獲得

### 失敗事例
- 6ヶ月かけてフル機能実装 → リリース後ユーザーがゼロ
- 「ニーズがあると思った」だけで検証なし → 典型的なパターン

---

## アンチパターン

- **機能を追加しながら「これもないとユーザーが使えない」と言い続ける** → 完成しない
- **インタビューで「使いますか？」と聞いて「はい」をニーズと思い込む** → 行動を見る
- **競合に全機能あるから自分も必要と考える** → 競合の弱点1点を突けば十分
- **ベータ版を無料で公開してフィードバックを待つ** → 無料ユーザーのフィードバックは当てにならない
- **MVPをリリースしても「まだ恥ずかしい」と広めない** → 見られなければ意味がない
