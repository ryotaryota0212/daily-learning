# MVP設計の原則 — 何を作らないか、最小限の検証方法

## 概要

個人開発者が最も陥りやすい罠は「誰も使わないものを完璧に作り上げること」だ。MVPとは「最低限の機能で仮説を検証する手段」であり、プロダクトを届けるゴールではなく**学びを得るための実験装置**。リソースが限られたソロファウンダーこそ、何を削るかの判断力が事業の生死を分ける。

---

## 核となる考え方

- **MVPの本質は「最小学習単位」**。機能を削ることが目的ではなく、最速で仮説を証明・反証すること
- **検証すべき仮説を1つに絞る**。「これが価値を感じてもらえるか」「このチャネルで届くか」は別の実験
- **作るコストより学ぶコストを最小化する**。機能を作る前に「手動で代替できるか」を必ず問う
- **完成度よりもユーザーの行動データ**。5人のユーザーの生の反応は100人のアンケートより価値がある
- ペイン（痛み）の強さがMVPの必要機能数を決める。強いペインなら荒削りでも使われる

---

## 実践フレームワーク・ステップ

### ステップ1：コアな仮説を1文で書く

```
「[ターゲット] は [問題] を抱えており、[解決策] によって [価値] を得られる」
```

例：「副業フリーランサーは請求書作成に毎月1時間を無駄にしており、自動生成ツールで月1時間を節約できる」

### ステップ2：「何を作らないか」リストを作る

削除候補の判断軸：
- 仮説の検証に直接関係しない機能 → 削除
- 「あったら便利」レベルの機能 → 削除
- ユーザーから明示的に求められていない機能 → 削除
- 手動オペレーションで代替できる部分 → 自動化を後回し

### ステップ3：MVPの形式を選ぶ

| 形式 | 向いている仮説 | 工数目安 |
|---|---|---|
| ランディングページ + メール登録 | 需要の有無 | 1日 |
| Nocode / スプレッドシート | 業務フロー価値 | 2〜3日 |
| 手動提供（コンシェルジュMVP） | 提供価値の質 | 0日（人力） |
| プロトタイプ動画 | UIへの反応 | 半日 |
| 最小機能のWebアプリ | 実使用の行動 | 1〜2週間 |

### ステップ4：成功指標を事前に決める

- 何人が使ったら「仮説OK」か？
- 何%が継続したら「価値あり」か？
- 何件の問い合わせがあれば「需要あり」か？

指標を先に決めないと「なんとなく続ける」罠にはまる。

### ステップ5：2週間サイクルで検証・廃棄・次へ

```
仮説設定 → 最小実験 → データ収集 → 学習 → 次の仮説
（2週間以内に1サイクル回す）
```

---

## 事例

### 成功例：Dropbox（コンシェルジュMVP）

実際のファイル同期機能を作る前に、機能を説明するデモ動画だけ公開。事前登録が75,000件集まり、需要を確認してから開発した。個人開発でも同じことができる。

### 成功例：個人開発SaaSのランディングページ検証

日本の個人開発者がNotion + Typeformだけで「請求書自動化ツール」のLPを作成、有料プラン事前登録を受付。50件集まった時点で開発を開始し、初月からMRR 30万円を達成。

### 失敗例：フル機能を3ヶ月で作った個人開発者

「競合より機能が多いほうが勝てる」と思い、3ヶ月かけてフル機能SaaSを完成。リリース後、ユーザーが求めていたのは機能の豊富さではなく「導入の簡単さ」だったことが判明。3ヶ月分の工数が無駄に。

---

## アンチパターン

- **「もう少し完成させてからリリースしよう」の無限ループ** → リリース日を先に決める
- **MVPにデザインの完成度を求める** → ユーザーは課題解決に対価を払う、見た目には払わない（初期は）
- **ユーザーの声なしに機能追加を続ける** → 想像ではなくデータで判断する
- **検証指標を後付けする** → 「まあまあ使われてるからOK」は学びゼロ
- **コンシェルジュ段階をスキップしてすぐ自動化する** → 手動で10人に届けることで見えるインサイトがある

## 明日から試せるアクション（3つ）

1. **今作っているプロダクト（または作ろうとしているもの）の「削除リスト」を作る** — 仮説検証に不要な機能を全部書き出し、最初のリリースから外す
2. **ランディングページだけ先に作って公開する** — 機能ゼロでも「事前登録」ボタンを設置し、需要の有無を1週間で確認する
3. **「これが成功したと言える数字」を今日中に1つ決める** — 登録者数、有料転換数、継続率など、検証前に指標を明文化する
