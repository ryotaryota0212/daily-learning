# MVP設計の原則 — 何を作らないかで決まる最小検証

## 概要

個人開発者が陥りがちな罠は「全部作ってから出す」こと。MVPの本質は「最速でリスクを消すこと」であり、コードを書く量を減らす技術だ。予算・時間・人手が限られるソロファウンダーにとって、MVP設計は最重要スキルの一つ。作るべきものを絞り込む判断力が、プロダクトの生死を分ける。

---

## 核となる考え方

- **MVP = 仮説検証装置**。プロダクトではなく「問いへの答えを得るツール」と捉える
- **削ることが設計**。追加する機能より「これがなくても検証できるか？」を問う
- **最大のリスクを最初に潰す**。「本当に人は金を払うか」を最初に検証する
- **完成度ではなく学習速度が基準**。恥ずかしいと思うなら出すのが遅すぎる（Reid Hoffman）
- **ユーザーの行動で検証する**。「使いたい」という言葉より「使った」という事実を信じる

---

## 実践フレームワーク・ステップ

### Step 1：仮説を言語化する（30分）

```
課題仮説：[ターゲット]は[課題]に困っている
解決仮説：[解決策]によって[成果]を得られる
収益仮説：[ターゲット]は[金額]を払う
```

この3つの仮説のうち、**最も不確かなもの**から検証する。

### Step 2：機能を3分類する

| 分類 | 基準 | 行動 |
|------|------|------|
| Core | 仮説の検証に必須 | 作る |
| Nice | あると良いが検証に不要 | 後回し |
| Waste | ユーザーが求めていない想定 | 捨てる |

### Step 3：最小の検証手段を選ぶ

| 検証したいこと | MVPの形 |
|---------------|---------|
| 課題が存在するか | ユーザーインタビュー（コードゼロ） |
| 解決策に需要あるか | LP + 事前登録フォーム |
| 操作性・UX | Figmaプロトタイプ |
| 実際に使うか | ウィザードオブオズ（裏で手動対応） |
| 継続して使うか | 招待制クローズドβ |
| 金を払うか | 決済フォーム（実装前に受注） |

### Step 4：成功基準を先に定義する

- 数値で定義する（「良い反応」ではなく「10人中7人が再訪」）
- 期間を決める（「2週間以内に」）
- 検証後の行動を決める（続ける/ピボット/中止）

## 成功・失敗の事例

### 成功例：Dropbox
- コードを書く前にデモ動画1本を公開
- 事前登録が75,000件 → 需要確認後に開発着手
- **学び：「作る前に売る」が最強のMVP**

### 成功例（個人開発）：Nomad List（Pieter Levels）
- 最初はGoogle Spreadsheetを公開しただけ
- バズったのを確認してからWebアプリ化
- **学び：既存ツールで「仮」版を作るのも立派なMVP**

### 失敗例：個人開発者あるある
- 6ヶ月かけてフル機能を開発 → リリース後ユーザーゼロ
- 「UI が完成してから見せたい」という完璧主義 → 機会損失
- **学び：恥ずかしいうちに出せなかったものは、出せるころには遅い**

---

## アンチパターン

- **機能追加でPMFを探す**：コアの課題が解決できていないのに機能を増やしても意味なし
- **友達・家族だけに見せる**：「良いね」という優しい嘘に騙される
- **定性フィードバックだけで判断する**：「使ってみたい」は行動データではない
- **技術的に面白いものを作る**：ユーザーが必要なものではなく、自分が作りたいものを優先する
- **完全なMVPを目指す**：「最小」の基準を上げ続けてリリースできない

3. **LPだけ作って事前登録を集める（目標：1週間以内に10人）。登録ゼロなら作るものを再考する**
