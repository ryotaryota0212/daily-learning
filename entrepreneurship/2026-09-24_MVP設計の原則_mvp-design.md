# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPは「最小限の機能を持つ製品」ではなく、**「最速で仮説を検証する手段」**だ。
多くの個人開発者はMVPと称して機能を削りながらも、3ヶ月かけてコードを書く。
本当のMVPは、コードすら書かないこともある。
「作ること」より「学ぶこと」を優先する思考が、時間・お金・精神力を節約する。

---

## 核となる考え方

- **MVPの目的は販売ではなく「仮説検証」**
  - 「このユーザーはこの問題を持っている」「この解決策に価値を感じる」という仮説を最速で確認する
- **作ること≠検証すること**
  - アンケート、LP、手動オペレーション、プロトタイプで検証できるなら、コードは不要
- **削れる機能は「あったらいい」なもの全て**
  - 通知、設定画面、管理画面、SNSログイン、多言語対応、ダッシュボード…ほぼ全部あとでいい
- **フィードバックループの速さが命**
  - 仮説→実験→学習→修正 のサイクルを1週間以内で回す
- **完成させる必要はない。動かせばいい**
  - バグがあっても、デザインが汚くても、最初の10人のユーザーには関係ない

## 実践フレームワーク：MVP設計3ステップ

### Step 1：検証したい仮説を1文で書く

```
「[ターゲット] は [課題] に困っており、[解決策] に [金額/行動] を払う」
```

例：「フリーランスエンジニアは請求書作成に毎月30分ムダにしており、
自動化ツールに月1,000円払う」

### Step 2：検証手段を選ぶ（安い順）

| 手段 | コスト | 検証できること |
|------|--------|--------------|
| 直接インタビュー（5人） | 0円・3日 | 課題の存在確認 |
| Notionで作ったLP | 0円・1日 | 価値訴求が刺さるか |
| LP＋メール登録フォーム | 0円・1日 | 需要の存在確認 |
| 手動オペレーション（Concierge MVP） | 0円・1週間 | ソリューション検証 |
| プロトタイプ（Figmaなど） | 0円・3日 | UXフロー検証 |
| コードなしツール（Glide/Bubble） | 低コスト・1週間 | 機能検証 |
| 実際のコード | 高コスト・数週間 | スケール検証 |

### Step 3：「成功の定義」を先に決める

検証前に「この数字が出たらGO」を決める。

例：
- LP登録率が10%以上 → 開発にGO
- 5人中3人がお金を払う意思表示 → 開発にGO
- 手動サービスを1ヶ月継続利用 → 自動化にGO

## 成功／失敗の事例

### 成功例：Dropbox（Concierge MVP）

プロトタイプ動画1本でメール登録75,000件を獲得。コードを書く前に需要を確認した。
個人開発版では「LP＋Twitterでの告知→メール登録数」で初期需要を測る同様のアプローチが有効。

### 失敗例：機能満載で3ヶ月後にリリース

「全部作ってからリリース」型の個人開発者の典型。
リリース後、誰も使わないことが判明。3ヶ月の時間を失う。
早期の5人ユーザーインタビューで「実は困っていない」が分かっていた。

### 個人開発の成功パターン

- LP公開→1週間で10人からDMが来る→開発スタート
- 「Notionテンプレート」で手動提供→有料購入が3件→自動化ツール化
- TwitterでMVPアイデアを投稿→反応の種類と数で需要確認

---

## アンチパターン

- **「完璧なUIを作ってからリリース」** → 永遠にリリースできない
- **「全機能入れてからユーザーに見せる」** → フィードバックが遅すぎる
- **「友達にだけ見せる」** → 本当のターゲットの反応が分からない
- **「リリースしたから後は待つだけ」** → 能動的に最初の10人を集める必要がある
- **「MVPなのに管理画面を作る」** → 最初はスプレッドシートで十分
- **「数字を測定しない」** → 感覚だけで「うまくいっている」と思い込む
