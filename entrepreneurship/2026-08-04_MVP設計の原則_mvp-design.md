# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPはMinimum Viable Productの略だが、「最低限の機能を詰め込む」ではなく「最速で仮説を検証する手段」として捉えることが本質。個人開発者はコードを書く能力があるゆえに「作りすぎる罠」に陥りやすい。MVP設計の核心は「何を作らないか」の選択にある。誰かに使われる前に費やした時間とコードはすべてリスクであり、検証なき実装は無駄になる可能性が高い。

---

## 核となる考え方

- **リスクの最小化**: MVPは「製品の最小版」ではなく「リスクの最小化装置」
- **仮説の可視化**: 何を検証したいかを先に言語化する。検証なきMVPはただの未完成品
- **価値の核心だけを残す**: ユーザーが「これがなければ使わない」という機能のみに絞る
- **スピードが正義**: 3ヶ月かけた完成品より、2週間で出した実験の方が多くを学べる
- **作らなくていい機能のシグナル**: ユーザーに聞かれていない、自分が欲しいだけ、競合が持っている

## 実践フレームワーク・ステップ

### Step 1: 検証したい仮説を1文で書く

```
「[ターゲット] は [問題] に悩んでいて、[解決策] があれば [行動/支払い] する」
```

例: 「副業フリーランサーは請求書作成に毎月2時間取られていて、自動化ツールがあれば月1,000円払う」

### Step 2: 仮説を「最速で」検証する方法を選ぶ

| 検証タイプ | 方法 | 期間 |
|---|---|---|
| 需要検証 | LP + 事前登録フォーム | 1〜3日 |
| 課題検証 | ユーザーインタビュー5件 | 1週間 |
| 解決策検証 | Figmaモックで反応確認 | 3日 |
| 支払意向検証 | 手動オペレーション（OzのWizard） | 1〜2週間 |
| 製品検証 | 実動するMVPリリース | 2〜4週間 |

### Step 3: 「削除リスト」を作る

MVPに入れない機能をあえてリスト化する。入れたい衝動が出たとき、削除リストに戻る。

- 「あったら便利」な機能 → 削除
- 「競合が持っている」機能 → 削除（今は不要）
- 「スケール後に必要」な機能 → 削除（今は手動でよい）
- 「自分が欲しい」機能 → 要検討（本当にユーザーも欲しいか？）

### Step 4: 成功の定義を先に決める

```
「もし [指標] が [数値] に達したら、仮説は検証できたとみなす」
```

例: 「2週間でLP訪問者の10%が事前登録したら需要あり」

## 成功・失敗の事例

### 成功: Dropbox の Explainer Video MVP
コードを1行も書かずにデモ動画だけ公開 → 一晩でベータ登録が75,000件に。「需要の検証」だけに絞ったMVP。

### 成功: 個人開発者のSaaSプレランチ
Twitterで「こんなツール作ったら使う？」と質問し、100いいねが付いたら開発開始するルールを設けた事例。作る前に市場の反応を計測。

### 失敗: 機能過多で3ヶ月かけた個人開発
「完璧なもの」を目指して3ヶ月開発 → リリース後、誰も使わない機能が7割。ユーザーインタビューなしに作り込んだ典型的な失敗。

---

## アンチパターン

- **「まだリリースできない症候群」**: 恥ずかしくないレベルになったらリリース、ではなく「恥ずかしいくらいがちょうどいい」
- **機能リストの肥大化**: 「ユーザーが求めているはず」で機能を追加し続ける。インタビューで確認した要求のみ実装
- **仮説なきMVP**: 「何となく便利そう」で作り始める。仮説なき実験は検証にならない
- **コードから始める**: 最初にFigmaやLPで検証できるものをコードで実装しようとする
- **競合のコピーをMVPと呼ぶ**: 競合の機能を全部再現しようとするのはMVPではなくクローン開発

## 明日から試せるアクション

1. **今作っているプロダクトの「削除リスト」を作る**: 全機能をリストアップし、「なくても仮説検証できるもの」を削除欄に移す
2. **仮説を1文で書く**: 「誰が・何に悩んでいて・何があれば・どう行動するか」を紙に書き出し、その仮説を検証するだけに絞る
3. **コードなしで検証できないか考える**: 今開発中の機能を「LPだけ・スプレッドシートだけ・手動オペレーションだけ」で代替できないか検討する
