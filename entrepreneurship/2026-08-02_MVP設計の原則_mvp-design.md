# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPは「最小限の機能を持つプロダクト」ではなく、「最小のコストで最大の学びを得る実験装置」だ。個人開発者が陥りがちな「作りすぎ」は、誰も使わない機能に時間を溶かす最大の罠。リソースが限られているからこそ、何を**作らないか**を決める力が生存率を左右する。

---

## 核となる考え方

- **MVPの目的は販売ではなく検証**。最初のバージョンで収益を上げようとするな
- **仮説を1つに絞れ**。「ユーザーはこの課題を持っている」という1点だけを確かめる
- **機能ではなく、価値の最小単位を作る**。スプレッドシートや手動オペレーションで代替できるなら、コードを書く前に検証せよ
- **恥ずかしいと感じるくらいがちょうどいい**（Reid Hoffman）。磨きすぎは学びの遅延
- **フィードバックループを短くする**。2週間以内にユーザーの反応を得られない設計は失敗

---

## 実践フレームワーク：MVP設計の5ステップ

### Step 1. 核心仮説を書き出す（30分）
```
課題仮説: [ターゲット]は[状況]で[課題]に困っている
解決仮説: [解決策]によってその課題を解決できる
行動仮説: ユーザーは[具体的行動]をする（登録・課金・シェア）
```

### Step 2. 検証手法を選ぶ（コードを書く前に）

| 仮説の種類 | 最小検証手法 | コスト |
|-----------|------------|--------|
| 課題の存在 | ユーザーインタビュー | ゼロ |
| 解決策の有効性 | モックアップ／Figma | ゼロ |
| 支払い意欲 | ランディングページ＋事前決済 | 数時間 |
| 継続利用 | スプレッドシート＋手動運用 | 数日 |
| スケール性 | 実際のコード | 数週間 |

### Step 3. 「削ぎ落とし基準」で機能リストを切る

機能リストを作ったあと、各機能に問う：
- **コア仮説の検証に必要か？** → NoならMVPから除外
- **ユーザーが「ないと使えない」と言うか？** → 推測するな、聞け
- **1週間で作れるか？** → 無理なら分割するか捨てる

### Step 4. スモークテストで需要を確認

コードを書く前にLP（ランディングページ）を公開し、メール登録や事前決済を集める。  
目安：100人にリーチして5人以上が行動を取れば続ける。

### Step 5. 1サイクル＝2週間の検証ループ

```
仮説設定 → 最小実装（3日） → ユーザーに見せる → 計測 → 振り返り → 次の仮説
```

## 事例

### 成功例：Dropbox（コード前の動画MVP）
プロダクトを作る前に機能デモ動画を公開し、一夜でウェイトリスト7万5千件を獲得。開発コストゼロで需要を証明した。

### 個人開発の成功例
- Twitterで「◯◯ツールを作ろうと思うが使いたい人は？」と投稿し、10RT以上来たら着手するという手法は定番のスモークテスト
- Notionテンプレートを先に販売し、需要確認後にSaaSとして作り直したソロファウンダーは多数

### 失敗例（よくあるパターン）
- 6ヶ月かけてフル機能を作り、リリース後にユーザーがゼロ
- ランディングページのCV率が0.5%なのに「UXが悪い」と思い込み、改善を繰り返す（課題自体が存在しない可能性を無視）

---

## アンチパターン

- **「あったらいいな機能」を全部入れる**：作るほど検証が遅れ、捨てにくくなる
- **身内だけに見せる**：知人は優しいフィードバックしかくれない。見知らぬ人に見せろ
- **完璧になるまで公開しない**：公開しないと何も学べない。恥ずかしさは慣れる
- **定性フィードバックだけで判断する**：「いいね」と言っても使わない人は多い。行動データを取れ
- **1つのMVPで複数仮説を検証しようとする**：焦点が分散し、何も分からないまま終わる
