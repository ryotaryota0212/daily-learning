# MVP設計の原則：何を作らないか、最小限の検証方法

## 概要

MVPとは「最小限の機能で仮説を検証するプロダクト」。多くの個人開発者が陥る失敗は「完璧なものを長期間かけて作り、誰にも使われなかった」パターン。MVP思考の本質は「削ること」にある。ユーザーが本当に必要としているものを最短で確かめ、フィードバックループを高速に回すことで、無駄な開発コストと機会損失を防ぐ。

---

## 核となる考え方

- **MVPはプロダクトではなく実験**：検証したい仮説があって、そのための最小手段がMVP
- **「最小限」は機能数ではなくリスクの最小化**：コアの価値仮説を検証できる最も小さな形
- **スピードが正義**：2週間以内に何らかのフィードバックが得られない設計は遅すぎる
- **作らないことがデフォルト**：機能追加の理由を「ユーザーが本当に困っているから」以外で正当化しない
- **MVPで完成度を求めない**：バグがあっても、UIが粗くても、ユーザーが価値を感じるかどうかが唯一の判断軸

---

## 実践フレームワーク・ステップ

### Step1：仮説の特定（30分）

検証すべき仮説を「問い」の形で書き出す。

```
顧客仮説：[ターゲット] は [問題] を抱えている
価値仮説：[解決策] によって [価値] を得られる
成長仮説：[チャネル] でユーザーを獲得できる
```

この中で「最もリスクが高い仮説」＝最初に検証すべき仮説。

### Step2：MVPの形を選ぶ

| MVP形式 | 向いているケース | コスト |
|---|---|---|
| **Smoke Test**（LPだけ作る） | 需要確認 | 1日 |
| **コンシェルジュMVP**（手作業でサービス提供） | プロセス検証 | 数時間 |
| **ウィザードオズMVP**（裏側は手動、表は自動に見せる） | UX検証 | 1〜3日 |
| **動くプロトタイプ**（コア機能のみ実装） | 技術検証 | 1〜2週 |

個人開発ならまずSmokeTestかコンシェルジュMVPから始める。コードを書く前に需要を確認する。

### Step3：スコープ削減の実践

「あると良い機能」リストを全部書いたあと、次の問いで削ぎ落とす：

1. この機能がなくてもユーザーは価値を感じるか？→ YES なら削る
2. この機能は仮説検証に必要か？→ NO なら削る
3. 3人のユーザーが明示的に要求したか？→ NO なら削る

### Step4：検証指標を先に決める

MVPをリリースする前に「何が起きたら仮説が正しいか」を数値で決める。

```
例：「10人に見せて3人が使い続けたら価値仮説は正しい」
例：「LPのCTRが5%超えたら需要あり」
```

## 成功・失敗の事例

### 成功例（ソロファウンダー）

- **Pieter Levelsのノマドリスト**：最初はスプレッドシートをTwitterで公開しただけ。反応を見てからサイトを作った。コードより先にユーザーの反応を確認した典型例。
- **IndieHackers創業者**：インタビュー記事を先に書いてトラフィックを確認してからプラットフォーム化。

### 失敗例（よくある個人開発）

- 3ヶ月かけてフル機能のSaaSを作り、リリース日に誰も来なかった
- ユーザーインタビューなしで「自分が使いたいもの」を作り続けた
- 「あとで使う機能」を先に実装してスコープが爆発した

---

## アンチパターン

- **「もう少し磨いてからリリース」** → 完璧主義がフィードバックループを止める
- **「MVPだから雑でいい」と開き直る** → ユーザーが価値を感じる部分は丁寧に作る（その他は粗くていい）
- **仮説なしにMVPを作る** → 何を検証しているか不明なまま作ると、結果をどう解釈すべきかわからない
- **ユーザー数が少ないからデータが信頼できないと言い訳する** → 5人でも定性的なパターンは見える
- **「MVPが終わったら次はβ版」と段階を無限に設ける** → リリース先延ばしの言い訳になる
