# MVP設計の原則――何を作らないか、最小限の検証方法

## 概要

MVPとは「Minimum Viable Product（最小限の実行可能なプロダクト）」の略。起業家にとって最大のリスクは「誰にも求められないものを長時間かけて作ること」。MVP思考は、検証前に大きく投資することを避け、最速で学習サイクルを回すための設計哲学。個人開発者にとっては特に重要で、1人の時間・お金・精神力は有限だからこそ「作らない判断」が事業の命運を分ける。

---

## 核となる考え方

- **MVPの目的は販売ではなく学習**  
  「売れるか」を試すのではなく「仮説が正しいか」を確かめるもの
- **価値仮説と成長仮説を分けて考える**  
  - 価値仮説：このプロダクトはユーザーに価値をもたらすか？
  - 成長仮説：ユーザーはどうやって増えていくか？
- **"Viable" を誤解しない**  
  「動けばいい」ではなく「コアな価値を届けられる最低限」という意味
- **機能ではなく体験を最小化する**  
  機能を削るのではなく「コアな体験を最もシンプルに届ける方法」を探す
- **フィーチャーは仮説に過ぎない**  
  実装前に「この機能が○○を解決すると思う」と仮説を明文化しておく

---

## 実践フレームワーク・ステップ

### Step 1: 検証したい仮説を1つに絞る

```
「[ターゲットユーザー] は [課題] があるために [行動] しているが、
[我々のソリューション] によって [結果] が得られる」
```

例：「副業エンジニアは案件探しに時間がかかりすぎているために
機会損失が起きているが、スキルマッチングBotによって週3時間を削減できる」

### Step 2: 「作らずに検証できるか？」を先に問う

| 検証方法 | コスト | 向いている仮説 |
|----------|--------|---------------|
| ランディングページ＋メール登録 | 極小 | 需要があるか |
| Notion/スプレッドシートで手動運用 | 小 | フローが機能するか |
| コンシェルジュMVP（手動で全部やる） | 小〜中 | 価値が伝わるか |
| プロトタイプ（Figma/ノーコード） | 中 | UIが使われるか |
| 実装したMVP | 大 | 実際に継続利用されるか |

**鉄則：上から順番に試す。いきなり実装しない。**

### Step 3: 何を「作らない」か決める

MVP設計チェックリスト：
- [ ] この機能がなくてもコアな価値は届くか？ → なければ削除
- [ ] 管理画面は後で作れるか？ → 最初は手動運用でOK
- [ ] ユーザー登録・認証は本当に必要か？ → 最初はメールだけでもOK
- [ ] 決済は最初から必要か？ → 最初は振込・PayPayでもOK
- [ ] 複数のユーザーセグメントに対応するか？ → 1セグメントに絞る

### Step 4: 成功の定義を先に決める

実験前に「この数字が出れば仮説が正しい」と決めておく

例：
- ランディングページの登録率 > 10%
- インタビューした10人中6人が「使いたい」と言う
- 初月に3人が実際に対価を払う

## 成功・失敗の事例

### 成功例：Dropbox（コンシェルジュ→動画MVP）
- 最初はサービスを作らず3分のデモ動画だけ公開
- 一夜で75,000件のメール登録 → 需要を確認してから開発
- **学び**：動くものを作る前に「欲しいと思うか」を確認できた

### 成功例：Zapier（手動マッチング）
- 最初はAPIを自動でつなぐのではなく、創業者が手動でzapを作っていた
- ユーザーのユースケースを深く理解してから自動化を実装
- **学び**：手動MVPで学習 → 自動化の優先順位が明確になった

### 個人開発での失敗例（典型パターン）
- 6ヶ月かけてフル機能のSaaSを作る → リリース後ユーザー0人
- 「使いやすいUI」に時間をかけすぎる → コア機能の検証が遅れる
- 複数機能を同時に検証しようとする → 何が機能したか分からない

---

## アンチパターン

- **「もう少し作ってからリリースしよう」の無限ループ**  
  → リリース日を先に決める。不完全でも出す。
- **MVPを"低品質なもの"と誤解する**  
  → コアな価値の体験は最高品質に。それ以外を削る。
- **検証の成功基準を決めずに始める**  
  → 後付けで「まあまあいいじゃないか」という結論に逃げる温床になる
- **ターゲットを広げすぎる**  
  → 「誰でも使える」= 「誰にも刺さらない」。最初の10人を決める。
- **機能追加で課題解決しようとする**  
  → リテンションが低い原因は機能不足ではなく、そもそも課題が違う可能性大

## 明日から試せるアクション（3つ）

1. **今作ろうとしているプロダクトの「削れる機能リスト」を作る**  
   全機能をリストアップ → 「コアな価値体験に不要なもの」を赤で塗る

2. **ランディングページを1日で作って公開する**  
   Notion/Framer/Carrdで仮のLPを作り、SNSで10人に見せてフィードバックを得る

3. **検証の成功基準を書き出す**  
   「○○が○○人いれば次のステップに進む」という数字を今日中に決める
