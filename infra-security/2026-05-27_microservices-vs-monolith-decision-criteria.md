# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」は最も誤った判断が多い設計決断の一つ。
マイクロサービスは**分散システムの複雑さ**を引き受ける代わりに独立スケール・独立デプロイを得る。
FastAPI + Cloud Run スタックでは「1サービス = 1 Cloud Run」が自然だが、サービス分割が早すぎると開発速度が激減する。
**まずモノリス、必要になったら切り出す**が AI 時代のデフォルト戦略。

---

## 仕組みの要点

### モノリス
- 1つのプロセスで全機能を提供。DB も共有。
- デプロイ・テスト・デバッグがシンプル
- チームが小さい・ドメイン境界が不明確な段階で最適
- Cloud Run では1つのコンテナにまとめて deploy

### マイクロサービス
- 機能ごとに独立したプロセス・DB・デプロイパイプライン
- サービス間通信（HTTP/gRPC/Pub/Sub）が必要
- チームが独立して動ける規模（通常 50人以上のエンジニア組織）が前提
- 分散トレーシング・サービスメッシュなどの運用コストが発生

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービス（分割基準が不明確） | モノリスから始めてドメイン境界を学ぶ |
| 共有DBをマイクロサービスで参照 | サービスごとに DB を所有（DB per service） |
| 同期HTTP呼び出しの連鎖（カスケード障害） | 非同期（Pub/Sub）で疎結合 |
| 「技術的関心」で分割（認証サービス、ログサービス） | 「ビジネスドメイン」で分割（注文、決済、ユーザー） |
| 早期の全面移行 | Strangler Fig パターンで段階的に切り出す |

## 設計例：Strangler Fig パターン

モノリスの前にルーターを置き、新機能から順にマイクロサービスへ切り出す。

```python
# Cloud Run: api-gateway (FastAPI ルーター)
from fastapi import FastAPI, Request
import httpx

app = FastAPI()
MONOLITH_URL = "https://monolith-xxxx.run.app"
PAYMENT_SVC   = "https://payment-xxxx.run.app"

@app.api_route("/{path:path}", methods=["GET","POST","PUT","DELETE"])
async def router(path: str, request: Request):
    # 切り出し済みのエンドポイントだけ新サービスへ
    if path.startswith("payments/"):
        target = PAYMENT_SVC
    else:
        target = MONOLITH_URL  # それ以外はモノリスへ

    async with httpx.AsyncClient() as client:
        resp = await client.request(
            method=request.method,
            url=f"{target}/{path}",
            headers=dict(request.headers),
            content=await request.body(),
        )
    return resp.json()
```

## 判断フレームワーク（切り出すタイミング）

切り出す**理由が明確**な場合のみ分割する：

1. **スケール要件の差異** — 特定機能だけ100倍のトラフィックを受ける
2. **デプロイ頻度の差異** — あるチームが1日20回、別チームが週1回
3. **技術スタックの違い** — ML推論だけ GPU インスタンスが必要
4. **組織の分離** — チームが完全に独立して所有できるドメインがある

**切り出さない方がよいシグナル：**
- チームが5人以下
- ドメイン境界がまだ変化している
- 分散トレーシング・サービスメッシュを運用できるインフラ力がない

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ設定が多い） |
| スケーラビリティ | 全体をスケール | 機能単位でスケール |
| 障害影響範囲 | 全機能に波及 | サービス単位で局所化（設計次第） |
| デバッグ難易度 | 低い | 高い（分散トレース必須） |
| チーム独立性 | 低い（競合が起きやすい） | 高い（DB・デプロイ独立） |
| 運用コスト | 低い | 高い（監視・ネットワーク・認証） |

## チェックリスト

- [ ] チーム規模と組織構造で「Conway の法則」を確認した（組織構造 = システム構造になる）
- [ ] 切り出す機能のドメイン境界が安定していると確認した
- [ ] サービス間認証（Cloud Run の IAM + ID トークン）を設計した
- [ ] 分散トレーシング（Cloud Trace / OpenTelemetry）の導入計画がある
- [ ] モノリスに戻す選択肢を排除していない（過剰分割は技術的負債）
