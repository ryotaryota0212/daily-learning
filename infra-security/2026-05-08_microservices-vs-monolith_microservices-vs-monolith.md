# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすれば良い設計」という誤解は根深い。  
実際には**チーム規模・デプロイ頻度・ドメイン複雑さ**が揃っていないとマイクロサービスはコストだけ増える。  
モノリスを正しく設計し、分割が必要になってから分離する「モジュラーモノリス→マイクロサービス」が現実解。  
AI時代においては「どちらが流行か」ではなく「**今のチームとシステムで何が壊れにくいか**」を説明できることが重要。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ単位。変更→テスト→デプロイが1サイクル
- サービス間通信がプロセス内関数呼び出し（レイテンシゼロ、トランザクション容易）
- デバッグ・ログ追跡が単純
- **問題点**: 大きくなるとデプロイリスクが高まる、チーム間の変更衝突が増える

### マイクロサービスの特性
- サービス単位で独立デプロイ、スケール、技術選択が可能
- チームが自律的に動ける（Conway's Lawを活用）
- **問題点**: ネットワーク通信・分散トレーシング・データ整合性が複雑になる

### モジュラーモノリス（推奨中間形態）
- 単一デプロイだが**ドメイン境界を明確なモジュールで分離**
- DB共有だが、モジュール間はAPIインターフェース越しに通信
- 将来の分割をコスト最小で準備できる

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで始める | モノリスで始め、ボトルネックが判明してから分割 |
| DBをサービス間で共有 | サービスごとにDBを持つ（または論理的に分離） |
| 境界が不明確なまま分割 | ドメイン境界（DDD bounded context）で分割する |
| 同期HTTP通信で全サービスを接続 | 書き込み系は非同期メッセージング、読み取り系はキャッシュ |
| デプロイパイプラインを共通化 | サービスごとに独立したCI/CDを持つ |
| 1人チームでマイクロサービス | サービスあたり最低2〜3人のチームが必要 |

## 判断フレームワーク

```
Q1: チームは何人か？
  < 10人 → モノリスで十分
  10〜50人 → モジュラーモノリスを検討
  50人以上 → マイクロサービスの価値が出始める

Q2: デプロイ頻度は？
  週1以下 → モノリスで管理可能
  1日複数回 × 複数チーム → デプロイ衝突が問題 → 分割の動機になる

Q3: スケール要件に差があるか？
  例: 「画像処理だけCPU負荷が100倍高い」→ そのサービスだけ分離する価値あり
  全体が同じ負荷 → モノリスで水平スケールすればよい
```

## 設計例: FastAPI + Cloud Run でのモジュラーモノリス

```
app/
  auth/          # Firebaseトークン検証
    router.py
    service.py
  orders/        # 注文ドメイン
    router.py
    service.py
    repository.py  # DBアクセスはドメイン内に閉じる
  notifications/ # 通知ドメイン（将来分割候補）
    router.py
    service.py
  shared/
    db.py        # DB接続（共有OK）
    events.py    # ドメインイベント定義（将来のメッセージキュー化への準備）
```

モジュール間はイベントバス（インプロセス）で疎結合にし、後でCloud Pub/Subに差し替えられる設計にする。

## 移行戦略: ストラングラーフィグパターン

```
[クライアント]
      ↓
  [APIゲートウェイ / Cloudflare]
      ↓                ↓
[新サービス(Cloud Run)]  [旧モノリス]
                         （残りのエンドポイント）
```

1. 分割したいドメインの新サービスを独立デプロイ
2. ゲートウェイでルーティングを切り替え（旧→新）
3. 旧モノリスから該当コードを削除
4. DBマイグレーション（共有DB → 専用DB）は最後・最も難しい

## トレードオフ比較

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備が必要） |
| デプロイリスク | 大（全体影響） | 小（サービス単位） |
| 障害の局所化 | 困難 | 可能（サーキットブレーカー等） |
| データ整合性 | 容易（トランザクション） | 困難（結果整合性） |
| 運用コスト | 低 | 高（サービスディスカバリ、分散トレーシング等） |
| チーム自律性 | 低 | 高 |
| Cloud Runでのコスト | 最小 | サービス数に比例して増加 |

## チェックリスト

- [ ] チームが10人未満ならモノリスかモジュラーモノリスを選ぶ
- [ ] ドメイン境界（bounded context）を定義してからモジュール分割する
- [ ] モジュール間通信をインターフェース（イベント）経由にし、将来の分割を準備する
- [ ] マイクロサービス化の動機が「デプロイ衝突」「スケール差」「チーム自律性」のどれかを確認する
- [ ] 分割前にCI/CDパイプラインとモニタリング基盤が整っていることを確認する
