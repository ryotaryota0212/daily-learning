# マイクロサービス vs モノリス：判断基準と移行戦略

## 概要
「マイクロサービスにすべき？」は技術選択の中でも失敗しやすい問いの一つ。マイクロサービスは運用コストが高く、小規模チームでは逆効果になりやすい。  
「いつ、なぜ分割するか」を設計段階で明確にすることが、シンプルで壊れにくいシステムへの近道。  
まずモノリスで検証し、ドメイン境界が見えてから分割するのが王道。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ単位。変更が速く、デバッグが容易
- DBトランザクションが単純（同一DB内でACID保証）
- チームが小さい段階では開発速度が圧倒的に速い
- スケールの限界：全体を一緒にスケールするしかない

### マイクロサービスの特性
- サービスごとに独立デプロイ・スケール可能
- チームをドメインで分割できる（Conway's Law）
- サービス間通信のオーバーヘッドと複雑さが増す
- 分散トレーシング・サービスメッシュなど運用コストが大きい

---

## 判断基準

| 条件 | モノリス推奨 | マイクロサービス推奨 |
|------|------------|------------------|
| チーム規模 | ～10人 | 10人以上・複数チーム |
| ドメイン境界 | 不明確 | 明確に定義済み |
| スケール要件 | 均一 | 部分的に集中 |
| デプロイ頻度 | 週次以下 | サービス独立で高頻度 |

---

## アンチパターン vs 正しい設計

### アンチパターン
- 小規模スタートアップが最初からマイクロサービスを採用（"premature distribution"）
- ドメイン境界が不明確なまま分割 → 密結合なマイクロサービス地獄
- 分散トランザクションを安易に実装 → 整合性保証が悪夢に
- DBを無理に分割して結合クエリが不可能に

### 正しい設計
- まずModular Monolith（モノリス内でモジュール境界を明確に定義）
- 境界が安定してから Strangler Fig Pattern で段階的に切り出す
- Cloud Run の場合：サービスごとに独立コンテナ、IAMで認証

---

## 移行例：Strangler Fig Pattern

```
[既存モノリス]
  ↓ 新エンドポイントを順次切り出す
[Cloud Run / API Gateway]
 ├── /users    → UserService   (新 Cloud Run)
 ├── /payments → PaymentService(新 Cloud Run)
 └── /legacy/* → モノリス（徐々に縮小して最終的に廃止）
```

**FastAPI + Cloud Run での切り出しイメージ:**
```python
# UserService (新マイクロサービス) main.py
from fastapi import FastAPI, Depends
from auth import verify_firebase_token  # Firebase Auth検証

app = FastAPI()

@app.get("/users/{uid}")
async def get_user(uid: str, user=Depends(verify_firebase_token)):
    # Neon DBに直接接続（RLS適用済み）
    return await user_repo.find(uid)
```

サービス間の呼び出しは **Cloud Run サービスアカウント + IDトークン** で認証。

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|------|---------|---------------|
| 開発速度（初期） | 速い | 遅い |
| スケーラビリティ | 限定的 | 高い |
| 運用コスト | 低い | 高い |
| 障害影響範囲 | 全体 | サービス単位 |
| デプロイリスク | 大きい（全体影響） | 小さい（部分影響） |
| 整合性保証 | 容易（同一DB） | 難しい（分散トランザクション） |

## チェックリスト
- [ ] チーム10人超・複数ドメインが明確になってから分割を検討した
- [ ] モノリス内でモジュール境界を先に設計した（Modular Monolith）
- [ ] Strangler Fig Patternで段階的に移行し、一気にリプレイスしない
- [ ] サービス間通信の失敗時の挙動（タイムアウト・リトライ・サーキットブレーカー）を設計した
- [ ] 分散トランザクションが必要な箇所を洗い出し、Sagaパターンを検討した
