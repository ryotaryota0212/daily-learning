# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき？」はシステム設計で最もよく問われる問いの一つ。
しかし多くの現場でマイクロサービスへの移行が失敗し、複雑性だけが残る。
重要なのは「技術トレンド」で選ぶのではなく、**チーム規模・デプロイ頻度・組織構造**を基に判断すること。
AI時代においても「どの分割が一番壊れにくいか」を設計する力が問われる。

---

## 仕組みの要点

### モノリスの特徴
- 全機能が単一デプロイ単位。シンプルで開発速度が高い
- トランザクション管理・データ整合性が容易
- デバッグ・ログ・テストが一体で完結
- チームが小さいうちは生産性が高い

### マイクロサービスの特徴
- サービスごとに独立デプロイ・スケール可能
- 障害が局所化される（うまく設計すれば）
- 技術スタックの自由度が高い
- チームが大きくなり、独立した開発が必要な場合に真価を発揮

### コンウェイの法則（最重要）
> システムのアーキテクチャは、それを作る組織の通信構造を反映する

- チームが1つ → モノリスが自然
- チームが機能別に分かれている → サービス分割が有効
- 組織構造と合っていないアーキテクチャは必ず崩壊する

---

## アンチパターン vs 正しい設計

### アンチパターン
| アンチパターン | 問題 |
|---|---|
| 小規模チームがマイクロサービスを選ぶ | 運用コストがコードより大きくなる |
| DBを共有したままサービスを分割 | 結合が残り分割の意味がない |
| 「機能ごと」ではなく「技術層ごと」に分割 | Controller/Service/DAOで分けるのはモノリス以下 |
| 移行を一気にやろうとする | リスクが集中し失敗する |

### 正しい設計判断フロー

```
チーム規模 < 10人?
  → モノリスから始める（99%正解）

デプロイ頻度・チーム数が増えてきた?
  → Strangler Fig パターンで段階移行

サービスを分割するなら:
  → ドメイン境界（Bounded Context）で分ける
  → DBは必ず分ける（共有DBは禁止）
  → 同期RPC < 非同期イベントを優先
```

## 移行戦略：Strangler Fig パターン

既存モノリスを壊さず、外側から少しずつ置き換える戦略。

```python
# Cloud Run + FastAPI での段階移行例
# Step1: 新機能はマイクロサービスで実装
# Step2: Cloudflare Workers / API GW でルーティングを切り替え

# ルーティング例（Cloudflare Workers）
# /api/v2/notifications/* → 新サービス（Cloud Run）
# /api/*                  → 既存モノリス（Cloud Run）

# Step3: 旧コードを削除
# → モノリスが「細く」なっていく
```

**ポイント：**
- 新機能は必ず新サービスに書く
- 古い機能は触らない（移行コストを集中させない）
- APIゲートウェイ（Cloudflare・Cloud Run Ingress）でルーティングを制御

## サービス分割の正しい単位（Bounded Context）

```
# NG: 技術層で分割
user-controller-service
user-service-layer
user-repository-service

# OK: ドメイン境界で分割
auth-service       # 認証・認可
notification-service  # 通知
billing-service    # 課金
content-service    # コンテンツ管理
```

分割の基準：
- **変更頻度が異なる**（課金は慎重、通知は頻繁）
- **スケール要件が異なる**（検索は高負荷、管理画面は軽量）
- **チームの所有権が明確**

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い |
| 運用コスト | 低い | 高い（監視・デプロイ・通信管理） |
| スケーラビリティ | 全体スケール | 部分スケール可能 |
| 障害の局所化 | 難しい | 設計次第で可能 |
| データ整合性 | トランザクションで容易 | 分散トランザクションが必要（複雑） |
| チーム独立性 | 低い（コンフリクト多発） | 高い |

**FastAPI + Cloud Run スタックでの現実解：**
- 初期は単一リポジトリのモノリスで速く作る
- Cloud Runの「1サービス1コンテナ」を活かし、後から分割しやすい設計にする
- DBはNeonで論理スキーマを分けておく（物理分割の準備）

- [ ] 移行はStrangler Figパターンで段階的に行う（一括移行はしない）
- [ ] 分割単位はドメイン境界（Bounded Context）に基づいているか
