# インシデント対応とポストモーテムの文化

## 概要

障害は必ず起きる。問題は「障害が起きるか否か」ではなく「起きたときに何分で気づき、何分で復旧し、再発を防げるか」だ。
インシデント対応の文化が整っていないチームは、同じ障害を繰り返し、毎回場当たり的に対処する。
ポストモーテム（事後検証）は「犯人探し」ではなくシステム改善の仕組みとして機能させることが重要。

---

## 仕組みの要点

### インシデント対応フロー

1. **検知** → アラートが鳴る（モニタリング設計が前提）
2. **トリアージ** → 影響範囲と深刻度を30秒で判断
3. **宣言** → Severity（P0〜P3）を決め、インシデントチャンネルを開設
4. **緩和（Mitigate）** → 原因特定より先に影響を止める（ロールバック、機能フラグOFF等）
5. **根本原因調査（RCA）** → 緩和後に落ち着いて掘り下げる
6. **解決宣言** → モニタリング値が正常に戻ったら宣言
7. **ポストモーテム** → 48〜72時間以内に実施

### Severity定義例

| Level | 影響 | 目標復旧時間（MTTR） |
|-------|------|---------------------|
| P0 | 全ユーザー利用不可 | 30分以内 |
| P1 | 主要機能の一部停止 | 2時間以内 |
| P2 | パフォーマンス劣化 | 翌営業日 |
| P3 | 軽微なバグ | 通常リリース |

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しいアプローチ |
|--------------|----------------|
| 原因を特定してから対処する | まず緩和、原因調査は後 |
| 「誰が悪いか」を追及する | 「なぜシステムがそうなったか」を問う |
| ポストモーテムをやらない/形式的にやる | アクションアイテムに期限とオーナーをつける |
| アラートが多すぎて慣れてしまう | アラートは全件対処できる量に絞る |
| 復旧手順が口頭伝承 | RunbookをWikiに整備し定期更新する |

## ポストモーテムの書き方（テンプレート）

```markdown
## インシデント概要
- 発生日時 / 検知日時 / 解決日時
- 影響: XX人のユーザーがYY機能を利用できなかった

## タイムライン
- 14:32 アラート発報
- 14:35 オンコール担当が確認開始
- 14:50 Cloud Runのリビジョンをロールバック
- 15:00 正常復帰確認

## 根本原因
- 環境変数の設定漏れによりDB接続が失敗
- ステージング環境では再現しなかった理由: 接続数が少ないため顕在化しなかった

## アクションアイテム
| # | 内容 | オーナー | 期限 |
|---|------|---------|------|
| 1 | デプロイチェックリストにenv var検証を追加 | @田中 | 8/14 |
| 2 | DB接続失敗時のアラートをP1に格上げ | @佐藤 | 8/21 |
```

## Cloud Run / Firebase Auth スタックでの実践

```python
# FastAPI: ヘルスチェックエンドポイント（インシデント検知の基礎）
@app.get("/healthz")
async def health_check():
    try:
        await db.execute("SELECT 1")          # DB疎通確認
        return {"status": "ok", "db": "ok"}
    except Exception as e:
        # P1アラートをここでトリガーする
        logger.error(f"DB health check failed: {e}")
        raise HTTPException(status_code=503, detail="DB unavailable")
```

- Cloud Run: `/healthz` をLiveness/Readiness probeに設定
- Firebase Auth障害時: 認証をスキップする緊急フラグを用意しておく
- Neon DB: 接続プールサイズの上限超過がよくある障害原因→メトリクス監視必須

## トレードオフ

| 観点 | 詳細 |
|------|------|
| ポストモーテム工数 vs 再発防止効果 | P0/P1は必須、P2は任意とすると工数が現実的 |
| アラート量 vs 検知漏れ | アラートが多すぎると疲弊してP0を見逃す。精度優先で設計 |
| 自動ロールバック vs 手動判断 | 自動は速いが誤発動リスクあり。P0のみ自動化が現実的 |
| 詳細なRunbook vs 陳腐化リスク | 手順書は定期レビューをセットで運用しないと腐る |
