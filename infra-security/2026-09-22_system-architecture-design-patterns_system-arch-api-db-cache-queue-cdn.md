# システム全体構成の設計パターン（API・DB・キャッシュ・キュー・CDN）

## 概要

AI時代に最も問われるのは「コードを書く力」ではなく「どの構成要素をどう組み合わせるか」の判断力。  
システムを構成する主要コンポーネント（API、DB、キャッシュ、キュー、CDN）それぞれの責務を理解し、  
シンプルかつ壊れにくい構成を設計できることがエンジニアの価値を決める。  
構成を間違えると、スケール時に全部作り直しになる。最初の設計判断がコストを左右する。

---

## 仕組みの要点

### 主要コンポーネントと責務

| コンポーネント | 責務 | 代表技術（本スタック） |
|---|---|---|
| API層 | リクエスト受付・認証・バリデーション | FastAPI on Cloud Run |
| DB（永続化） | 一貫性が必要なデータの永続化 | Neon (PostgreSQL) |
| キャッシュ | 読み取り高速化・DBへの負荷軽減 | Redis / Cloud Memorystore |
| キュー | 非同期処理・サービス間デカップリング | Cloud Tasks / Pub/Sub |
| CDN | 静的アセット配信・エッジキャッシュ | Cloudflare |

### データフローの基本パターン

```
[クライアント]
    │
    ▼
[CDN / Cloudflare]  ← 静的ファイル・エッジキャッシュはここで終了
    │ 動的リクエスト
    ▼
[API (Cloud Run)]  ← 認証(Firebase Auth)・バリデーション・ビジネスロジック
    │        │
    ▼        ▼
  [DB]    [キャッシュ]  ← 読み取り: キャッシュ優先、ミス時はDB
  (Neon)  (Redis)
    │
    ▼
  [キュー]  ← 重い処理・外部通知は非同期化（メール送信、レポート生成等）
```

### 各層の設計判断ポイント

**API層**
- ステートレスに保つ → Cloud Run の水平スケールが機能する
- セッション状態はDBかRedisに持つ、インスタンスに持たない
- 重い処理は即レスポンスせずキューに積む（タイムアウト回避）

**DB層**
- 書き込みはすべてDBへ（キャッシュに書かない）
- 読み取り頻度の高いデータ・計算コストが高いデータをキャッシュ対象に
- RLSで行レベルのアクセス制御（マルチテナント対応）

**キャッシュ層**
- Cache-Asideパターンが基本（読み時にミス→DBから取得→キャッシュ保存）
- TTLは短め（整合性優先なら60-300秒）
- キャッシュキーの設計ミスが最大の落とし穴

**キュー層**
- 処理失敗時のリトライ・Dead Letter Queueを必ず設計する
- べき等性を保証（同じメッセージが2回来ても結果が同じ）

## アンチパターン vs 正しい設計

| アンチパターン | 問題 | 正しい設計 |
|---|---|---|
| APIインスタンスにセッション保存 | スケールアウト時に不整合 | RedisやDBに外出し |
| 全リクエストをDBに直接投げる | DB過負荷・スロークエリ連鎖 | キャッシュ層で頻出データをバッファ |
| 重い処理を同期APIで実行 | タイムアウト・UX悪化 | キューに積んで非同期化 |
| CDNなしで静的ファイルをAPIから配信 | 無駄なスケーリングコスト | CloudflareでCDN配信 |
| キャッシュに書き込んでDBに後で同期 | データ欠損リスク | 書き込みは常にDB優先 |

## コード例：Cache-Aside パターン（FastAPI + Redis）

```python
import json
from redis.asyncio import Redis
from app.db import get_user_from_db

redis: Redis = Redis.from_url("redis://localhost")

async def get_user(user_id: str) -> dict:
    cache_key = f"user:{user_id}"
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)

    user = await get_user_from_db(user_id)
    await redis.setex(cache_key, 300, json.dumps(user))  # TTL: 5分
    return user
```

## トレードオフ

| 観点 | シンプル構成 | フル構成（キャッシュ+キュー+CDN） |
|---|---|---|
| 開発速度 | 速い | 遅い（各層の設計コスト） |
| スケーラビリティ | DBがボトルネックになりやすい | 高い |
| 障害点 | 少ない | Redisやキューの障害も考慮が必要 |
| 運用コスト | 低い | 高い |

**判断基準:** DAU 1万以下 → シンプル構成から始める。ボトルネックが見えてから追加するのが正解。最初から全部入れるのは早期最適化。

## チェックリスト

- [ ] APIインスタンスはステートレスか（セッションをインスタンスに持っていないか）
- [ ] 書き込みはDB優先、キャッシュに直接書いていないか
- [ ] 重い処理（メール・PDF生成等）はキューで非同期化されているか
- [ ] キャッシュのTTLとキー設計が明確か
- [ ] CDNで静的アセットが配信されており、APIへの無駄なリクエストが減っているか
