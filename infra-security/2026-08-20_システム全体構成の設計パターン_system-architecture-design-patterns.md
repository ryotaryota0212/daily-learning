# システム全体構成の設計パターン（API・DB・キャッシュ・キュー・CDN）

## 概要

AI時代に最も差がつくのは「動くコードを書く力」ではなく「システムをどう構成するか決める力」。
どのコンポーネントをどこに配置し、どう連携させるかの判断が、スケーラビリティ・可用性・運用コストすべてに直結する。
FastAPI + Neon + Cloud Run + Firebase Auth スタックを例に、典型的な設計パターンを整理する。

---

## 仕組みの要点

### 標準的な構成レイヤー

```
クライアント
  → CDN（Cloudflare）        ← 静的アセット配信・DDoS防御
  → APIゲートウェイ / BFF     ← 認証・レート制限・ルーティング
  → Cloud Run（FastAPI）     ← ビジネスロジック
  → Cache（Redis/Memcached） ← 読み取り高速化
  → DB（Neon/PostgreSQL）    ← 永続化
  → Queue（Pub/Sub）        ← 非同期・重い処理の分離
  → Worker（Cloud Run Job）  ← バックグラウンド処理
```

### 各コンポーネントの役割と判断基準

| コンポーネント | 使う判断基準 | 使わない判断基準 |
|---|---|---|
| CDN | 静的ファイル・グローバルユーザー | 全データが動的・リアルタイム |
| キャッシュ | 読み取り多・DBが遅い | 更新頻度高・一貫性が最重要 |
| キュー | 処理が重い・失敗リトライ必要 | レスポンスが即時必要 |
| BFF | モバイル/Web で異なるAPI形状 | クライアントが1種類 |

---

## アンチパターン vs 正しい設計

### ❌ アンチパターン

- **全部APIに詰め込む**: 認証チェック・DBアクセス・メール送信を1エンドポイントで処理 → タイムアウト・再試行困難
- **DBに直接アクセスさせる**: クライアントがDBに直接つなぐ → RLS頼みになりセキュリティが脆弱
- **キャッシュを後付け**: ボトルネックが出てから追加 → キャッシュキー設計が散らかる
- **同期でメール/外部API呼び出し**: レスポンスタイムが外部サービスに依存

### ✅ 正しい設計

- **責務の分離**: 認証（Firebase Auth）・ビジネスロジック（FastAPI）・永続化（Neon）を明確に分ける
- **非同期で切り離す**: 重い処理（メール・PDF生成・AI推論）はキューに入れてWorkerへ
- **キャッシュはデータ特性で設計**: 参照頻度・TTL・更新頻度を先に定義する

## コード/設計例（FastAPI + Pub/Sub）

```python
# ❌ 同期で全部やる（アンチパターン）
@app.post("/orders")
async def create_order(order: OrderIn, user=Depends(get_current_user)):
    db_order = await db.insert(order)
    await send_email(user.email, db_order)   # 外部API呼び出しがブロック
    await generate_invoice(db_order)         # 重い処理がブロック
    return db_order

# ✅ キューで非同期分離（正しい設計）
@app.post("/orders")
async def create_order(order: OrderIn, user=Depends(get_current_user)):
    db_order = await db.insert(order)
    await pubsub.publish("order-created", {"order_id": db_order.id})
    return db_order   # すぐ返す

# Worker側（Cloud Run Job）でメール・請求書生成を処理
```

## トレードオフ

| 選択 | メリット | デメリット |
|---|---|---|
| キャッシュ追加 | レスポンス高速・DBリソース削減 | 一貫性管理が必要・キャッシュ無効化が複雑 |
| キュー追加 | 非同期・再試行・ピーク平滑化 | 即時確認できない・べき等性設計が必要 |
| BFF追加 | クライアント最適・API隠蔽 | 管理コスト増・レイヤー追加 |
| モノリスのまま | シンプル・デバッグしやすい | スケールしにくい・障害が全体に波及 |

**原則**: シンプルに始めて、実際のボトルネックが見えてから複雑化する。最初からキューやBFFを入れない。
