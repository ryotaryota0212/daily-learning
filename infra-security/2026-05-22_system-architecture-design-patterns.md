# システム全体構成の設計パターン（API・DB・キャッシュ・キュー・CDN）

## 概要

「とりあえず動くAPIを作る」だけでは設計とは呼べない。  
スケール・可用性・コスト・運用性を考慮した上で「なぜこの構成か」を説明できることが、AI時代に求められる設計力の核心。  
本記事では、FastAPI + Neon + Cloud Run 構成を軸に、各レイヤーの役割と選択基準を整理する。

---

## 仕組みの要点

### 典型的なWebシステムのレイヤー構成

```
[ユーザー]
   ↓
[CDN / Cloudflare]  ← 静的ファイル配信、DDoS防御、WAF
   ↓
[APIゲートウェイ or ロードバランサー]  ← レート制限、ルーティング
   ↓
[アプリサーバー (Cloud Run / FastAPI)]  ← ビジネスロジック
   ↓           ↓
[キャッシュ]  [メッセージキュー]  ← Redis / Pub/Sub
   ↓
[DB (Neon / PostgreSQL)]  ← 永続化
```

### 各コンポーネントの責務

| コンポーネント | 役割 | 使うべき場面 |
|---|---|---|
| CDN | 静的アセット配信、エッジキャッシュ | 画像・JS・CSS配信、グローバルユーザー |
| APIゲートウェイ | 認証集約、レート制限、ルーティング | マイクロサービス間、外部公開API |
| アプリサーバー | ビジネスロジック | 常に必要 |
| キャッシュ (Redis) | 読み取り高速化、セッション管理 | 頻繁に読まれる・変化の少ないデータ |
| メッセージキュー | 非同期処理、負荷平滑化 | メール送信、重い処理、外部API連携 |
| DB | 永続化、トランザクション | 正規化・一貫性が必要なデータ |

---

## アンチパターン vs 正しい設計

### アンチパターン

- **全部DBに直アクセス**: キャッシュなし → スパイク時にDB死亡
- **同期的に全部やる**: メール送信・通知をAPIレスポンス内で実行 → レイテンシ増大
- **DBを巨大な1インスタンス**: 垂直スケール限界、SPOFになる
- **CDNなしで静的ファイル配信**: アプリサーバーがボトルネックになる
- **設計なしで機能追加**: 後からキャッシュ/キューを入れようとすると全部書き直し

### 正しい設計原則

- **読み書き分離**: 読み取り多いデータはキャッシュ経由
- **非同期化**: レスポンスに不要な処理はキューに積む
- **静的 / 動的の分離**: CDNで捌けるものはアプリサーバーに来させない
- **障害境界を明確に**: 1コンポーネントの障害が全体に波及しない設計

## 設計例：ユーザー投稿システム（FastAPI + Neon + Cloud Run）

```python
# 投稿作成API：重い処理は非同期化する設計
@app.post("/posts")
async def create_post(post: PostCreate, user=Depends(get_current_user)):
    # 1. DBに保存（コアデータは同期）
    db_post = await db.insert(Post(user_id=user.id, content=post.content))

    # 2. 通知・インデックス更新は非同期キューへ
    await pubsub_client.publish("post-created", {
        "post_id": db_post.id,
        "user_id": user.id
    })

    # 3. キャッシュを無効化
    await redis.delete(f"user:{user.id}:posts")

    return {"id": db_post.id}  # すぐ返す（キューは別ワーカーが処理）
```

**ポイント**:
- 投稿保存（コア）→ 同期
- 通知送信・全文検索インデックス更新（副作用）→ 非同期
- 関連キャッシュの削除を忘れずに

## トレードオフ

| 選択 | メリット | デメリット |
|---|---|---|
| キャッシュ追加 | 読み取りが高速・DB負荷減 | データ整合性の管理が必要・無効化設計が複雑 |
| キュー追加 | レイテンシ改善・耐障害性向上 | 処理の遅延・べき等性設計が必要・デバッグ難易度増 |
| CDN追加 | スケール・レイテンシ改善 | キャッシュ設定ミスで古いデータ配信・パージコスト |
| モノリス維持 | シンプル・デプロイ容易 | スケールの粒度が粗い・一部障害で全体停止リスク |

**判断の優先順位**:  
1. まずモノリス + DB のみでシンプルに作る  
2. 読み取りボトルネックが出たらキャッシュを追加  
3. 重い処理が出たらキューを追加  
4. グローバル展開・静的ファイルが増えたらCDN追加  
（最初から全部入れるのは過設計）
