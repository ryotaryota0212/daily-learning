# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき」という誘惑は常にある。しかし多くのスタートアップや中小チームにとって、モノリスの方がシンプルで壊れにくい。AI時代において「どちらが良いか」ではなく「今の自分たちに何が合うか」を判断する力が重要。

---

## 仕組みの要点

### モノリス（Monolith）
- 1つのプロセスで全機能を提供
- デプロイ単位が1つ → シンプル
- サービス間通信なし → レイテンシ低、トランザクション管理が楽
- 開発初期・小チームに最適

### マイクロサービス（Microservices）
- 機能単位で独立したサービスに分割
- 各サービスが独立してデプロイ・スケール可能
- チーム境界（Conway's Law）に合わせた分割が前提
- 運用コスト（サービス間通信、分散トレーシング、DevOps成熟度）が高い

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで始める | モノリスから始めて境界が見えてから分割 |
| 技術的都合だけで分割（言語、DB） | ビジネス境界（ドメイン）に沿って分割 |
| 分散モノリス（サービスが密結合） | 各サービスが独自DBを持ち、独立して動作 |
| 全機能を一度に移行 | ストラングラーフィグパターンで段階移行 |

---

## 判断基準

### モノリスを選ぶとき
- チームが10人以下
- ドメイン境界がまだ不明確
- MVPフェーズ・プロダクト未検証
- DevOps・k8s等の運用スキルが成熟していない

### マイクロサービスを検討するとき
- チームが独立してデプロイできるほど大きい（2ピザルール）
- 特定機能だけスケールが必要（例：動画処理）
- 障害隔離が事業上必要（決済と検索を分離したい）
- 異なる技術スタックが明確に有利な領域がある

---

## 移行戦略：ストラングラーフィグパターン

```
[ユーザー] → [API Gateway / Nginx]
                 ↓             ↓
          [新サービス]   [旧モノリス]
          (切り出し済み)  (残りの機能)
```

1. **境界を特定** → DDDのBounded Contextを使い、ドメインを識別
2. **新サービスを並行作成** → モノリスに影響せずに実装
3. **ルーティングを切り替え** → API GatewayでURL単位で振り分け
4. **モノリスから削除** → 新サービスが安定したら旧コードを削除

FastAPI + Cloud Run での例:
```python
# Cloud Run: 新しい通知サービスを独立デプロイ
# main.py (notification-service)
from fastapi import FastAPI
app = FastAPI()

@app.post("/notifications/send")
async def send_notification(payload: NotificationPayload):
    # モノリスから切り出した通知ロジック
    return await notification_handler.send(payload)
```

## トレードオフ整理

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ設定コスト大） |
| スケーラビリティ | 全体スケールのみ | 機能単位でスケール可 |
| 障害影響範囲 | 全機能に波及 | 隔離可（ただし分散障害が複雑化） |
| 運用コスト | 低 | 高（監視・デプロイ・通信管理） |
| チーム自律性 | 低（コンフリクト多） | 高（独立デプロイ可） |

## チェックリスト

- [ ] チーム規模・スキルレベルを考慮したか（小チームはモノリス優先）
- [ ] ドメイン境界を先に設計したか（コード上のモジュール境界を明確に）
- [ ] 移行はストラングラーフィグで段階的に行うか
- [ ] 各サービスが独自DBを持つ設計になっているか（分散モノリス回避）
- [ ] 分散トレーシング（Cloud Trace等）の準備ができているか
