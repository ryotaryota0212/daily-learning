# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき？」は最もよくある設計の問いの一つだが、**判断を誤ると複雑性だけが増してシステムが壊れやすくなる**。
モノリスは「古い」ではなく「シンプルで壊れにくい」設計。マイクロサービスは組織規模・チーム構造・スケール要件が伴って初めて効果を発揮する。
FastAPI + Cloud Run スタックでは「モジュラーモノリス → 部分的分離」が現実解になることが多い。

---

## 仕組みの要点

### モノリスの特性

- 単一デプロイ単位 → デプロイが単純、ローカル開発が楽
- 関数呼び出しで通信 → レイテンシゼロ、トランザクション管理が容易
- 1つのDB → JOIN・整合性が自然に保たれる
- 欠点：巨大化するとビルド遅延・チーム間の変更衝突が起きる

### マイクロサービスの特性

- 独立デプロイ → 高頻度リリースが可能（ただしオーケストレーション複雑）
- ネットワーク通信（HTTP/gRPC） → レイテンシ・障害伝播・分散トレーシングが必要
- サービスごとのDB → 結果整合性・Sagaパターンが必要
- Conway's Law：**組織の構造がアーキテクチャに反映される**

---

## 判断基準：どちらを選ぶか

| 基準 | モノリス有利 | マイクロサービス有利 |
|---|---|---|
| チーム規模 | 〜10人 | 複数チームが独立して動く |
| リリース頻度 | 週1〜月1 | サービスごとに独立デプロイ必要 |
| スケール要件 | 全体を水平スケール | 特定機能だけ高負荷 |
| ドメイン境界 | 不明確 | 明確に分離できる |
| チームスキル | K8s/分散システム未経験 | SRE・インフラ力がある |

**判断の原則：**
- スタートアップ初期・10人以下 → **必ずモノリスから始める**
- 「将来スケールするから」はマイクロサービスを選ぶ理由にならない
- 分割の判断は「チームが衝突しているか」が最も重要なシグナル

---

## アンチパターン vs 正しい設計

### アンチパターン

- **ナノサービス**：1関数1サービスに分割してネットワーク通信が爆増
- **分散モノリス**：サービスは分かれているが強依存でまとめてデプロイ必要
- **DBを共有するマイクロサービス**：独立性がなく分割の意味がない
- 「モダンに見える」という理由だけでマイクロサービス化

### 正しい設計：モジュラーモノリス

```
# FastAPIでのモジュラーモノリス構成例
app/
  routers/
    users.py      # ユーザードメイン
    payments.py   # 決済ドメイン
    orders.py     # 注文ドメイン
  services/
    user_service.py
    payment_service.py
  models/         # 共通DB（Neon PostgreSQL）

# 将来マイクロサービス化する場合は routers/ を独立サービスに切り出す
```

モジュール間は**直接インポートではなくサービス層経由**で呼び出す → 後で分離しやすい。

---

## 移行戦略：ストラングラーフィグパターン

モノリスから段階的に切り出す手法。一気にリプレイスしない。

```
1. モノリス前段にAPIゲートウェイを置く
2. 高負荷 or 独立チームが担当する機能を1つ切り出す
3. ゲートウェイでルーティングを新サービスへ段階的に切り替え
4. 旧モノリスの該当コードを削除
5. 繰り返す（急がない）
```

Cloud Run では**サービスごとに独立デプロイ可能**なため、段階移行に向いている。

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備コスト） |
| 障害の影響範囲 | 全体に波及 | サービス単位に限定（設計次第） |
| 運用複雑性 | 低い | 高い（分散トレーシング・サービスメッシュ） |
| チームの自律性 | 低い | 高い |
| データ整合性 | 強整合（ACID） | 結果整合（Saga/補償トランザクション） |

## チェックリスト

- [ ] チームが10人以上で、かつ異なる機能で衝突が起きているか確認した
- [ ] モノリスをモジュール分割してから分離を検討している（モジュラーモノリスが先）
- [ ] 分離候補のドメイン境界が明確に定義できている
- [ ] 分散トレーシング・サービス間認証の運用体制がある
- [ ] ストラングラーフィグパターンで段階的移行を計画している
