# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要
「マイクロサービスにすれば scalable」は誤解。小規模チームや初期フェーズでマイクロサービスを選ぶと、分散システムの複雑さに潰される。重要なのは「今のチームとビジネス規模に合った構成はどれか」を判断する力。AI時代においても、この設計判断はコードより人間が担うべき領域。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ、単一DB、単一プロセス
- 開発・テスト・デバッグが容易
- チームが小さいほど生産性が高い
- 垂直スケールは限界があるが、Cloud Runなら水平スケールも可能
- デプロイ単位が大きい → 変更のリスクが全体に波及

### マイクロサービスの特性
- サービスごとに独立デプロイ・スケール
- 技術スタックの自由度が高い
- チーム境界をサービス境界に合わせられる（Conway's Law）
- ネットワーク遅延・分散トランザクション・サービス間認証などの複雑さが増す

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい判断 |
|---|---|
| 最初からマイクロサービスで設計 | モノリスで始めて、分割ラインが明確になったら分割 |
| DBを全サービスで共有 | サービスごとにDBを分離（または論理的に分離） |
| チームが1つなのにサービスを分割 | チーム境界 = サービス境界が原則 |
| 同期RPC(HTTP)で全通信 | 疎結合な非同期（Pub/Sub）を基本にする |
| マイクロサービス化 = リファクタリング と混同 | 分割は設計の変更。まず境界を設計してから実装 |

---

## 判断フレームワーク

### モノリスを選ぶ条件
- チームが5人以下
- プロダクトのドメイン境界がまだ不明確
- 初期フェーズ（PMF前）
- 開発スピードが最優先

### マイクロサービスを検討する条件
- チームが複数存在し、サービス境界でオーナーシップを分けたい
- 特定機能のスケール要件が大幅に異なる（例: 動画変換 vs APIサーバー）
- デプロイ頻度が高く、独立リリースが必要
- 障害を隔離したい（サーキットブレーカーで他サービスを守る）

---

## 段階的移行パターン（Strangler Fig）

```
[Before] モノリス
  FastAPI app → 全機能 → Neon DB

[Step 1] 新機能だけ別サービスに切り出す
  FastAPI app (既存) ─→ Neon DB
       ↓ HTTP
  新サービス (Cloud Run) → 専用 DB

[Step 2] 既存機能を順次移行
  API Gateway (Cloud Run or Cloudflare) 
    ├→ 認証サービス (Firebase Auth + Cloud Run)
    ├→ 注文サービス (Cloud Run + Neon)
    └→ 通知サービス (Cloud Run + Pub/Sub)
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い |
| 運用複雑度 | 低い | 高い（監視・デプロイ・サービス間通信） |
| スケーラビリティ | 限定的 | 柔軟 |
| 障害の局所化 | 困難（全体に波及） | 可能（サービス単位で分離） |
| チーム自律性 | 低い | 高い |
| コスト（小規模） | 安い | 高い（管理オーバーヘッド） |

## FastAPI + Cloud Run での現実的な中間解

完全マイクロサービスでなく「モジュラーモノリス」が現実解になることが多い。

```python
# モジュラーモノリス: ルーターでドメインを分離
# main.py
from fastapi import FastAPI
from app.routers import orders, users, notifications

app = FastAPI()
app.include_router(orders.router, prefix="/orders")
app.include_router(users.router, prefix="/users")
app.include_router(notifications.router, prefix="/notifications")
# → 将来の分割を見据えた境界を持ちつつ、今はシングルデプロイ
```

## チェックリスト

- [ ] チームの人数と境界を先に決め、サービス分割はそれに合わせているか
- [ ] DBの分離方針が決まっているか（共有DBはアンチパターン）
- [ ] サービス間通信の障害時の挙動を設計しているか（タイムアウト・リトライ・CB）
- [ ] モジュラーモノリスを中間ステップとして検討したか
- [ ] 分割のコスト（運用・監視・デプロイ複雑化）を定量的に評価したか
