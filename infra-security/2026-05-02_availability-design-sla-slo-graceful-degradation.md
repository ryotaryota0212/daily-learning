# 可用性設計：SLA/SLO・冗長化・フェイルオーバー・グレースフルデグラデーション

## 概要
- 「常に100%動く」は不可能。**何%まで落ちることを許容するか**を先に決めるのが可用性設計。
- SLA/SLO を決めずに冗長化すると、コストが青天井になる。
- AI時代に評価されるのは「壊れないシステム」より「壊れても被害を最小化できる設計」を語れる人。
- FastAPI + Cloud Run + Neon の構成でも、何が SPOF（単一障害点）かを把握していないと、ある日突然全停止する。

## 用語の整理

| 用語 | 意味 | 例 |
|---|---|---|
| SLA | 顧客との契約上の保証値 | 99.9% / 月 |
| SLO | 社内で目指す目標値（SLA より厳しめ） | 99.95% |
| SLI | 実測指標 | 成功リクエスト率、p99レイテンシ |
| エラーバジェット | 1 - SLO。許容される失敗の総量 | 99.9% → 月43分 |

- 「99.9% (Three Nines)」= 月43分のダウンが許容される
- 「99.99% (Four Nines)」= 月4.3分。**コストは桁で跳ね上がる**

## 仕組みの要点
- **冗長化**: 同じ役割のインスタンスを複数走らせ、1つ落ちても継続させる（Cloud Run はデフォルトで複数インスタンス）。
- **フェイルオーバー**: プライマリが死んだらスタンバイに切り替え。Neon は read replica + branching で擬似的に対応可能。
- **ヘルスチェック**: `/healthz` が浅いと「DB切れてるのに 200 返す」事故が起きる。**依存先まで含めて確認**。
- **グレースフルデグラデーション**: 全機能停止ではなく、重要機能だけ生かす（例：レコメンド失敗時は人気順を返す）。
- **エラーバジェット運用**: 予算が残っていれば新機能リリース、尽きたら信頼性改善に集中。

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| SLO を決めずに「とにかく落とすな」 | SLO を数値で合意し、エラーバジェットで判断 |
| ヘルスチェックが `return "ok"` だけ | DB/外部API疎通までチェック、ただし**深すぎる依存はNG** |
| 外部API失敗で 500 を返してユーザー画面が真っ白 | フォールバック値・キャッシュ済みデータで縮退運転 |
| マルチリージョンで「完全冗長」と言いつつ DB が単一リージョン | SPOF を図に書き出して洗い出す |
| リトライ無制限で障害が連鎖 | サーキットブレーカー + 指数バックオフ |

## コード例：縮退運転とヘルスチェック

```python
from fastapi import FastAPI, HTTPException
from sqlalchemy import text

app = FastAPI()

@app.get("/healthz")  # liveness: プロセスが動いているか
async def healthz():
    return {"status": "ok"}

@app.get("/readyz")  # readiness: トラフィックを受けられるか
async def readyz(db=Depends(get_db)):
    try:
        await db.execute(text("SELECT 1"))
        return {"status": "ready"}
    except Exception:
        raise HTTPException(503, "db unavailable")

@app.get("/recommendations")
async def get_recs(user_id: str):
    try:
        return await reco_service.fetch(user_id, timeout=0.5)
    except (TimeoutError, ServiceError):
        return await popular_items_cache.get()  # 縮退: 人気順で代替
```

ポイント：
- `/healthz`（liveness）と `/readyz`（readiness）を分ける。Cloud Run / k8s で挙動が変わる。
- 依存先障害時は **例外を握って代替値を返す**。完全失敗は最終手段。

## トレードオフ

| 選択肢 | メリット | コスト・リスク |
|---|---|---|
| SLO 99.9% | コスト現実的、運用容易 | 月43分のダウン許容 |
| SLO 99.99% | 顧客信頼度高 | 監視・冗長化コストが数倍 |
| マルチリージョン Active-Active | 災害時も無停止 | データ整合性・コスト・複雑度が爆発 |
| シングルリージョン + バックアップ | シンプル・安価 | 復旧に時間 |
| ヘルスチェックを浅くする | 誤判定が少ない | 障害検知が遅れる |
| ヘルスチェックを深くする | 早期検知 | カスケード障害（DB遅延でインスタンス全滅） |

## 意思決定の指針
- **まず SLO を決める**。決まっていないと「これで十分か」を議論できない。
- **SPOF を図に書く**。Cloud Run は冗長でも、Neon・Firebase Auth・外部 API は単一点。
- **障害シナリオを書き出す**：「Neon が10分止まったらどうなる？」を答えられるか。
- **コストと釣り合うか**：99.99% を目指す前に、本当にそれが事業価値に見合うか確認。
