# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか」という問いは、AI時代の設計判断の中でも最も誤解されやすいもの。  
多くのチームが「スケールするから」という曖昧な理由でマイクロサービスを選び、運用コストに潰される。  
正しい問いは「**今のチームと規模で、マイクロサービスの複雑さを払えるか**」。  
FastAPI + Cloud Run スタックでは特に、分割のコストとメリットのバランスを慎重に見極める必要がある。

---

## 仕組みの要点

### モノリスとは
- 単一デプロイ単位。コード・DBが一体
- 開発・テスト・デプロイが単純
- チームが小さいうちは圧倒的に生産性が高い

### マイクロサービスとは
- サービスごとに独立デプロイ・独立DB
- サービス間はAPI/メッセージキューで通信
- スケール・障害分離は優れるが、運用複雑度が急増

### 判断の核心：コンウェイの法則
> 「システムの構造は、それを作る組織のコミュニケーション構造に収束する」

- チームが1〜2チームなら、モノリスが自然な形
- チームが独立して動ける規模（5チーム以上）になってからマイクロサービスを検討

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 初手でマイクロサービス | モノリスから始め、ボトルネックが出たら分割 |
| サービスをDB共有 | サービスごとに独立DBを持つ |
| 同期HTTPで全サービス連携 | 非同期Pub/Subで疎結合にする |
| デプロイが独立していない | 各サービスが独立してCI/CDできる |
| 全部を細かく分割 | ビジネスドメイン境界（DDD境界）で分割する |

### モノリスが正解なケース
- チーム3名以下、またはエンジニア10名未満
- ドメインがまだ安定していない（仕様変更が頻繁）
- デプロイ頻度が週1以下
- ユーザー数が10万以下で負荷が予測できる

### マイクロサービスが正解なケース
- 特定機能だけ独立スケールが必要（例：画像処理・ML推論）
- チームが5以上で、互いのデプロイをブロックしたくない
- サービスごとに言語・技術選択を変えたい正当な理由がある

## コード/設計例（Cloud Run 前提）

### モノリス構成（初期推奨）
```
# Cloud Runに1サービスとしてデプロイ
services/
  app/          # FastAPIアプリ本体
    routers/
      users.py
      orders.py
      payments.py
    db/         # Neon PostgreSQL（単一DB）

# docker-compose.yml（ローカル開発）
services:
  app:
    build: .
    ports: ["8000:8000"]
  db:
    image: postgres:15
```

### マイクロサービス移行（段階的分割）
```
# Step 1: モノリス内でモジュール境界を明確化
# Step 2: 境界をAPIで切り出し（Strangler Fig パターン）
# Step 3: Cloud Runサービスとして独立デプロイ

# 分割後の構成例
cloud-run-services/
  user-service/      # users DB
  order-service/     # orders DB
  payment-service/   # payments DB（外部SaaS連携）
  api-gateway/       # Cloud Run + Cloud Endpoints
```

---

## Strangler Fig パターン（安全な移行戦略）

```
Before:
  Client → Monolith (all logic)

Step 1: ルーターを挟む
  Client → API Gateway → Monolith

Step 2: 新サービスを追加
  Client → API Gateway → Payment Service (new)
                       → Monolith (rest)

Step 3: 移行完了後にモノリス側を削除
  Client → API Gateway → Payment Service
                       → Order Service
                       → User Service
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（基盤整備が必要） |
| デプロイ複雑度 | 低い | 高い（CI/CD, サービスメッシュ） |
| 障害分離 | 弱い（全体停止リスク） | 強い（一部だけ落ちる） |
| スケール柔軟性 | 全体スケール | サービス単位でスケール |
| 分散トレーシング | 不要 | 必要（Cloud Trace等） |
| チーム独立性 | 低い | 高い |
| 運用コスト | 低い | 高い |

## チェックリスト

- [ ] チーム規模・体制で分割を正当化できるか確認した
- [ ] ドメイン境界（どこで切るか）を明確に定義した
- [ ] サービスごとにDBを独立させている（DB共有していない）
- [ ] モノリスからの移行はStrangler Figパターンで段階的に行う
- [ ] 分散トレーシング（Cloud Trace）とログ集約の設計をした
