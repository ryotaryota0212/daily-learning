# マイクロサービス vs モノリス：判断基準と移行戦略

## 概要

「マイクロサービスにすればスケールする」という誤解が蔓延している。実際には**組織・チーム規模・運用コストとのトレードオフ**であり、多くのスタートアップにとってモノリスは正しい選択だ。AI時代の設計者に求められるのは、流行に流されず「なぜその構成か」を説明できる力。

---

## 仕組みの要点

### モノリスの特徴
- 単一デプロイ単位。コードが1つのプロセスで動く
- サービス間通信がインプロセス呼び出し（低レイテンシ）
- トランザクションが容易（1つのDBに対してACIDが成立）
- 開発・デバッグ・テストがシンプル

### マイクロサービスの特徴
- 独立デプロイ可能な複数サービス
- サービス間通信がネットワーク経由（REST/gRPC/イベント）
- 分散トレーシング・サービスメッシュなど運用複雑度が上がる
- チーム独立性・技術スタック独立性を得られる

### 判断の3軸
| 軸 | モノリス有利 | マイクロサービス有利 |
|---|---|---|
| チーム規模 | 〜10人 | 複数チーム（Conway's Law） |
| スケール要件 | 均等なスケール | 部分的な高負荷（決済だけ重いなど） |
| デプロイ頻度 | 週1〜月1 | 各チームが独立してデプロイしたい |

---

## アンチパターン vs 正しい設計

### アンチパターン
- **分散モノリス**：サービスに分割したが、デプロイは全部一緒。サービス間の結合が強く、独立していない
- **最初からマイクロサービス**：ドメイン境界が不明確なまま分割 → 後で境界を引き直すコストが爆発
- **同期HTTP呼び出しの連鎖**：A→B→C→Dと同期呼び出し → どこかが遅いと全体が遅い

### 正しい設計
- **モノリス・ファースト**：まずモノリスで作り、分割理由が明確になってから切り出す
- **モジュラーモノリス**：単一デプロイだが内部はドメイン境界でモジュール化 → 後でマイクロサービスに分割しやすい
- **ストラングラーフィグパターン**：モノリスを少しずつ置き換え（いきなり全体を書き直さない）

## コード/設計例（FastAPI + Cloud Runでのモジュラーモノリス構造）

```
app/
├── main.py              # エントリポイント
├── modules/
│   ├── auth/            # 認証ドメイン
│   │   ├── router.py
│   │   └── service.py
│   ├── orders/          # 注文ドメイン
│   │   ├── router.py
│   │   └── service.py
│   └── notifications/   # 通知ドメイン（後でCloud Pub/Sub化候補）
│       └── service.py
└── shared/
    └── db.py            # DB接続（共有）
```

```python
# main.py - ドメインごとにルーターを登録
from fastapi import FastAPI
from app.modules.auth.router import router as auth_router
from app.modules.orders.router import router as orders_router

app = FastAPI()
app.include_router(auth_router, prefix="/auth")
app.include_router(orders_router, prefix="/orders")
```

この構造なら `notifications` を後で独立サービスに切り出しやすい。

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備が必要） |
| 運用複雑度 | 低い | 高い（監視・トレーシング・デプロイ管理） |
| 部分スケール | 不可（全体スケール） | 可能 |
| 障害影響範囲 | 広い（一部障害が全体に波及しやすい） | 狭い（サービス単位で分離） |
| チーム独立性 | 低い | 高い |

**Cloud Runでの現実的な落とし所**：  
モジュラーモノリスを1つのCloud Runサービスとして動かし、負荷の高いバッチ処理や通知だけCloud Functions/別Cloud Runに分離する「部分的マイクロサービス」が費用対効果が高い。

## チェックリスト

- [ ] チームが10人以上で、独立デプロイの必要性が出てからマイクロサービスを検討する
- [ ] 分割前に「ドメイン境界（何と何は独立して変わるか）」を明確にする
- [ ] モノリスの内部はモジュール境界を守り、後で分割できる構造を保つ
- [ ] サービス間をまたぐトランザクションの設計（SAGAパターン等）を事前に理解する
- [ ] マイクロサービス移行時はストラングラーフィグパターンで段階的に行う
