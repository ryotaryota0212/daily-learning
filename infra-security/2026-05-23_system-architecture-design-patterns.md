# システム全体構成の設計パターン（API・DB・キャッシュ・キュー・CDN）

## 概要

「動くコードを書く力」より「システムを成立させる力」が問われる時代、最初の設計判断が最もコストに直結する。
コンポーネント（API・DB・キャッシュ・キュー・CDN）の責務を明確にし、「なぜその構成か」を説明できることが設計者の本質的な仕事。
間違った場所にデータを置くと、スケールアップコスト・障害影響範囲・レイテンシがすべて悪化する。

---

## 各コンポーネントの責務と選択基準

### API（Cloud Run）
- **責務**: ビジネスロジックの実行・入力検証・認証
- **設計原則**: ステートレスに保つ → 水平スケールが容易になる
- **アンチパターン**: セッション状態をメモリに持つ（スケールアウト時に壊れる）

### DB（Neon / PostgreSQL）
- **責務**: 信頼できる唯一のデータソース（Source of Truth）
- **設計原則**: 書き込みは必ずDB経由、キャッシュはあくまで読み取り高速化
- **アンチパターン**: 集計・検索をすべてDBに投げる → ボトルネックになる

### キャッシュ（Redis / Cloud Memorystore）
- **責務**: 読み取りレイテンシ削減・DB負荷軽減
- **設計原則**: キャッシュはいつ消えてもよいデータのみ。TTLを必ず設定する
- **アンチパターン**: キャッシュを書き込みの主体にする（データ不整合リスク）

### キュー（Cloud Pub/Sub / Cloud Tasks）
- **責務**: 非同期処理・ピーク吸収・サービス間の疎結合化
- **設計原則**: キューに入れた時点でユーザーにレスポンスを返す
- **アンチパターン**: 重い処理をAPIリクエスト内で同期実行（タイムアウト・UX悪化）

### CDN（Cloudflare）
- **責務**: 静的アセット配信・エッジキャッシュ・DDoS防御
- **設計原則**: オリジンへのリクエストを最小化。キャッシュヒット率を監視する
- **アンチパターン**: 動的データをCDNにキャッシュして古いデータを返す

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 全リクエストがDBに直撃 | 読み取りにキャッシュを挟む |
| APIがセッション状態を保持 | ステートレス設計＋JWTで認証 |
| 重い処理を同期で実行 | キューに積んで非同期処理 |
| 静的ファイルをCloud Runから配信 | CDN経由で配信 |
| 1台のDBに全負荷 | 読み取りレプリカ or キャッシュで分散 |

## 構成例（FastAPI + Neon + Redis + Pub/Sub + Cloudflare）

```
[ユーザー]
    ↓ HTTPS
[Cloudflare CDN] ← 静的アセット・エッジキャッシュ
    ↓ キャッシュMISS時
[Cloud Run: FastAPI]
    ├── Firebase Auth で認証検証
    ├── Redis: キャッシュ読み取り（Cache-Aside）
    ├── Neon(PostgreSQL): 書き込み・キャッシュMISS時の読み取り
    └── Pub/Sub: 非同期タスク（メール送信・集計等）をキューへ
         ↓
    [Cloud Run: Worker] ← Pub/Sub サブスクライバー
```

**リクエストフロー例（ユーザープロフィール取得）:**
```python
async def get_profile(user_id: str, redis: Redis, db: AsyncSession):
    # 1. キャッシュ確認（Cache-Aside）
    cached = await redis.get(f"profile:{user_id}")
    if cached:
        return json.loads(cached)
    # 2. DBから取得
    profile = await db.execute(select(User).where(User.id == user_id))
    result = profile.scalar_one()
    # 3. キャッシュに保存（TTL: 5分）
    await redis.setex(f"profile:{user_id}", 300, result.json())
    return result
```

## トレードオフ

| 観点 | シンプル構成 | フル構成 |
|---|---|---|
| 運用コスト | 低い（管理対象が少ない） | 高い（Redis・Pub/Sub管理が必要） |
| レイテンシ | DBに依存 | キャッシュで大幅改善 |
| 一貫性 | 高い（常にDB） | キャッシュ無効化のバグリスク |
| スケール上限 | DB性能に依存 | 水平スケールしやすい |

**判断基準:**
- MAU < 1万: APIとDBだけで始める。Redisは不要
- 読み取り多い・同じデータを繰り返し返す: キャッシュを追加
- 重い処理（PDF生成・メール・集計）: キューを追加
- 静的ファイルあり: 最初からCDN

## チェックリスト

- [ ] APIはステートレスか（ローカルメモリにセッションを持っていないか）
- [ ] キャッシュにTTLが設定されているか
- [ ] 重い処理（数秒かかる処理）はキューに委譲しているか
- [ ] DBへの直接アクセスはWrite/Source-of-Truthのみか
- [ ] 障害時に「どのコンポーネントが落ちたらどうなるか」を説明できるか
