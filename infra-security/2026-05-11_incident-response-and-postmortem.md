# インシデント対応とポストモーテムの文化

## 概要
障害は必ず起きる。差がつくのは「障害後に何をするか」。
ポストモーテムとは障害の根本原因を特定し、再発防止策を組織の知識として残す文化的実践。
「犯人探し」ではなく「システム改善」が目的。障害対応力はチームの成熟度を最もよく表す指標の1つ。

---

## インシデント対応の5フェーズ

| フェーズ | 目的 | 判断基準 |
|---------|------|----------|
| **検知** | 異常を早期に発見 | アラートが鳴る前にユーザー報告はないか |
| **初動** | 被害を止める | まず「影響範囲を広げない」を優先 |
| **診断** | 原因を絞り込む | 仮説を立て証拠を確認する |
| **復旧** | サービスを戻す | 完全修正より早期回復を優先 |
| **事後** | 再発を防ぐ | ポストモーテムで記録・共有 |

---

## 仕組みの要点

- **Incident Commander（IC）**: 1人が指揮を取り、並走する作業を統括する役割を明示的に決める
- **コミュニケーションチャンネル分離**: 対応チャンネル（#incident-XXXX）とステータス通知を分ける
- **タイムライン記録**: 対応中も「何時に何をしたか」を逐次メモ。後のポストモーテムに使う
- **5 Whys**: 「なぜ?」を5回繰り返して根本原因へ。表面症状で止まらない
- **Blameless文化**: 個人のミスではなくシステムの欠陥として分析する

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい対応 |
|--------------|-----------|
| 「誰がやらかした」で終わる | 「なぜシステムがそれを許した」を問う |
| 障害中に複数人が同時に操作 | ICが司令塔、他はサポートに徹する |
| 口頭だけで対応、記録なし | Slackに逐次タイムラインを貼る |
| 再発防止策が「気をつける」 | プロセス・自動化・テストで担保する |
| ポストモーテムが書かれない | 1週間以内に必ず書く、テンプレート化する |

## ポストモーテム テンプレート（最小構成）

```markdown
## 概要
- 発生日時: 2026-05-10 14:30 JST
- 復旧日時: 2026-05-10 15:45 JST (影響: 75分)
- 影響範囲: 認証APIが断続的に503 (リクエストの約30%)

## タイムライン
- 14:30 Cloud Run が503を返し始める
- 14:38 アラート発火、IC指名
- 14:55 Neon接続プールの枯渇を特定
- 15:10 接続数上限を緩和、一時回復
- 15:45 正式修正デプロイ完了

## 根本原因
- バッチ処理が接続を解放せずリークしていた
- 接続プールの上限アラートが設定されていなかった

## 再発防止策
- [ ] 接続リークのユニットテスト追加
- [ ] DB接続数メトリクスのアラート設定
- [ ] バッチ処理にコネクション解放の明示的処理を追加
```

## トレードオフ

| 観点 | 詳細なポストモーテム | 簡易ポストモーテム |
|------|-------------------|--------------------|
| 再発防止効果 | 高い | 低い |
| 作成コスト | 高い（2〜3時間） | 低い（30分） |
| 適切な場面 | P0/P1インシデント | P2/P3、軽微な障害 |

- **重大度の定義**（例）: P0=全サービス停止、P1=主要機能停止、P2=一部機能劣化、P3=パフォーマンス低下

---

## FastAPI + Cloud Run 構成での実践ポイント

- Cloud Run の **CPU/メモリ/リクエスト数** を Cloud Monitoring でアラート設定
- Neon の **接続数上限** を `max_connections` で監視し、80%超で通知
- Firebase Auth の **認証エラー率** を Cloud Logging でフィルタ＋アラート
- FastAPI に `/healthz` エンドポイントを設け、Cloud Run のヘルスチェックと連動させる
