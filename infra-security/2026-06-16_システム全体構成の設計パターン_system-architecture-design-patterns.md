# システム全体構成の設計パターン（API・DB・キャッシュ・キュー・CDN）

## 概要

Webサービスはいくつかの標準的な構成要素の組み合わせで成り立つ。「どのコンポーネントを、どこに、なぜ置くか」を説明できることがシステム設計の基本。AI時代はコードを書く部分は自動化されやすくなるが、**構成の妥当性を判断する力**は人間が担う。コンポーネント間のデータフロー・ボトルネック・障害影響範囲を即座に語れることが、設計者の価値になる。

---

## 主要コンポーネントの役割と配置

### 全体像（FastAPI + Neon + Cloud Run スタック）

```
Client
 └─ Cloudflare CDN/WAF
     └─ Cloud Run (FastAPI)  ← ステートレス・水平スケール
          ├─ Neon (PostgreSQL) ← 永続データ（Read Replica 分離）
          ├─ Redis (Upstash)   ← セッション・キャッシュ
          ├─ Cloud Pub/Sub     ← 非同期ジョブ
          └─ Firebase Auth     ← 認証トークン検証（CDKなし）
```

### 各コンポーネントの責務

| コンポーネント | 役割 | 置かない場合のリスク |
|---|---|---|
| CDN | 静的資材配信・DDoS吸収 | オリジンに全トラフィックが直撃 |
| APIサーバ (Cloud Run) | ビジネスロジック・認証検証 | スケールできない |
| DB (Neon) | 信頼できる唯一の真実 | データ整合性崩壊 |
| キャッシュ (Redis) | DBへの頻繁なクエリを回避 | DBがボトルネックに |
| キュー (Pub/Sub) | 遅い処理をAPIから切り離す | タイムアウト・レスポンス遅延 |

---

## アンチパターン vs 正しい設計

### アンチパターン

- **全部DBに聞く設計**: キャッシュなしでリクエストごとにDB参照 → DBがスケールボトルネック
- **同期処理でメール送信**: APIハンドラ内でメール送信 → タイムアウトリスク
- **Cloud Runに状態を持つ**: セッションをローカルメモリに保持 → スケールアウト時にセッション喪失
- **単一DBエンドポイント**: Read/Write 混在 → Write負荷がRead性能を圧迫

### 正しい設計

- Read Replica でRead/Write分離。書き込みはPrimary、参照はReplica
- キャッシュは「DBの前段」ではなく「頻繁に変わらないデータのみ」に限定
- 重い処理（メール送信・画像処理・AI推論）は必ずキューを経由
- Cloud Runはステートレス。状態はRedisかDBに持たせる

## 設計例：ユーザー投稿APIの構成

```python
# FastAPI エンドポイント例（非同期処理への委譲）
@router.post("/posts")
async def create_post(post: PostCreate, user=Depends(verify_firebase_token)):
    # 1. DBに保存（同期）
    saved = await db.posts.insert(user_id=user.uid, content=post.content)

    # 2. 重い後処理はキューへ委譲（非同期）
    await pubsub.publish("post-created", {"post_id": saved.id})

    # 3. キャッシュ無効化
    await redis.delete(f"user:{user.uid}:posts")

    return {"id": saved.id}
```

**ポイント**:
- APIは保存と委譲だけを担当。処理は即座に返る
- 通知・インデックス更新はサブスクライバーが非同期処理
- キャッシュ無効化でデータ鮮度を保証

## トレードオフ

| 選択 | メリット | コスト |
|---|---|---|
| キャッシュ追加 | DBクエリ削減・高速化 | キャッシュ無効化の複雑さ、データ不整合リスク |
| Read Replica | 参照性能向上 | 数ミリ秒のレプリケーション遅延（結果整合性） |
| キュー化 | APIレスポンス高速化 | 失敗時の再試行・モニタリング設計が必要 |
| CDN追加 | 静的資材配信の高速化 | キャッシュパージの手間、動的コンテンツには効かない |
| マイクロサービス化 | 独立スケール | サービス間通信の複雑さ・運用コスト増 |

**基本方針**: 最初はモノリスで始め、ボトルネックが明確になった箇所だけを切り出す。CDN・キャッシュ・キューはモノリスのままでも導入可能。

## チェックリスト

- [ ] Cloud Runのインスタンスはステートレスか（ローカル状態を持っていないか）
- [ ] 重い処理（メール・AI・ファイル変換）はキュー経由になっているか
- [ ] DBのRead/WriteはReplica分離の候補を検討したか
- [ ] キャッシュ対象は「TTLが設計できるデータ」に限定されているか
- [ ] コンポーネントが1つ落ちたとき、他コンポーネントへの影響を説明できるか
