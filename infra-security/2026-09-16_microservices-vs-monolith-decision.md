# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

AI時代において「マイクロサービスを使うべきか？」という問いは頻繁に発生する。しかし多くのチームがモノリスで十分な段階でマイクロサービスを導入し、運用コストと複雑性に苦しむ。
**重要なのは「マイクロサービスが正しいか」ではなく「今のチームと規模にとって最もシンプルで壊れにくい構成は何か」を判断できること**。

---

## 仕組みの要点

### モノリスの特徴
- 単一デプロイ単位・単一データベース・シンプルな運用
- トランザクションが自然に一貫（ACID保証が容易）
- デバッグ・ローカル開発が容易
- チームが小さいほど生産性が高い

### マイクロサービスの特徴
- サービスごとに独立デプロイ・独立スケール・独立DB
- 組織構造とシステム境界を一致させる（コンウェイの法則）
- 分散トレーシング・サービスメッシュ等の追加インフラが必要
- 障害の局所化が可能だが、分散障害パターンが発生しうる

### モジュラーモノリス（中間解）
- 単一デプロイだが内部はモジュール分割
- チーム間の境界を設計し、将来の分割を容易にする
- 多くのケースで最初の正解はこれ

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスを選択 | モノリスで始めて境界が明確になってから分割 |
| DBを共有するマイクロサービス | サービスごとに独立したDB（DBが共有ならモノリスと同じ） |
| 全エンドポイントを同期APIで繋ぐ | 非同期イベントで疎結合、同期は最小限 |
| デプロイ単位だけ分割（ロジックは結合）| ドメイン境界に沿って責務ごと分割 |
| 「とりあえずマイクロサービス」で採用 | チーム人数・デプロイ頻度・スケール要件で判断 |

---

## 判断フレームワーク

```
判断基準チェックリスト（モノリスで十分な条件）:
  □ 開発チームが5-8人以下
  □ サービス全体のデプロイを週1-2回まとめてできる
  □ 特定モジュールだけ10倍スケールする必要はない
  □ ドメイン境界がまだ明確に見えていない（設計が熟していない）
  □ 分散トレーシング・サービスメッシュを運用するOpsメンバーがいない

→ 上記が多いほどモノリス（またはモジュラーモノリス）が正解

マイクロサービスが有効な条件:
  □ チーム（スクワッド）が独立してデプロイしたい
  □ 特定サービスだけコスト・スケール要件が異なる
  □ 技術スタックを分けたい正当な理由がある（ML推論サービス等）
  □ ドメイン境界がビジネス上明確に存在する
```

## FastAPI + Cloud Run での実装例

### モジュラーモノリスの構造（推奨スタート地点）

```
app/
  routers/
    auth.py      # Firebase Auth検証
    users.py     # ユーザー管理
    orders.py    # 注文管理
  services/
    user_service.py
    order_service.py
  db/
    models.py    # 単一Neon DB
main.py          # 単一エントリポイント → Cloud Run 1サービス
```

### サービス分割時の境界設計

```python
# 悪い例：注文サービスがユーザーDBを直接参照
# order_service.py
from app.db.user_model import User  # ← 直接import = 境界違反

# 良い例：ユーザー情報はAPIまたはイベント経由
async def get_order(order_id: str, user_id: str):
    # user_idはJWTから取得（Firebase Auth）
    # ユーザー詳細が必要なら user_service API を呼ぶ
    order = await order_repo.get(order_id)
    if order.user_id != user_id:
        raise HTTPException(403)
    return order
```

### Cloud Runでの段階的分割

```bash
# モノリス: 1サービス
gcloud run deploy app --image gcr.io/project/app

# 分割後: サービスごとにデプロイ
gcloud run deploy user-service  --image gcr.io/project/user-service
gcloud run deploy order-service --image gcr.io/project/order-service
# サービス間通信: Cloud Run内部URLで認証（Workload Identity）
```

## 移行戦略（モノリス → マイクロサービス）

### ストラングラーフィグパターン
1. 新機能から独立サービスとして実装
2. モノリス内の既存機能を徐々にサービスへ移行
3. モノリスを"絞め殺す"（最終的に削除）

### 実践的な分割順序
```
優先度高（分割しやすい）:
  - 認証・認可（Firebase Auth統合）
  - 通知サービス（非同期、疎結合）
  - 外部API統合（決済、メール等）

優先度低（分割コスト大）:
  - コアドメインロジック（トランザクション境界が複雑）
  - レポート・集計（複数DBのJOINが必要になりがち）
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | ◎ 速い | △ インフラ設定に時間 |
| スケール柔軟性 | △ 全体スケール | ◎ 部分スケール |
| 障害影響範囲 | △ 全体に波及 | ◎ 局所化しやすい |
| 運用複雑性 | ◎ シンプル | △ 分散システムの難しさ |
| トランザクション | ◎ ACID容易 | △ Sagaパターン等が必要 |
| チーム独立性 | △ コード競合 | ◎ 独立デプロイ |

**結論：Neon（PostgreSQL）+ Cloud Run + Firebase Auth のスタックでは、
まずモジュラーモノリスで始め、チームが10人超・スクワッドが独立したいタイミングで分割を検討するのが最もコスパが良い。**

## チェックリスト

- [ ] チームサイズ・デプロイ頻度・スケール要件を確認してからアーキテクチャを決定している
- [ ] モノリスでも内部モジュール境界（ドメイン境界）を設計している
- [ ] サービス分割時、DBも分離しているか（共有DBは分割の意味がない）
- [ ] サービス間通信は非同期ファースト（同期は最小限）になっているか
- [ ] 移行はストラングラーフィグパターンで段階的に進めているか
