# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「とりあえずマイクロサービスにしよう」という判断がプロジェクトを壊す。モノリスは悪ではなく、多くの場合スタート時点の正解。分散システムの複雑さは無料ではない。チームの規模・デプロイ頻度・スケール要件を見て「今どちらが壊れにくいか」を判断することがAI時代のエンジニアに求められる設計力。

## 仕組みの要点

### モノリスの特性
- 単一プロセス・単一DB。デプロイが1回で済む
- サービス間通信がin-processなので高速・信頼性高
- デバッグ・追跡が容易（1ログ、1トレース）
- 小チーム（10人以下）では圧倒的にシンプル

### マイクロサービスの特性
- 独立デプロイ・独立スケール・独立障害境界
- チームが分かれているとき、所有権が明確
- 分散システムの複雑さ（ネットワーク遅延・整合性・サービスディスカバリ）が伴う
- 運用コストが高い（監視・トレーシング・サービスメッシュ）

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで始める | モノリスで始めて、境界が見えたら分割 |
| チームより多いサービス数 | チームの数 ≒ サービスの数が目安 |
| 全サービスが同じDBを共有 | サービスごとにDBを持つ（データ独立性） |
| 同期HTTP呼び出しの連鎖 | 非同期キューで疎結合にする |
| 「マイクロサービス = 良い設計」という思い込み | モノリスが正解なケースも多い |

## コード/設計例（モジュラーモノリス → サービス分割の流れ）

```python
# Step1: モノリス内でモジュール境界を明確にする（モジュラーモノリス）
# app/modules/billing/service.py
# app/modules/user/service.py

# Step2: モジュール間はインターフェース経由のみ（内部DB直参照禁止）
from app.modules.user.service import UserService  # OK
# from app.modules.user.models import User        # NG: 内部実装への依存

# Step3: 境界が安定したら Cloud Run の別サービスへ切り出し
# POST /internal/users/{id}  ← サービス間API
# または Pub/Sub で非同期通信
```

## 判断フレームワーク

**モノリスで始めるべき条件（ほぼ全スタートアップ）**
- チームが10人以下
- ドメイン境界がまだ曖昧
- デプロイ頻度が低い（週1以下）

**マイクロサービスを検討する条件**
- チームが独立してデプロイしたい
- 特定コンポーネントだけスケールしたい（例：動画処理・ML推論）
- 障害をサービス単位で隔離したい

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ設定が多い） |
| スケール | 全体のみ | 部分スケール可能 |
| 障害範囲 | 1つで全体影響 | 独立して隔離可能 |
| 運用コスト | 低い | 高い |
| チーム自律性 | 低い（コンフリクト多） | 高い（独立所有権） |

FastAPI + Cloud Run の文脈では、まず **1つの Cloud Run サービスとして構築**し、モジュール境界を明確にしてから必要に応じてサービス分割するのが現実解。分割後のサービス間通信は Cloud Pub/Sub or Cloud Run 内部URLで実施。
