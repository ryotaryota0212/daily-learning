# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか」は多くのチームが直面する判断だが、**正解はチームの規模・ドメインの複雑さ・デプロイ頻度**によって変わる。
モノリスを「古い設計」と思い込んでマイクロサービスに移行した結果、分散システムの複雑さに潰されるチームは多い。
AI時代においては「何を選ぶか」より「なぜそれを選ぶか・いつ変えるか」を説明できることが重要。

---

## 仕組みの要点

### モノリスの特性
- 全機能が1プロセスで動く。デプロイは1回、デバッグは簡単
- トランザクションがシンプル（DBのACIDを素直に使える）
- チームが小さい（〜10人）うちは生産性が高い
- スケールするとき：**全体を一緒にスケール**するしかない

### マイクロサービスの特性
- 機能ごとに独立したサービス＋DBを持つ
- チームが独立してデプロイできる（Conway's Law との整合）
- 障害が局所化されやすい（1サービスが落ちても全体に波及しない）
- 代償：**分散システムの複雑さ**（ネットワーク遅延・整合性・オーケストレーション）

### 判断軸（3つの問い）
1. **チーム規模**：Amazonの「ピザ2枚ルール」〜8人/サービスが目安。10人未満ならモノリス
2. **デプロイ独立性**：「決済だけ1日10回デプロイしたい」ならサービス分割の動機になる
3. **スケール特性**：「検索だけ100倍のトラフィックが来る」なら部分スケールが必要

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービス（開発初期） | モノリスから始め、境界が見えたら分割 |
| サービス間でDBを共有する | サービスごとにDBを所有（データは APIで取得） |
| 同期HTTPで全サービスを数珠つなぎ | 非同期メッセージ（Pub/Sub）で疎結合化 |
| デプロイパイプラインが1本のまま | サービスごとに独立したCI/CDを整備 |
| 「マイクロ」すぎる分割（関数レベル） | ドメイン境界（Bounded Context）で分割 |

## 移行戦略：Strangler Fig パターン

モノリスを壊さずに段階的に剥がす手法。

```
[クライアント]
    |
[APIゲートウェイ / Cloudflare]
    |                    |
[既存モノリス]    [新サービス（Cloud Run）]
    |
  [Neon DB]        [新サービス専用DB]
```

**ステップ**
1. APIゲートウェイ（Cloudflare Workers）をフロントに置く
2. 分割したい機能を新サービス（Cloud Run）で実装
3. ゲートウェイのルーティングを新サービスに切り替え
4. モノリス側の該当コードを削除
5. 繰り返し → モノリスが空になったら完了

# FastAPI + Firebase Auth でサービス間認証

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備コスト大） |
| デプロイリスク | 全体に波及 | 局所化できる |
| 障害調査 | ログが一か所 | 分散トレーシングが必要 |
| トランザクション | ACIDで簡単 | Sagaパターン等が必要 |
| チームスケール | 10人超で摩擦増 | チームごとに独立できる |
| クラウドコスト | 安い（1サービス） | サービス数×管理コスト |

**FastAPI + Cloud Run スタックでの現実的な指針**
- スタートアップ・個人開発：**モノリスで十分**。Cloud Runは1コンテナで水平スケールできる
- 機能単位で「デプロイ頻度が違う」「チームが別」になった時点で分割を検討
- 分割の単位は「ドメイン境界」（認証・決済・通知 等）であり、技術レイヤーではない
