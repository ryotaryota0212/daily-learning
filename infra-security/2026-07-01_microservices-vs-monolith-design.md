# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにしたい」は技術的な憧れで選ばれやすいが、多くのチームにとってモノリスの方が正解。  
AI時代のエンジニアに求められるのは「どちらが流行か」ではなく「今のチームとシステムにどちらが合うか」を判断する力。  
誤った分割は、デプロイ複雑性・ネットワーク障害・データ整合性問題を一気に抱える。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ単位・単一DB・シンプルなローカル関数呼び出し
- 開発初期は圧倒的に速い
- トランザクションが自然に使える
- スケールはアプリ全体を複製（Cloud Runなら十分対応可）

### マイクロサービスの特性
- サービスごとに独立デプロイ・独立DB
- チームが大きく、サービス境界がチーム境界と一致するとき真価を発揮（Conway's Law）
- ネットワーク呼び出しになるため遅延・障害リスクが上がる
- データ整合性はEventual Consistencyで設計が必要

### 判断の基準（どちらを選ぶか）

| 判断軸 | モノリス有利 | マイクロサービス有利 |
|--------|------------|-----------------|
| チーム規模 | 〜10人 | 20人以上・複数チーム |
| デプロイ頻度 | 週次程度 | サービス単位で独立して週複数回 |
| スケール要件 | 機能ごとの差が小さい | 特定機能だけ激しいトラフィック |
| ドメイン境界 | 不明確・変化中 | 明確に分離できている |

---

## アンチパターン vs 正しい設計

### アンチパターン
- 「マイクロサービスの方がモダンだから」で分割 → 分散モノリス化
- 1サービスが別サービスのDBを直接参照 → 結合度は上がりデプロイ独立性は失われる
- サービス間の同期HTTP呼び出しの連鎖 → 1箇所の障害が全体に伝播
- 10人以下のチームで5つ以上のマイクロサービス → 運用コストで開発が止まる

### 正しい設計
- まずモノリスで作り、**ボトルネックが明確になったら**分割する（"Monolith First"）
- 分割するならドメイン境界（DDD Bounded Context）で切る
- サービス間通信は非同期（Pub/Sub）を優先し、同期は最小限に
- 各サービスは独自DBを持ち、他サービスのDBには触らない

## コード/設計例（FastAPI + Cloud Run）

```python
# モノリス段階：内部モジュール境界を明確にしておく
# app/domains/orders/service.py
class OrderService:
    def create_order(self, user_id: str, items: list) -> Order:
        # 将来マイクロサービス化するとき、ここが境界になる
        inventory = self.inventory_repo.check(items)
        order = self.order_repo.create(user_id, items)
        self.notification_repo.enqueue(order.id)  # 非同期キューへ
        return order

# 分割後：サービス間はHTTPではなくPub/Subで通信
# Cloud Run + Cloud Pub/Sub
def on_order_created(event: dict):
    """通知サービス側のサブスクライバー"""
    order_id = event["order_id"]
    send_notification(order_id)
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|------|---------|--------------|
| 開発速度（初期） | 速い | 遅い |
| スケール柔軟性 | 低い | 高い |
| 障害の局所化 | 難しい | しやすい |
| 運用複雑性 | 低い | 高い（監視・デプロイ・ネットワーク） |
| データ整合性 | 強い（ACID） | 弱い（Eventual） |

**Cloud Run採用時の補足：** モノリスでも Cloud Run のオートスケールで水平スケールは対応できるため、「スケールのためにマイクロサービスが必要」は多くの場合誤り。

- [ ] サービス間の同期HTTP連鎖を避け、非同期Pub/Subを使っているか
- [ ] 各マイクロサービスが独自DBを持ち、他のDBを直接参照していないか
- [ ] 分割の理由が「流行」ではなく「スケール要件 or チーム境界」になっているか
