# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」は多くのチームが誤った理由で答えを出す問題。
Netflixがマイクロサービスだからといって、5人チームのプロダクトに適用するのは誤り。
アーキテクチャの選択は「スケールの必要性」「チームサイズ」「障害の影響範囲」で決まる。
AI時代においてこの判断を誤ると、無駄な複雑性で開発速度を大幅に落とす。

---

## 仕組みの要点

### モノリス（Monolith）

- 全機能が1プロセスで動く。デプロイ単位が1つ
- DB接続・関数呼び出しで内部連携 → レイテンシ低
- 開発・テスト・デバッグが単純
- 欠点：スケールの単位が粗い、デプロイ1回でシステム全体が影響を受ける

### マイクロサービス（Microservices）

- 機能ごとに独立したプロセス・DB・デプロイ
- チーム間の独立性が高い（組織構造と対応させる）
- 欠点：ネットワーク越しの通信、分散トレーシング、サービス間認証、データ整合性が複雑になる

### モジュラーモノリス（中間解）

- 1プロセスだが、内部をモジュール（ドメイン）で明確に分割
- 将来のマイクロサービス分割への準備として最適
- 多くの場合、これが正解

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 流行だからマイクロサービスを採用 | チームサイズ・スケール要件から判断 |
| 最初からマイクロサービスで設計 | まずモノリスで作り、境界が見えてから分割 |
| 全サービスが同一DBを共有 | サービスごとにDBを持つ（DBまで分離して初めてマイクロサービス） |
| 同期HTTP呼び出しで強結合 | 非同期イベント駆動で疎結合を維持 |
| マイクロサービス化 = コンテナ化と誤解 | 独立デプロイ・独立スケールこそが本質 |

---

## 判断フレームワーク

### モノリスを選ぶべき条件

- チームが10人以下
- プロダクトがまだPMFを探っている段階
- ドメインの境界がまだ不明確
- Cloud Run 1サービスで十分スケールできる（→ たいていの場合これで足りる）

### マイクロサービスを選ぶべき条件

- チームが独立して異なるサービスをデプロイしたい（Conway's Law）
- 特定機能だけ極端にスケールが必要（例：画像処理だけGPUが必要）
- 異なる技術スタックが必要な理由がある
- SLAが機能ごとに異なる（決済はゼロダウン、それ以外は多少許容）

## 設計例：FastAPI + Cloud Run でのモジュラーモノリス

```
app/
  main.py              # エントリポイント
  routers/
    auth.py            # 認証ドメイン
    users.py           # ユーザードメイン
    billing.py         # 課金ドメイン
  services/
    auth_service.py    # ドメインロジック（外部依存なし）
    billing_service.py
  repositories/
    user_repo.py       # DB操作のみ
```

```python
# 境界を守る原則：ドメイン間は直接インポートしない
# BAD: billing_service から user_repo を直接使う
# GOOD: user情報はAPIレスポンス経由か、共有の読み取り専用モデルで参照
```

→ このまま Cloud Run 1サービスとしてデプロイ。

## 移行戦略（モノリス → マイクロサービス）

### Strangler Fig パターン（最も安全）

1. モノリスの前にAPIゲートウェイ（Cloudflare / Cloud Run）を置く
2. 分離したいドメインを新サービスとして実装
3. APIゲートウェイのルーティングで新サービスに切り替え
4. 旧モノリスから該当コードを削除

```
Before: Client → Monolith
After:  Client → Gateway → [新サービス(billing)] or [モノリス(other)]
```

### データ分離の手順（最難関）

1. まずコードを分離（DBは共有のまま）
2. 共有テーブルを新サービス専用DBにコピー（二重書き込み期間を設ける）
3. 読み取りを新DBに切り替え
4. 旧DBの該当テーブルを削除

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備が必要） |
| 障害の影響範囲 | 全体 | 局所化できる（設計次第） |
| デプロイの独立性 | 低い | 高い |
| 運用コスト | 低い | 高い（分散トレーシング等が必要） |
| スケールの柔軟性 | 粗い | 細かい |

**FastAPI + Cloud Run の場合：**
Cloud Run は1サービスでも同時実行数・インスタンス数を柔軟にスケールできる。
多くのスタートアップはモジュラーモノリス + Cloud Run で十分。

## チェックリスト

- [ ] チームが10人以上か、または独立デプロイの必要性が明確か確認した
- [ ] ドメイン境界（Bounded Context）をコード内部で明確に分けているか
- [ ] サービス分割するなら、DBも分離する計画があるか
- [ ] 分散トレーシング（Cloud Trace）・サービス間認証（Cloud Run IAM）の準備があるか
- [ ] まずモジュラーモノリスで始め、境界が固まってから分割する方針か
