# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき」という圧力に負けてモノリスを早期分割すると、分散システムの複雑さだけが増して開発速度が落ちる。AI時代のエンジニアに求められるのは「いまどちらが正しいか」を状況から判断し、段階的に移行できる設計力。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ・単一プロセス。開発初期は最速
- トランザクション・一貫性の担保がシンプル
- デバッグ・ローカル実行が容易
- チームが小さいうちは「コード修正→即反映」の速度が出る

### マイクロサービスの特性
- サービスごとに独立デプロイ・スケール可能
- 障害が局所化しやすい（ただし分散障害は複雑化）
- チーム間の境界が明確になる（Conway's Law）
- 必要な複雑さ：サービス間通信・分散トレーシング・Saga/補償トランザクション

---

## 判断基準

| 観点 | モノリスが正解 | マイクロサービスが正解 |
|------|--------------|----------------------|
| チーム規模 | ~10名 | 複数チームが独立して動く |
| デプロイ頻度 | 週1〜月1 | サービスごとに独立してデプロイしたい |
| スケール要件 | 均一なトラフィック | 特定機能だけ高負荷 |
| ドメイン境界 | 不明確・変化中 | 明確で安定している |
| 運用成熟度 | 少ない | K8s・サービスメッシュを運用できる |

**原則：ドメイン境界が安定するまでモノリスで正解。**

---

## アンチパターン vs 正しい設計

### アンチパターン
- 最初からマイクロサービスで始める（"Distributed Monolith"になりがち）
- 機能単位ではなく技術レイヤー単位で分割（frontend/backend/db サービス等）
- サービス間で DB を共有する（結合度が下がらない）
- 同期HTTP呼び出しを連鎖させる（障害が伝播、レイテンシ増大）

### 正しい設計
- 最初はモジュラーモノリス（境界を内部で持ち、後で切り出せる構造）
- 分割単位は「ビジネスケイパビリティ」（DDD の Bounded Context）
- サービスごとに独立した DB を持つ
- 非同期イベント（Pub/Sub）で疎結合に保つ

## 移行パターン：Strangler Fig

```python
# FastAPI でのモジュラーモノリス例（後で分割しやすい構造）
# app/
#   routers/
#     orders.py   ← Orderドメイン
#     users.py    ← Userドメイン
#   services/
#     order_service.py
#     user_service.py

# ルーターを独立して登録 → 将来的に別サービスへ切り出し可能
from fastapi import FastAPI
from app.routers import orders, users

app = FastAPI()
app.include_router(orders.router, prefix="/orders")
app.include_router(users.router, prefix="/users")

# Cloud Run では各ルーターを別サービスとしてデプロイするだけで分割完了
```

**移行手順（Strangler Fig）：**
1. モノリス内に明確なモジュール境界を作る
2. 新機能は新サービスとして追加
3. 既存機能を順次切り出し（トラフィックをルーティング層で切り替え）
4. 旧コードを枯らす

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|------|--------|---------------|
| 開発速度（初期） | 速い | 遅い |
| 開発速度（大規模） | 遅くなる | チームが独立できれば速い |
| 運用コスト | 低 | 高（監視・デプロイ複雑化） |
| 障害影響範囲 | 広い | 局所化できるが分散障害は複雑 |
| データ一貫性 | 容易 | Saga/補償が必要 |

**Cloud Run + FastAPI の場合：** サービスをコンテナ単位で分けるだけでマイクロサービス化できるため、移行コストは比較的低い。ただし Firebase Auth トークン検証・Neon DB 接続管理を各サービスで持つ設計が必要。

## チェックリスト

- [ ] ドメイン境界（Bounded Context）が安定しているか確認してから分割
- [ ] サービス間通信は同期 vs 非同期の選択を意識的に行う
- [ ] DB は必ずサービスごとに分離（共有 DB は絶対に避ける）
- [ ] まずモジュラーモノリスで境界を内部に作る
- [ ] 分散トレーシング（Cloud Trace 等）なしでマイクロサービスに移行しない
