# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき？」という問いは、AI時代においても設計判断の根幹を問う。誤った分割は「分散モノリス」という最悪の構成を生む。重要なのはトレードオフを正確に理解し、チームとシステムの状況に応じて選ぶ力。正解は「小さく始めてモノリス、必要になったら分割」が9割のケースで正しい。

---

## 仕組みの要点

### モノリスの特徴
- 単一デプロイ単位。全機能が1プロセス
- DB共有が前提、トランザクションが容易
- 開発速度が速い（サービス間通信不要）
- スケールは全体一括（部分的スケールが困難）

### マイクロサービスの特徴
- 各サービスが独立してデプロイ・スケール可能
- サービス間はネットワーク通信（REST/gRPC/Pub/Sub）
- 障害の影響範囲を局所化できる
- 組織とアーキテクチャを合わせやすい（Conway's Law）

### コンウェイの法則（最重要）
> 「システムの構造はそれを設計する組織のコミュニケーション構造を反映する」

チームが3人なのにマイクロサービスを選ぶのは、組織構造との不一致。**チーム数 ≒ サービス数**が持続可能な比率。

---

## アンチパターン vs 正しい設計

### アンチパターン：分散モノリス
```
サービスA ─── DB共有 ─── サービスB ─── DB共有 ─── サービスC
               ↑
     サービス間で同じDBテーブルを読み書き
     → デプロイが連鎖、障害が連鎖
```
- サービスを分けたのにDBを共有している
- サービスAの変更がサービスBのデプロイを強制する
- ネットワーク遅延だけ増えて分散のメリットゼロ

### 正しい設計：ドメイン境界で分割
```
サービスA(users) ── DB-A    サービスB(orders) ── DB-B
      ↑ 非同期イベント(Pub/Sub) ↓
    それぞれが独自のDBを所有
    サービス間はAPIかイベントのみ
```

## 判断基準フレームワーク

### モノリスを選ぶべき状況
| 条件 | 理由 |
|------|------|
| チームが10人以下 | 調整コストが開発速度を上回る |
| ドメイン境界が不明瞭 | 誤った分割は後で高コストに |
| スタートアップ期 | 速度優先、設計の正解が未確定 |
| トランザクション整合性が必須 | 分散トランザクションは複雑 |

### マイクロサービスを選ぶべき状況
| 条件 | 理由 |
|------|------|
| チームが独立してデプロイしたい | 組織の自律性が必要 |
| 機能ごとにスケール要件が異なる | 動画変換だけ大量リソースが必要など |
| 技術スタックを変えたい部分がある | 特定機能だけRustで書きたいなど |
| 障害の影響範囲を限定したい | 決済が落ちても閲覧は続けたい |

## コード/設計例：FastAPI でのサービス間通信

```python
# 非同期イベント経由（推奨）：サービスを疎結合に保つ
import httpx
from google.cloud import pubsub_v1

# ❌ 同期HTTP呼び出し（密結合・障害連鎖リスク）
async def create_order_bad(user_id: str):
    async with httpx.AsyncClient() as client:
        user = await client.get(f"http://user-service/users/{user_id}")
        # user-serviceが落ちたらorder-serviceも死ぬ

# ✅ Pub/Sub経由（疎結合・障害非連鎖）
def create_order_good(order_data: dict):
    publisher = pubsub_v1.PublisherClient()
    topic = "projects/my-project/topics/order-created"
    publisher.publish(topic, data=str(order_data).encode())
    # user-serviceが落ちていても注文は受け付けられる
```

## モノリスからマイクロサービスへの移行戦略

### ストラングラーフィグパターン（推奨）
1. モノリスの前にAPIゲートウェイを置く
2. 新機能は新サービスに追加
3. 既存機能を少しずつ新サービスに移行
4. モノリスが空になったら廃止

```
Before: クライアント → モノリス
After:  クライアント → APIゲートウェイ → 新サービスA
                                         → 旧モノリス（縮小中）
```

### 移行の順序
- **先に分離しやすいもの**: 認証、通知、ファイルアップロード
- **後回しにすべきもの**: コアビジネスロジック、トランザクション境界

## チェックリスト

- [ ] チーム規模とサービス数が対応しているか（小チーム＝モノリス）
- [ ] DBを複数サービスで共有していないか（分散モノリス検出）
- [ ] サービス間通信を同期HTTPに依存しすぎていないか
- [ ] ドメイン境界が明確に定義されているか（境界曖昧＝分割しない）
- [ ] 移行はストラングラーフィグで段階的に行えているか
