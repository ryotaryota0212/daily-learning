# マイクロサービス vs モノリス：判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」は多くのチームが直面する設計判断。しかし**マイクロサービスはデフォルト選択ではない**。組織・チーム規模・ドメインの複雑さを無視して分割すると、運用コストが爆発する。AI時代においてこそ「なぜ分けるか」をトレードオフとともに説明できる力が問われる。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ単位。開発・デバッグ・テストがシンプル
- トランザクションが1DBで完結し、データ整合性を保ちやすい
- チームが小さいほどモノリスの方が生産性が高い
- 境界が曖昧になると「泥団子モノリス（Big Ball of Mud）」化する

### マイクロサービスの特性
- サービス単位でスケール・デプロイ・技術選択を独立できる
- チーム間の独立性（コンウェイの法則）が大規模組織の生産性を上げる
- ネットワーク通信・分散トランザクション・サービスディスカバリの複雑さが増す
- **最低でも5〜10チームが存在して初めてメリットが出る**

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい判断 |
|---|---|
| 「スケールするかも」でマイクロサービス採用 | モノリスから始め、ボトルネックが明確になってから分割 |
| ドメイン設計なしにCRUDエンドポイントで分割 | DDD（境界づけられたコンテキスト）でドメインを先に定義 |
| 複数サービスが共有DBを使う | サービスごとにDBを独立させる（疎結合の原則） |
| 「マイクロ」を追求して全部サービス化 | コアドメインのみ分離し、周辺はモジュラーモノリスに留める |

---

## 設計例：段階的移行パターン（Strangler Fig）

モノリス内でドメイン境界をモジュールとして明示しておき、後からサービスとして切り出す。

```python
# モノリス内に「将来のサービス境界」をモジュールで明示
# src/users/router.py  ← 将来独立するドメイン
from fastapi import APIRouter
router = APIRouter(prefix="/users", tags=["users"])

# src/orders/router.py  ← 別ドメイン
from fastapi import APIRouter
router = APIRouter(prefix="/orders", tags=["orders"])

# main.py: まず統合、後で分離
app.include_router(users.router)
app.include_router(orders.router)
# 分離時: Cloud Run に別サービスとしてデプロイし、
#         API Gateway でルーティングを切り替えるだけ
```

**ポイント：** モジュール境界が明確なら、分離コストは最小限。最初から「疎結合なモノリス」を作るのがベスト。

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ設定に工数） |
| スケーラビリティ | 全体一括 | サービス単位で最適化可能 |
| 障害範囲 | 全体に波及しやすい | サービス単位で局所化可能 |
| 運用コスト | 低い | 高い（監視・デプロイが複数） |
| データ整合性 | 単一DBで保証しやすい | 分散トランザクション（Saga等）が必要 |
| 適したチーム規模 | 小〜中規模 | 大規模（複数チーム） |

---

## Cloud Run での実践

- **モノリス段階：** 1つの Cloud Run サービスに FastAPI アプリ全体をデプロイ
- **分離時：** サービスごとに Cloud Run サービスを作り、VPC Connector + IAM で内部通信を制限
- **Neon（PostgreSQL）：** 分割後は Neon の複数DBまたはスキーマ分離でデータを独立させる
- **Firebase Auth：** サービス間でも同じIDトークンを検証することで認証基盤を共有できる
