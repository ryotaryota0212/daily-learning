# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき」という圧力は常にある。しかし多くのプロジェクトで、マイクロサービスは問題を解決するより増やす。判断基準は「今のチームとシステムで何が壊れているか」であり、アーキテクチャは手段に過ぎない。AI時代においても、構成の複雑さはデバッグコスト・デプロイコスト・認知負荷に直結するため、シンプルさの価値を正しく見積もる力が問われる。

---

## 仕組みの要点

### モノリスの特徴
- 単一プロセス・単一デプロイ単位
- 関数呼び出しで内部通信 → レイテンシゼロ・トランザクション容易
- 開発初期のスピードが最速
- 問題：スケールの粒度が粗い、デプロイが全体に影響、チームが大きくなるとコード競合増

### マイクロサービスの特徴
- 独立プロセス・独立デプロイ単位
- ネットワーク越しの通信（REST/gRPC/メッセージキュー）
- チームごとの独立した開発・リリースが可能
- 問題：分散トランザクション困難、障害箇所が増える、オーバーヘッドが大きい

### モジュラーモノリス（中間形態）
- 単一デプロイだがコード上は明確にモジュール分離
- 将来のマイクロサービス分割への布石として有効
- 多くのプロジェクトでベストな選択肢

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで始める | モノリスで始めて、分割の必要が出たら分ける |
| チームなし・ユーザーなしでサービス分割 | チームの自律性が必要になったときに分割 |
| 全サービスが同一DBを共有 | サービスごとにDBを分離（サービス境界を守る） |
| 同期HTTP呼び出しの連鎖 | 非同期メッセージングで疎結合にする |
| 「マイクロサービス＝モダン」の思い込み | 問題を明確にしてから構成を選ぶ |

---

## 分割判断のフレームワーク

### 分割すべきシグナル
- **スケール要件が違う**：認証サービスは低負荷、画像処理は高負荷 → 別々にスケールしたい
- **デプロイ頻度が違う**：特定機能だけ週10回リリースしたい
- **チームが独立している**：2チーム以上が同じコードを頻繁に競合しながら編集している
- **技術スタックが違う必要がある**：ML処理はPython、Webは TypeScript

### 分割すべきでないシグナル
- チームが5人以下
- サービス間でトランザクション整合性が必要な処理が多い
- ユーザー数・負荷がまだ小さい
- 開発スピードを最大化したい段階

## 移行戦略（モノリス → マイクロサービス）

### Strangler Fig パターン（推奨）

```
[既存モノリス]
  ├── 機能A（そのまま）
  ├── 機能B（そのまま）
  └── 機能C → [新サービスCへ移行中]
              ↑
         APIゲートウェイで振り分け

手順:
1. APIゲートウェイを前段に置く
2. 新サービスを並行稼働させ、一部トラフィックを流す
3. 動作確認後、モノリス側の機能を削除
```

### FastAPI + Cloud Run での実践

```python
# メインサービス（モノリス）
# cloud_run_service: main-app

# 分割後: 通知サービスを別Cloud Runに切り出す
# cloud_run_service: notification-service

# main-app から notification-service を呼ぶ
import httpx
from google.auth.transport.requests import Request
from google.oauth2 import id_token

async def call_notification_service(user_id: str, message: str):
    token = id_token.fetch_id_token(Request(), NOTIFICATION_SERVICE_URL)
    async with httpx.AsyncClient() as client:
        await client.post(
            f"{NOTIFICATION_SERVICE_URL}/notify",
            json={"user_id": user_id, "message": message},
            headers={"Authorization": f"Bearer {token}"},
        )
```

## トレードオフ整理

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い |
| スケール柔軟性 | 粗い | 細かい |
| デプロイリスク | 全体影響 | 独立 |
| 障害影響範囲 | 全体 | 局所（ただし分散障害）|
| 運用コスト | 低い | 高い |
| チーム独立性 | 低い | 高い |

**Cloud Run での考慮**：サービスごとに独立してデプロイ・スケールできるため、マイクロサービスとの相性は良い。ただしサービス間通信はIDトークン認証必須（IAM設定漏れはセキュリティホール）。
