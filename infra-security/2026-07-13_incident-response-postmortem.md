# インシデント対応とポストモーテムの文化

## 概要

システムは必ず壊れる。問題はそれを「どう検知し、どう収束させ、どう再発を防ぐか」だ。
インシデント対応が体系化されていないチームは同じ障害を繰り返し、信頼を失う。
ポストモーテム（障害振り返り）は「犯人探し」ではなく「構造的な原因を取り除く」文化を根付かせる。
SRE（サイト信頼性エンジニアリング）の核心がここにある。

---

## 仕組みの要点

### インシデントの4フェーズ

| フェーズ | やること |
|---|---|
| 1. 検知 | アラートが上がる。誰かが気づく |
| 2. 対応（Triage） | 影響範囲を把握し、優先度を決める |
| 3. 収束（Mitigate） | 被害を止める（原因究明より先に） |
| 4. 復旧（Resolve） | 正常状態に戻す |

### 役割分担（ICS: Incident Command System）

- **IC（Incident Commander）**: 全体の指揮。他の人に作業を割り振る。自分では触らない
- **Ops Lead**: 実際に調査・修正するエンジニア
- **Comms Lead**: ステークホルダーへの状況報告担当
- IC が複数いると混乱する。1人に絞る

### 重要な原則

- **まず止める、後で直す**: ロールバックやトラフィック遮断が根本修正より速い
- **タイムライン記録**: Slackのスレッドなどに時刻付きでログを残す（振り返りに必須）
- **コミュニケーション過剰くらいがちょうどいい**: 沈黙は不安を生む

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 全員が同時にターミナルを触る | IC が一人に作業指示を出す |
| 原因を特定してから復旧する | まず収束（ロールバック）してから原因調査 |
| ポストモーテムで犯人を責める | Blame-Free: 「なぜそうなる構造があったか」を問う |
| 障害後に何もしない | Action Item を必ず出し、期限と担当者を決める |
| アラートが多すぎて慣れる（Alert Fatigue） | P1/P2/P3 で重要度を分け、P1は即人が対応 |

## 設計例：インシデント対応フロー（FastAPI + Cloud Run 想定）

```python
# Cloud Run + Cloud Monitoring でのアラート設定例（Terraform）
resource "google_monitoring_alert_policy" "high_error_rate" {
  display_name = "P1: Error rate > 5%"
  conditions {
    condition_threshold {
      filter          = "resource.type=\"cloud_run_revision\" AND metric.type=\"run.googleapis.com/request_count\""
      aggregations {
        per_series_aligner = "ALIGN_RATE"
      }
      comparison = "COMPARISON_GT"
      threshold_value = 0.05
      duration = "60s"
    }
  }
  notification_channels = [google_monitoring_notification_channel.pagerduty.name]
}
```

### ポストモーテムの構成（テンプレート）

```
# Postmortem: [タイトル] YYYY-MM-DD

## Summary
- 影響期間: XX:XX ~ XX:XX（XX分）
- 影響範囲: 本番ユーザーの XX% が XX機能を利用不可

## Timeline
- 14:00 アラート発報
- 14:05 ICがアサイン、調査開始
- 14:20 原因特定（Cloud Run のメモリ不足）
- 14:25 インスタンスメモリを 512MB → 1GB に変更、ロールバック
- 14:30 復旧確認

## Root Cause
Neon DB の接続プールが枯渇。同時リクエストが急増した際に
コネクション待機が蓄積し、タイムアウトが連鎖した。

## Action Items
| 対策 | 担当 | 期限 |
|---|---|---|
| DB接続プールサイズの上限設定を追加 | @tanaka | 7/20 |
| 接続待機時間のメトリクスをダッシュボードに追加 | @sato | 7/15 |
```

---

## トレードオフ

| 観点 | 内容 |
|---|---|
| **収束速度 vs 原因調査** | ロールバックは速いが「なぜ壊れたか」は後回しになる。許容できる場合はロールバック優先 |
| **Alert の感度** | 感度を上げると誤報が増え疲弊する。感度を下げると検知が遅れる |
| **Blame-Free 文化** | 責任を問わないと学習できる。ただし重大な怠慢は別途対処が必要 |
| **ポストモーテムのコスト** | 全障害に実施すると工数大。P1/P2のみ必須とし、P3は任意とするのが現実的 |
