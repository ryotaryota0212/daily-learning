# マイクロサービス vs モノリス：判断基準と移行戦略

## 概要

AI時代において「とりあえずマイクロサービス」という選択は最悪の出発点になりうる。
分散システムの複雑性（ネットワーク障害・分散トランザクション・サービス間認証）はモノリスの複雑性とは次元が違う。
最初の正しい問いは「なぜ分割するのか？」であり、スケーラビリティ・チームサイズ・デプロイ頻度の要件から逆算して決める。
FastAPI + Cloud Run + Neon のスタックでは「モジュラーモノリス」が多くの場合最適解になる。

---

## 仕組みの要点

### モノリスの特徴
- 単一デプロイ単位。全機能が1プロセス内
- DBはスキーマで共有 → トランザクションが簡単
- ローカル関数呼び出し → レイテンシゼロ、デバッグ容易
- チーム小規模（〜10人）では開発速度が最速

### マイクロサービスの特徴
- サービスごとに独立デプロイ・スケール
- DBも原則サービスごとに分離 → 結果整合性が必要になる
- サービス間通信はHTTP/gRPC → ネットワーク障害を常に想定
- Conway の法則：組織構造がシステム構造を決める

### モジュラーモノリス（中間解）
- 単一デプロイだがコード上のモジュール境界が明確
- DBはスキーマ分離（同一DBサーバー内でスキーマを分ける）
- 後からマイクロサービスに分割しやすい状態を保つ
- Cloud Run のオートスケールで単一サービスでも十分スケールする

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービス | モノリスから始め、明確な分割理由ができたら移行 |
| 機能単位で分割（UserService / OrderService） | **ビジネスドメイン境界**（Bounded Context）で分割 |
| 共有DBをマイクロサービスで使い回す | サービスごとにDB分離。どうしても共有するなら読み取り専用レプリカ |
| 同期HTTP呼び出しでサービスを数珠つなぎ | 非同期メッセージング（Pub/Sub）で疎結合に |
| モノリスを「レガシー」と呼んで捨てる | ストラングラーフィグパターンで段階移行 |

---

## 判断基準フレームワーク

### モノリスを選ぶ条件（多くのスタートアップはここ）
- チームが10人以下
- ドメイン境界がまだ明確でない（プロダクト探索中）
- デプロイ頻度が週数回以下
- 単一チームが全機能を所有している

### マイクロサービスを検討する条件（すべて満たすなら）
- 独立してスケールしたい機能がある（例：動画変換だけ重い）
- 別チームが別サービスを独立デプロイしたい
- 言語/フレームワークをサービスごとに変えたい理由がある
- SLAが機能ごとに異なる（決済は99.99%、通知は99%等）

## コード/設計例：モジュラーモノリスの構造

```
# FastAPI モジュラーモノリスの推奨ディレクトリ構造
app/
  modules/
    users/          # ユーザーモジュール（境界明確）
      router.py     # APIルート
      service.py    # ビジネスロジック
      repository.py # DB操作（このモジュールのテーブルのみ触る）
      schemas.py
    orders/         # 注文モジュール（usersに依存しない設計）
      router.py
      service.py
      repository.py
  shared/           # 共通ユーティリティ（DBセッション、認証など）
    database.py
    auth.py
  main.py
```

**DB分離の方針（Neon PostgreSQL）:**
```sql
-- 同一DBだがスキーマを分離してモジュール境界を強制
CREATE SCHEMA users;
CREATE SCHEMA orders;
-- orders スキーマから users テーブルへの直接JOINを禁止
-- 必要ならAPIレイヤー経由でデータ取得（後の分割を容易に）
```

## ストラングラーフィグパターン（段階移行）

```
[現状] モノリス → 全トラフィック
         ↓
[Step1] 新機能のみ新サービスで実装（モノリスは既存機能を保持）
         ↓
[Step2] Cloud Run + Cloudflare でルーティング分岐
         ↓
[Step3] 旧機能を新サービスに移植し、モノリスから削除
         ↓
[完了] モノリスが消えるか、コアドメインだけ残る
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ設定コスト大） |
| スケーラビリティ | 全体一括スケール | 機能単位でスケール可能 |
| 障害の影響範囲 | 全体に波及しやすい | 局所化できる（設計次第） |
| デバッグ難易度 | 低い | 高い（分散トレーシング必須） |
| チーム独立性 | 低い（衝突しやすい） | 高い |
| インフラコスト | 低い | 高い（サービス数×Cloud Runコスト） |

**Cloud Run における注意点：**
- モノリスでも Cloud Run は最小インスタンス数=0 にすればコスト最適
- マイクロサービス化すると各サービスのコールドスタートが独立して発生
- サービス間通信は Cloud Run の内部URLを使い、外部公開しない
