# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」は最もよく議論される設計判断の一つ。しかし多くのチームがスケールや複雑さを過小評価してマイクロサービスを選び、後悔する。AI時代においては「正解の構成」より「今のチームと規模に合った構成を選び、説明できる力」が問われる。

---

## 仕組みの要点

### モノリス
- 全機能が1つのプロセス/デプロイ単位に集まる構成
- DBも基本的に1つ。テーブル間のJOINが容易
- デプロイ・テスト・デバッグがシンプル
- 欠点：1つのバグが全体に影響、スケールが機能単位でできない

### マイクロサービス
- 機能ごとに独立したサービスとして分割
- サービス間はAPI（HTTP/gRPC）またはメッセージキューで通信
- 独立デプロイ・独立スケールが可能
- 欠点：分散システムの複雑さ（ネットワーク遅延、障害伝播、データ整合性）

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで始める | モノリスで始めて境界が明確になったら分割 |
| チームが小さいのにサービスを増やす | サービス数 ≈ チーム数（Conway's Law） |
| 共有DBを複数サービスが直接参照 | サービスごとにDBを持ち、APIでのみ連携 |
| 全部を分散トランザクションで解決しようとする | Sagaパターン or 結果整合性を受け入れる |
| マイクロサービス化 = 現代的、という思い込み | 問題の規模に合った構成を選ぶ |

---

## 判断基準フレームワーク

### モノリスを選ぶべき状況
- チーム規模が5名以下
- プロダクトがまだProduct-Market Fitを探している段階
- ドメイン境界がまだ不明確
- 初期スタートアップ（スピードが最優先）

### マイクロサービスを検討する条件（全て満たすこと）
- チームが複数あり、独立してデプロイしたい
- 機能ごとにスケール要件が大きく異なる
- ドメイン境界が明確に定義できている
- インフラ・監視の運用コストを吸収できる体制がある

---

## 移行戦略：Strangler Fig パターン

```
[Before]
  モノリス (FastAPI)
  └── /users, /orders, /payments, /notifications 全部ここ

[Step 1] 新サービスを追加し、ルーティングだけ切り替え
  Cloud Run (Router / API Gateway)
  ├── /notifications → 新規: notifications-service
  └── それ以外 → 既存モノリス（そのまま）

[Step 2] 残りも境界が明確な順に切り出す
  ├── /payments → payments-service (PCI-DSS分離の理由もある)
  └── /users, /orders → モノリスのまま維持（無理に分けない）
```

**ポイント：** 全部一度に移行しない。最も独立性が高く、分離の恩恵が大きい部分から始める。

## Cloud Run + FastAPI でのサービス間認証

```python
# サービスAがサービスBを呼ぶ際、Cloud Run のサービスアカウントトークンを使う
import google.auth.transport.requests
import google.oauth2.id_token

async def call_service_b(endpoint: str, payload: dict):
    auth_req = google.auth.transport.requests.Request()
    token = google.oauth2.id_token.fetch_id_token(auth_req, endpoint)
    headers = {"Authorization": f"Bearer {token}"}
    async with httpx.AsyncClient() as client:
        return await client.post(endpoint, json=payload, headers=headers)
```

**注意：** サービス間通信はIAM + IDトークンで保護。JWTを手作りしない。

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備が先） |
| デプロイ独立性 | なし | あり |
| 障害の影響範囲 | 全体 | サービス単位（ただし連鎖障害のリスク） |
| データ整合性 | 容易（同一DB） | 困難（分散トランザクション） |
| 運用コスト | 低い | 高い（監視・サービスメッシュ等） |
| 組織との適合性 | 小チーム向き | 複数チーム向き |

## チェックリスト

- [ ] チーム規模と組織構造に合った構成を選んでいるか（Conway's Law を意識）
- [ ] 分割する場合、ドメイン境界が明確に説明できるか
- [ ] サービス間通信の認証・認可が設計されているか（IAMトークン等）
- [ ] 障害時の連鎖（カスケード障害）を防ぐ設計があるか（タイムアウト、サーキットブレーカー）
- [ ] 移行は段階的（Strangler Fig）で、全部一度に切り替えていないか
