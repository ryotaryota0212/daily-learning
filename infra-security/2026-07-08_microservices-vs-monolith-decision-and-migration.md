# マイクロサービス vs モノリス：判断基準と移行戦略

## 概要

「マイクロサービスにすべき？」はAI時代でも頻出の設計判断。  
答えは「チームとシステムの規模次第」だが、判断を誤ると**不必要な複雑性**を抱えて開発速度が激減する。  
重要なのは「どっちが正しいか」ではなく「今の自分たちに合っているか」を説明できること。  
FastAPI + Cloud Run スタックでは、モノリスから始めてサービス分割する段階的アプローチが現実的。

---

## 仕組みの要点

### モノリス
- 単一デプロイ単位。全機能が1つのプロセスで動く
- 開発初期は**圧倒的にシンプル**。DB共有、関数呼び出し、トランザクションが自然
- スケーリングは「全体を増やす」のみ（粒度が粗い）
- チームが小さいうちは最適解になりやすい

### マイクロサービス
- 機能単位で独立デプロイ・スケールできる
- サービス間はHTTP/gRPC/メッセージキューで通信
- **分散システムの複雑性**（ネットワーク遅延、部分障害、データ整合性）が必ず発生する
- Conway's Law：組織構造がシステム構造を決める

### 分割の正しい単位
- **境界づけられたコンテキスト（DDD）**：ビジネスドメインの自然な境界で切る
- データが本当に独立できるか確認（JOINが必要 → 分割コストが高い）

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービス | モノリスから始め、ボトルネックが見えたら分割 |
| 技術レイヤーで分割（DB層、API層） | ビジネスドメインで分割（注文、決済、ユーザー） |
| 同期API呼び出しの連鎖 | 非同期メッセージで疎結合に |
| 分散モノリス（データは共有DB） | サービスごとにDBを持つ |
| マイクロサービス = スケールする | スケールはインフラ設計の問題。モノリスでもCloud Runで十分スケールする |

## 設計例：モジュラーモノリス（推奨スタート地点）

```python
# FastAPI + Cloud Run：機能をモジュールで分けつつ単一デプロイ
# app/
# ├── main.py
# ├── modules/
# │   ├── users/    (router, service, repository)
# │   ├── orders/   (router, service, repository)
# │   └── payments/ (router, service, repository)

# main.py
from fastapi import FastAPI
from app.modules.users.router import router as users_router
from app.modules.orders.router import router as orders_router

app = FastAPI()
app.include_router(users_router, prefix="/users")
app.include_router(orders_router, prefix="/orders")
# → 後でサービス分割するときはrouterをそのまま別サービスへ移植
```

分割の判断基準：
- **デプロイ頻度が違う**（注文は毎日、請求は月次）→ 分割の候補
- **スケール要件が違う**（画像処理だけCPUが重い）→ 分割の候補
- **チームが独立して動きたい**（5人×3チームに成長）→ 分割の候補

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ・通信設計が必要） |
| 障害の影響範囲 | 全体 | 局所化できる（ただし分散障害が難しい） |
| データ整合性 | トランザクションで簡単 | 分散トランザクション（Saga等）が必要 |
| スケーリング粒度 | 粗い | 細かい（コスト最適化できる） |
| 運用コスト | 低い | 高い（サービスDiscovery、可観測性が必要） |
| 向いている段階 | MVP〜PMF | チーム10人以上、ドメイン安定後 |

**Cloud Run での現実解**：  
モノリスでもCloud Runの自動スケールで十分。10万req/dayまではモノリスが正解。
