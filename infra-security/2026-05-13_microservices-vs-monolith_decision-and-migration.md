# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスの方がスケールする」という誤解から、小規模チームが無理に分散システムを構築して崩壊するケースは多い。重要なのは「どちらが正しいか」ではなく「今のチームと規模に何が合うか」の判断力。特にAI時代は、一人でも複雑なコードが書けるため、**分割の恩恵よりも分散システムの複雑性が上回る**リスクが増している。

---

## 仕組みの要点

### モノリスの特徴
- 1つのデプロイ単位。全コードが同一プロセス
- DB呼び出しはローカル関数呼び出しと同等のコスト
- テスト・デバッグが単純。ログが1箇所に集まる
- チームが小さいほど認知負荷が低い

### マイクロサービスの特徴
- サービスごとに独立デプロイ・スケール可能
- 障害が局所化できる（サーキットブレーカーが前提）
- チーム境界＝サービス境界（コンウェイの法則）
- ネットワーク遅延・分散トランザクション・サービスディスカバリが必要になる

### 判断の実際的な基準
| 条件 | 推奨 |
|------|------|
| チーム5人以下 | モノリス |
| 機能ごとにスケール要件が異なる | マイクロサービス |
| デプロイ頻度がチームごとに異なる | マイクロサービス |
| 1DBで完結する | モノリス |
| 異なる言語・技術が必要 | マイクロサービス |

---

## アンチパターン vs 正しい設計

### アンチパターン
- **分散モノリス**: サービスは分割したが、DBは共有。デプロイ順序に依存が残る
- **過早分割**: ドメイン境界が不明確なうちに分割し、後で再統合が必要になる
- **RPC over HTTP の乱用**: サービス間同期呼び出しが増え、1つの障害が全体に伝播
- **モノリスの全行書き直し**: ビッグバン移行で失敗するパターン

### 正しい設計
- **Modular Monolith（モジュラーモノリス）が中間解**: モノリスだがモジュール境界を明確にし、将来の分割を容易にする
- **Strangler Fig Pattern**: 新機能だけをマイクロサービスで作り、徐々に既存を置き換える
- **DB分割が先**: サービス分割の前にDBスキーマの境界を決める

---

## 設計例：Strangler Figパターン（FastAPI + Cloud Run）

```
# 段階1: モノリス内に明確なモジュール境界を作る
# app/
#   auth/      ← 将来サービス化候補
#   orders/    ← 将来サービス化候補
#   main.py

# 段階2: Cloudflare WorkersやAPI GatewayでルーティングをProxy
# /api/auth/* → auth-service (Cloud Run)
# /api/*      → monolith (Cloud Run)  ← まだここが本体

# 段階3: authモジュールを別Cloud Runサービスに切り出す
# monolithはauth-serviceをHTTP呼び出し or Firebase Auth SDKに委譲
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|------|----------|----------------|
| 開発速度（初期） | 速い | 遅い（インフラ構築コスト） |
| デバッグ難易度 | 低い | 高い（分散トレーシングが必要） |
| スケール柔軟性 | 低い | 高い |
| チーム独立性 | 低い | 高い（チームが大きいほど恩恵） |
| 障害の局所化 | 難しい | 可能（設計次第） |
| 運用コスト | 低い | 高い（サービスディスカバリ・監視・ネットワーク） |

**実用的な結論**: まずモジュラーモノリスで始め、スケールまたはチーム分割が必要になった時点でStrangler Figで分離する。
