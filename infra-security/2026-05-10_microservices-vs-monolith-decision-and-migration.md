# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか」は、AI時代の設計判断で最も問われる問いの一つ。
多くのチームが「スケールのため」と言いながら不必要に分散システムの複雑さを抱える。
正しい判断基準は「**今のチームと規模にとって最もシンプルで壊れにくい構成はどれか**」である。

---

## 仕組みの要点

### モノリス（Monolith）
- 1プロセスで全機能を提供。デプロイ・デバッグが単純
- Cloud Run 1サービスにすべて収める構成が典型
- 内部モジュール間はただの関数呼び出し（ネットワーク不要）

### マイクロサービス（Microservices）
- 機能を独立したサービスに分割。各サービスが独自にデプロイ可能
- サービス間通信はHTTP/gRPC/メッセージキュー
- 分散システム特有の問題（遅延・部分障害・トランザクション）が発生

### モジュラーモノリス（現実的な中間解）
- モノリスでありながら内部を明確なモジュールに分割
- 将来の分割を見越した設計をしつつ、今は1プロセスで動かす

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 小規模チームがマイクロサービスを採用 | チーム数≒サービス数が原則（Conway's Law） |
| 「スケールのため」と言いながら実際は低負荷 | ボトルネック計測してから分割を検討 |
| 最初からマイクロサービス設計 | モノリスから始めて必要に応じて分割 |
| サービス間で直接DBを共有 | サービスごとに独立したDBを持つ |
| 分散トランザクションを実装 | Sagaパターンか結果整合性で設計 |

---

## 判断基準：マイクロサービスに移行すべきタイミング

```
チーム規模 >= 3チーム（各チームが独立してデプロイしたい）
AND
特定機能のスケール要件が他と大きく異なる（例：動画変換だけ重い）
AND
デプロイ頻度が高く、モノリスのデプロイ時間が問題になっている
```

判断しない理由（移行しない根拠も同じくらい重要）:
- チームが1〜2チーム以下
- スケール要件が均一
- 運用コストを増やせる人員がいない

## FastAPI + Cloud Run での構成例

### モノリス（推奨スタート地点）
```
cloud-run/
  app/
    api/          # ルーター
      auth.py
      items.py
    services/     # ビジネスロジック（モジュール分離）
      auth_service.py
      item_service.py
    db/           # DB接続（Neon PostgreSQL）
  main.py
```

### 分割の最小ステップ（必要になったら）
```
# ①重いバッチ処理だけを別Cloud Runサービスに切り出す
# メインAPI → Cloud Run（api-service）
# バッチ処理 → Cloud Run（batch-service、最小インスタンス0）

# サービス間通信：Cloud Tasks or Pub/Sub（直接HTTP呼び出しは避ける）
```

## 移行戦略：Strangler Fig パターン

```
1. モノリストの前段にAPI Gatewayを置く（Cloud Run + nginx 等）
2. 新機能は新サービスとして実装し、Gatewayがルーティング
3. 旧機能を徐々に新サービスに移行
4. モノリストが空になったら廃止
```

切り出す順序の基準:
1. デプロイ頻度が最も高い機能
2. スケール要件が他と明らかに異なる機能
3. チームの境界と一致している機能

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（基盤整備が必要） |
| デプロイ独立性 | なし | あり |
| 障害の局所化 | 難しい | しやすい（設計次第） |
| 運用コスト | 低い | 高い（監視・ネットワーク・サービスメッシュ） |
| テストのしやすさ | 高い（E2Eが単純） | 低い（サービス間モック が必要） |
| スケール柔軟性 | 全体単位 | 機能単位 |
