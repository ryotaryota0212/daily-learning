# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」は現代システム設計で最も誤解されやすい判断の一つ。  
マイクロサービスは複雑性を「組織的に管理できる単位」に分散させるアーキテクチャ。  
チーム・スケール・デプロイ頻度が伴わない段階での採用は、コストだけが増える。  
AI時代においても「なぜ分割するのか」を説明できない設計は技術的負債の温床になる。

---

## 仕組みの要点

### モノリスの特徴
- 単一デプロイ単位でコード・DB・プロセスが一体
- 開発初期は速い（共有型・単純なトランザクション）
- スケールは「全体をまとめて」行うしかない

### マイクロサービスの特徴
- サービスごとに独立してデプロイ・スケール可能
- サービス間通信はネットワーク越し（REST/gRPC/メッセージキュー）
- DBも原則サービスごとに分離（Shared DB は避ける）
- 観測性・サービスメッシュ・分散トレーシングが必要になる

### 判断の核心：「何が独立して変化するか」
- 変更頻度・チーム所有権・スケール要件が異なる場合に分割する価値がある
- 同じチームが全部触るなら分割しても利点は少ない

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで始める | モノリスで始めて境界が明確になったら分割 |
| サービス間でDBを共有する | サービスごとに独立したDBスキーマ/インスタンス |
| 同期REST呼び出しを連鎖させる | 非同期メッセージで疎結合にする |
| デプロイを一斉に行う | サービスごとに独立したCI/CDパイプライン |
| 分散トランザクションを使う | Sagaパターン・補償トランザクションで整合性を担保 |

## コード/設計例（モノリスからの段階的分割）

```python
# ① まずモノリスでドメイン境界を明確にする（モジュラーモノリス）
# app/
#   users/     ← Userドメイン（独立した責務）
#   orders/    ← Orderドメイン
#   payments/  ← Paymentドメイン（最もスケールが異なる）

# ② PaymentだけCloud Runサービスとして切り出す
# payments_service/main.py
from fastapi import FastAPI
app = FastAPI()

@app.post("/payments/charge")
async def charge(order_id: str, amount: int):
    # Stripe等の外部決済API呼び出し
    return {"status": "ok", "order_id": order_id}

# ③ モノリス側からはHTTPクライアントで呼び出す
import httpx
async def call_payment_service(order_id: str, amount: int):
    async with httpx.AsyncClient() as client:
        r = await client.post(
            "https://payments-svc-xxx.run.app/payments/charge",
            json={"order_id": order_id, "amount": amount}
        )
    return r.json()
```

## 移行戦略：ストラングラーフィグパターン

```
[既存モノリス] ──→ (Cloudflare / API Gateway)
                         ↓ 新パスのみルーティング
                   [新マイクロサービス]
```

1. モノリスの前段にプロキシを置く
2. 新機能・切り出し済み機能だけ新サービスに流す
3. モノリスは徐々に縮小・最終的に廃止

---

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備が必要） |
| デプロイリスク | 高（全体に影響） | 低（サービス単位） |
| 障害の影響範囲 | 全体 | 局所化できる |
| 運用複雑性 | 低 | 高（監視・通信・整合性） |
| スケーラビリティ | 均一スケールのみ | サービス単位で最適化可能 |
| チーム規模適性 | 小規模（〜10人） | 大規模（複数チーム） |

**FastAPI + Cloud Run の文脈では：**
- Cloud Run は「コンテナ単位のサービス」なのでマイクロサービスと相性が良い
- ただし、Neon(PostgreSQL)のRLSで権限分離できているなら1DBで複数サービスを運用可能
- Firebase Auth のトークン検証は各サービスで共通ライブラリ化して再利用する

## チェックリスト

- [ ] サービス分割の境界は「チームの所有単位」と一致しているか
- [ ] DBを共有していないか（Shared DBはマイクロサービスのアンチパターン）
- [ ] サービス間の同期呼び出し連鎖が3段以上になっていないか
- [ ] 各サービスが独立してデプロイ・ロールバックできるか
- [ ] 分散トレーシング（Cloud Trace等）で障害箇所を特定できるか
