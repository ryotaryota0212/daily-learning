# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき？」は最もよく聞かれる設計上の問いの一つだが、正解は「規模と組織次第」。
間違った判断は、運用コストの爆発・障害の複雑化・開発速度の低下を招く。
AI時代においてもこの原則は変わらない。むしろ「余計な複雑さを排除する力」がより重要になっている。

---

## 仕組みの要点

### モノリスとは
- 1つのアプリに全機能が含まれる構成
- デプロイ単位が1つ、DBも基本1つ
- シンプルだが、規模が大きくなるとビルド・テスト・デプロイが重くなる

### マイクロサービスとは
- 機能ごとに独立したサービスに分割
- 各サービスが独立してデプロイ・スケール可能
- サービス間はHTTP/gRPC/メッセージキューで通信

### Conwayの法則（最重要）
> システムの構造は、それを作る組織のコミュニケーション構造を反映する

- 3人チームでマイクロサービス → 全部自分たちで運用、メリットなし
- 複数チームが独立して動けるなら → マイクロサービスが活きる

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービス | モノリス → 必要になったら分割 |
| 機能単位で細かく分割しすぎ | ドメイン境界（Bounded Context）で分割 |
| DBを各サービスで共有 | 各サービスが自分のDBを持つ |
| 同期HTTP呼び出しの連鎖 | 非同期メッセージで疎結合に |
| 全部マイクロサービスに移行 | ボトルネックになった部分だけ切り出す |

### 判断基準チェック

```
モノリスを選ぶ条件:
  - チームが5人以下
  - プロダクトがまだ初期フェーズ（PMF前）
  - ドメイン境界がまだ不明確

マイクロサービスを選ぶ条件:
  - 複数チームが独立してデプロイしたい
  - 特定機能だけスケールさせたい（例: 動画変換だけ）
  - 技術スタックを機能ごとに変えたい理由がある
```

## 設計例（FastAPI + Cloud Run での段階的分割）

### フェーズ1: モジュラーモノリス（推奨スタート）

```
app/
  ├── auth/       # Firebase Auth連携
  ├── billing/    # Stripe決済
  ├── core/       # 共通ロジック
  └── main.py     # 1つのエントリーポイント
```

- Cloud Run 1サービスにデプロイ
- 内部はモジュールで分離 → 後の分割が楽になる

### フェーズ2: ボトルネックだけ切り出す

```
# 元のモノリスから billing だけ切り出す例
# billing-service/main.py

from fastapi import FastAPI
app = FastAPI()

@app.post("/webhooks/stripe")
async def stripe_webhook(request: Request):
    # 重い処理をここに集約してスケールさせる
    ...
```

- Cloud Run の billing-service に独立デプロイ
- モノリス側からは内部HTTP or Pub/Sub で呼び出す

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（インフラ整備が必要） |
| デプロイ | 全体再デプロイ | 独立デプロイ可能 |
| 障害影響 | 全体が落ちる | サービス分離で局所化できる |
| 運用コスト | 低い | 高い（監視・ネットワーク・認証） |
| スケール | 全体一括 | 機能ごとに最適化可能 |
| デバッグ | 簡単（ログ1箇所） | 難しい（分散トレーシング必要） |

## チェックリスト

- [ ] チーム規模・組織構造がマイクロサービスを正当化するか確認した
- [ ] まずモジュラーモノリスで境界を明確にしてから分割を検討した
- [ ] 分割するサービスは「DBも含めて独立」できるか確認した
- [ ] サービス間通信は同期か非同期か、障害時の挙動を設計した
- [ ] 分散トレーシング（Cloud Trace等）の準備ができてから分割した
