# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」はAI時代にも繰り返される問いだが、正解は一つではない。
多くのスタートアップが「スケールを見越して」早期にマイクロサービスへ移行し、複雑性の重みで開発速度を失う。
逆に巨大なモノリスが「壊れにくさ」を維持しながらスケールしている事例も多い。
重要なのは「どちらが正しいか」ではなく「今のチームと規模において何が最もシンプルで壊れにくいか」を判断できること。

---

## 仕組みの要点

### モノリスの特性
- 単一デプロイ単位。コードの変更が即座に全機能に反映される
- サービス間通信がプロセス内関数呼び出し → レイテンシゼロ、トランザクション管理が容易
- 開発初期の速度が高い。1リポジトリ、1デプロイパイプライン
- ボトルネックはデータベース競合・CPU/メモリの単一ノード上限

### マイクロサービスの特性
- サービスごとに独立デプロイ。障害の影響範囲を局所化できる
- 技術スタックをサービス単位で選択可能
- サービス間通信がネットワーク越し → レイテンシ増加、分散トランザクションが複雑化
- 運用オーバーヘッドが高い（サービスディスカバリ、分散ログ、トレーシング等が必要）

---

## アンチパターン vs 正しい設計

### アンチパターン
| アンチパターン | 何が起きるか |
|---|---|
| 初期からマイクロサービス | チームが小さく、境界が不明確なまま分割 → 分散モノリス（最悪の状態） |
| 機能単位で細かく分割 | 「ユーザーサービス」「メールサービス」「通知サービス」を全部別にする → 1リクエストで10サービスを呼ぶ |
| DBを共有したままサービスを分割 | テーブルを複数サービスが直接参照 → サービスの独立性がゼロ |
| 「スケールのため」という曖昧な理由 | 実際のボトルネックを測定せず移行 → 複雑性だけ増える |

### 正しい設計判断のフロー
```
チームが10人未満 → まずモノリスで始める
    ↓
開発速度が落ちてきた原因を特定
    ↓
デプロイ競合？ → モジュラーモノリスで解決できないか？
スケール問題？ → どのDBテーブル/どのAPIがボトルネックか？
組織の分断？ → コンウェイの法則でチーム構造が反映される
    ↓
「このサービスだけ独立してスケールしたい」が明確になったら分割
```

## 移行戦略：ストラングラーフィグパターン

モノリスを壊さずに段階的にマイクロサービスへ移行する手法。

```python
# Cloud Run上のAPIゲートウェイ（FastAPI）でルーティング制御
# モノリスとマイクロサービスを並行稼働させる

from fastapi import FastAPI, Request
import httpx

app = FastAPI()

# 新サービスが準備できた機能だけ切り替え
FEATURE_FLAGS = {
    "/api/payments": "https://payment-service-xxx.run.app",
    # それ以外はモノリスへ
}

MONOLITH_URL = "https://monolith-xxx.run.app"

@app.api_route("/{path:path}", methods=["GET","POST","PUT","DELETE"])
async def proxy(path: str, request: Request):
    route = f"/{path}"
    target = FEATURE_FLAGS.get(route, MONOLITH_URL)
    async with httpx.AsyncClient() as client:
        resp = await client.request(
            method=request.method,
            url=f"{target}{route}",
            headers=dict(request.headers),
            content=await request.body(),
        )
    return resp.json()
```

**ポイント：**
- モノリスを止めずに新サービスを追加
- フィーチャーフラグで切り替え率を段階的に上げる
- 失敗したら即座にモノリスへ戻せる

## トレードオフ整理

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 開発速度（初期） | 速い | 遅い（環境構築複雑） |
| デプロイリスク | 全体影響 | 局所化 |
| 障害の連鎖 | 部分障害が全体停止になりやすい | サーキットブレーカーで局所化 |
| トランザクション | ACID保証が容易 | 結果整合性（Sagaパターン等）が必要 |
| 運用コスト | 低 | 高（分散ログ・トレーシング必須） |
| チーム規模 | 〜15人に適する | 複数チームが独立して動く場合に向く |

**FastAPI + Cloud Runスタックでの現実解：**
- Cloud Runは「1サービス = 1コンテナ」でスケールするため、モジュール単位でサービスを分けやすい
- 初期はモノリスとして1つのCloud Runサービスで動かし、ボトルネックが出たサービスだけ切り出す
- Neonは接続プール（pgBouncer）の上限があるため、サービス数が増えると接続数に注意
