# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべき？」はAI時代のシステム設計で最も誤解されやすい問いの一つ。  
正解は「チームの規模・開発速度・障害耐性の要件によって決まる」であり、マイクロサービスは万能解ではない。  
分割コストを払うに足るスケール・チーム規模か判断できることが、設計者としての核心スキルになる。

---

## 仕組みの要点

### モノリスの特性

- **単一デプロイ単位**：全機能が1プロセス。デプロイが単純。
- **低レイテンシ**：関数呼び出しで完結。ネットワーク遅延なし。
- **開発速度が高い（初期）**：ローカル環境構築が容易、IDE横断が効く。
- **障害境界がない**：1か所のバグで全体停止リスク。

### マイクロサービスの特性

- **独立デプロイ**：サービスごとにリリースサイクルを持てる。
- **独立スケール**：ボトルネックのサービスだけスケールアウト可能。
- **障害の局所化**：1サービス落ちても他が生き続ける（サーキットブレーカー必要）。
- **複雑性コスト**：分散トレーシング、サービス間認証、ネットワーク障害を自前で管理。

### 判断の核心：Conway's Law

> 「システム設計はそれを作る組織の構造を反映する」

- チームが1つ → モノリスが自然。分割しても組織が追いつかない。
- チームが独立して動ける規模（6〜8人/チーム × 複数チーム）→ マイクロサービスが有効。

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービス（設計が決まっていない段階） | まずモノリスで境界を発見してから分割 |
| ドメイン境界があいまいなまま分割 | Bounded Contextを先に定義 |
| 全サービスが共通DBを参照 | サービスごとにDBを持つ（DB per Service） |
| 同期HTTP呼び出しのチェーン（A→B→C→D） | 非同期イベントで依存を切る |
| モノリスのコードをそのままサービスに切り出す | まずモジュールとして分離し、後でプロセスを分ける |

## 移行戦略：Strangler Fig パターン

モノリスを一気に書き換えずに段階的に移行する標準アプローチ。

```
[クライアント]
     |
  [APIゲートウェイ / リバースプロキシ]
     |                  |
[新サービス(A)]    [モノリス(B,C,D...)]
```

```python
# Cloud Run上のAPIゲートウェイ例（FastAPI）
from fastapi import FastAPI
import httpx

app = FastAPI()

# 移行済み機能 → 新サービスへルーティング
@app.get("/orders/{order_id}")
async def get_order(order_id: str):
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://order-service/orders/{order_id}")
        return resp.json()

# 未移行機能 → モノリスへプロキシ
@app.get("/reports/{report_id}")
async def get_report(report_id: str):
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://monolith/reports/{report_id}")
        return resp.json()
```

**移行手順**
1. モノリス内でモジュールを明確に分離（境界を引く）
2. APIゲートウェイを前段に置く（ルーティング制御）
3. 最もデプロイ頻度が高い機能から順に切り出す
4. 新サービスが安定したらモノリス側を削除

## FastAPI + Cloud Run での構成例

```
Cloud Run サービス構成（マイクロサービス化後）

user-service     → Firebase Auth連携、ユーザー管理
order-service    → Neon DB（orders スキーマ）+ RLS
notification-svc → Pub/Sub consumer、メール/プッシュ送信
api-gateway      → Cloud Run（ルーティング + 認証ミドルウェア）

サービス間認証: Cloud Run サービスアカウント + ID トークン
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 初期開発速度 | 速い | 遅い（インフラ構築コスト大） |
| スケール柔軟性 | 低い（全体スケール） | 高い（部分スケール） |
| 障害耐性 | 低い（全体影響） | 高い（局所化できる） |
| 運用複雑性 | 低い | 高い（分散トレース必須） |
| チーム独立性 | 低い | 高い |
| 適切な段階 | 〜10人チーム、PMF前 | 複数チーム、機能が安定後 |

**判断の目安**：  
「今のチームで、今の規模で、マイクロサービスの複雑性を吸収できるか？」がNOならモノリスを選ぶ。  
マイクロサービスは「将来のための設計」ではなく「今の課題を解決するための設計」。
