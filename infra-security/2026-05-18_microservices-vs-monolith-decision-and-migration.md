# マイクロサービス vs モノリスの判断基準と移行戦略

## 概要

「マイクロサービスにすべきか？」はAI時代でも頻出の設計判断だ。問題は「マイクロサービスは優れている」という思い込みが先行し、コスト・複雑さ・チーム規模を無視した選択がされることにある。正しい判断は「今の組織・規模・問題に対してどちらがシンプルで壊れにくいか」を軸に行う。

---

## 仕組みの要点

### モノリスの特性
- 単一プロセス・単一デプロイ単位
- サービス間通信がインプロセス呼び出し → レイテンシゼロ・トランザクション管理が容易
- デバッグ・ローカル開発が単純
- 初期段階では圧倒的に生産性が高い

### マイクロサービスの特性
- サービスごとに独立してデプロイ・スケール可能
- 技術スタックを分けられる（ただし統一した方が運用コストは低い）
- 障害の影響範囲を限定できる（ただし分散障害は複雑化する）
- チームごとのオーナーシップが明確になる

### 判断の核心：Conway's Law
> 「システムのアーキテクチャは、それを設計した組織のコミュニケーション構造を反映する」

- チームが3〜5人 → モノリスが自然
- チームが分割されてリリース干渉が頻発 → 分割を検討
- 組織構造なしにマイクロサービスを入れると、「分散モノリス」という最悪形態になる

---

## アンチパターン vs 正しい設計

| アンチパターン | 正しい設計 |
|---|---|
| 最初からマイクロサービスで設計 | モノリスからスタートし境界が見えてから分割 |
| サービス間でDBを共有 | サービスごとに独立したDB（Schema Separation） |
| 同期HTTP呼び出しを多段にネスト | 非同期メッセージキュー or BFF層で集約 |
| 全サービスを同時デプロイ | サービス単位の独立デプロイ（バージョニング付き） |
| 分散トランザクションをXAで実装 | Sagaパターン（補償トランザクション）で代替 |

## 設計例：モジュラーモノリスから分割する手順

```
Phase 1: モジュラーモノリス（推奨スタート地点）
FastAPI アプリ
  ├── routers/
  │   ├── auth.py      # 認証ドメイン
  │   ├── orders.py    # 注文ドメイン
  │   └── payments.py  # 決済ドメイン
  ├── services/        # ドメインごとに分離
  └── db/              # スキーマはドメインごとに名前空間分け

Phase 2: 境界が明確になったら切り出す
- 決済だけ Cloud Run サービスを分割
- 非同期処理（メール等）は Cloud Tasks に切り出す
- 認証は Firebase Auth に委譲済みなので実質分離済み
```

### FastAPI + Cloud Run での最小分割パターン
```python
# サービス間通信は内部URLを使う（外部に晒さない）
PAYMENT_SERVICE_URL = os.getenv("PAYMENT_SERVICE_URL")  # 内部エンドポイント

async def call_payment_service(payload: dict) -> dict:
    async with httpx.AsyncClient() as client:
        # Cloud Run サービス間：GCP の内部認証トークンを付与
        token = await get_id_token(PAYMENT_SERVICE_URL)
        resp = await client.post(
            f"{PAYMENT_SERVICE_URL}/charge",
            json=payload,
            headers={"Authorization": f"Bearer {token}"},
            timeout=5.0,
        )
        resp.raise_for_status()
        return resp.json()
```

## トレードオフ

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| 初期開発速度 | 速い | 遅い（インフラ設定コスト大） |
| 運用複雑さ | 低い | 高い（サービスディスカバリ、分散トレーシング等） |
| スケール柔軟性 | 全体一括 | サービス単位（コスト最適化可能） |
| 障害局所化 | 難しい | しやすい（ただし連鎖障害のリスクも増える） |
| チーム独立性 | 低い | 高い（組織が大きい場合に有効） |
| デバッグ難易度 | 低い | 高い（分散トレーシング必須） |

### 判断フローチャート
```
チームは何人？
  └─ ~10人 → モノリスで十分
  └─ 10人超かつリリース干渉が問題 → モジュラーモノリス検討
      └─ 特定ドメインが独立スケール必要 or チーム完全分離必要 → 該当部分だけ切り出す
```

## チェックリスト

- [ ] チーム規模・組織構造を先に確認してからアーキテクチャを決めたか
- [ ] モノリス内でドメイン境界（モジュール分割）が先に明確になっているか
- [ ] サービス間でDBを共有していないか（分散モノリス化の確認）
- [ ] サービス間通信に Cloud Run の内部認証（IDトークン）を使っているか
- [ ] 分割後に分散トレーシング（Cloud Trace 等）を導入済みか
