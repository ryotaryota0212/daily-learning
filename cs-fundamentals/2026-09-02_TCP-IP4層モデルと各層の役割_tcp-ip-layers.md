# TCP/IPの4層モデルと各層の役割

## 概要

インターネット通信の土台となるTCP/IPモデルは4層で構成される。各層が独立した責務を持ち、上位層は下位層の実装を意識しない（レイヤー分離）。FastAPIサーバーがHTTPリクエストを受け取る裏側では、このスタック全体が動いている。層の役割を知ることで、「なぜコネクションが切れるか」「なぜレイテンシが生じるか」を正確に特定できる。

---

## 仕組みの要点

```
[アプリケーション層]  HTTP, DNS, SMTP, WebSocket
        ↕  (データ)
[トランスポート層]    TCP, UDP
        ↕  (セグメント/データグラム)
[インターネット層]   IP, ICMP
        ↕  (パケット)
[ネットワーク接続層] Ethernet, Wi-Fi, PPP
        ↕  (フレーム)
```

### 各層の責務

**ネットワーク接続層（リンク層）**
- 同一ネットワーク内の物理的なデータ転送
- MACアドレスで機器を識別（ARPでIPからMACを解決）
- フレーム単位で送受信、CRCによる誤り検出

**インターネット層**
- 異なるネットワーク間のルーティング（IPアドレスで宛先指定）
- パケット分割（フラグメンテーション）と再組み立て
- ベストエフォート：順序保証なし、再送なし

**トランスポート層**
- TCP：3ウェイハンドシェイク → 順序保証 + 再送制御 + フロー制御
- UDP：コネクションレス → オーバーヘッド小、順序保証なし
- ポート番号でプロセスを識別（同一IPの複数サービスを区別）

**アプリケーション層**
- エンドユーザーが直接利用するプロトコル
- HTTP（80/443）、DNS（53）、SMTP（25）など
- ソケットAPIを通じてトランスポート層を利用

---

## カプセル化の仕組み

送信時、データは各層でヘッダーを付加される（カプセル化）。  
受信時は逆順にヘッダーを取り除く（デカプセル化）。

```
[HTTP データ]
→ [TCP ヘッダー | HTTP データ]          ← セグメント
→ [IP ヘッダー | TCP ヘッダー | HTTP データ]   ← パケット
→ [Ethヘッダー | IP | TCP | HTTP | FCS]     ← フレーム
```

## TCPコネクションの実際

```python
import socket

# TCP接続（3ウェイハンドシェイク）の観察
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(("example.com", 80))  # SYN → SYN-ACK → ACK

# HTTP/1.1リクエスト送信
s.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")

response = b""
while chunk := s.recv(4096):
    response += chunk

s.close()  # FIN → ACK → FIN → ACK（4ウェイハンドシェイク）
print(response[:200])
```

## よくある誤解・落とし穴

| 誤解 | 実際 |
|------|------|
| TCPは信頼性があるので完璧 | 順序・再送保証はあるが遅延・輻輳は起きる |
| UDPは信頼性がないから使えない | DNS・動画ストリーミング・QUICでは必須 |
| IPアドレス = サーバー1台 | NATやロードバランサーで多対多になる |
| ポートはOSが管理する | 0-1023は特権ポート、1024-65535はユーザー空間 |

**TIME_WAIT問題**
- TCP切断後、ソケットは`TIME_WAIT`状態で2MSL（通常60秒）残る
- 高トラフィックでポートが枯渇しうる → `SO_REUSEADDR`で緩和

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Cloud Run** はHTTPSリクエストをTLSで受け取り → TLS終端後に平文HTTPをコンテナへ転送（アプリ層のみ意識すればよい）
- **Neonへの接続** は TCP上のPostgreSQLプロトコル。コネクションプーリング（PgBouncer）で`TIME_WAIT`とハンドシェイクオーバーヘッドを削減
- **レイテンシ診断** で`ping`（ICMP：インターネット層）と`traceroute`（TTLを利用）を使い分ける
- **WebSocket** はHTTPアップグレード後もTCPコネクションを使い続ける（アプリ層の話だがトランスポート層は同じTCP）
- `curl -v`の`* Connected to`→`> GET`→`< HTTP/1.1`の流れがカプセル化の逆順に対応
