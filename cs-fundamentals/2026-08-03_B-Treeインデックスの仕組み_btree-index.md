# B-Treeインデックスの仕組みと計算量

## 概要

B-Treeインデックスはリレーショナルデータベースで最も広く使われるインデックス構造。PostgreSQL（Neon含む）のデフォルトインデックスでもある。「なぜクエリが速いのか／遅いのか」を理解するには、B-Treeの内部構造を知ることが不可欠。インデックスの設計ミスはAPIレイテンシに直結する。

## 仕組みの要点

- **B-Treeは平衡多分木**: 全葉ノードの深さが等しく、検索パスの長さが保証される
- **PostgreSQLの実装はB+Tree**:
  - 内部ノード（ルート・枝）: キーのみ保持、子ノードへのポインタを持つ
  - 葉ノード: キー + ヒープタプルへのポインタ（TID）を保持
  - 葉ノード同士は**双方向リンクリスト**で連結 → 範囲検索が高速

```
        [ルート: 30 | 60]
       /        |        \
 [10|20]    [35|50]    [70|80]   ← 葉ノード（TID付き）
    ↔           ↔          ↔    ← リンクリスト連結
```

- ノードはページ（8KB）単位でディスクに保存。1ページに数百キーを格納
- 分岐数（Order）が大きいほど木が浅くなり、ディスクI/O回数が減る

## 計算量・パフォーマンス特性

| 操作 | 計算量 | 備考 |
|------|--------|------|
| 等値検索 | O(log N) | ルートから葉まで降下 |
| 範囲検索 | O(log N + K) | Kは結果件数。葉リスト走査 |
| 挿入 | O(log N) | ノード分割が発生する場合あり |
| 削除 | O(log N) | ノード再結合が発生する場合あり |

- テーブルが100万行でも木の高さは3〜4段程度（ディスクI/Oが少ない）
- 書き込みのたびにB-Tree更新が必要 → インデックスは書き込みコストを増やす

## コード例（SQL）

```sql
-- 単一カラムインデックス
CREATE INDEX idx_users_email ON users(email);

-- 複合インデックス（順序が重要: 左端から使われる）
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC);

-- EXPLAINで実行計画を確認
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 1 AND created_at > '2026-01-01';
-- "Index Scan using idx_orders_user_date" が出ればOK
-- "Seq Scan" が出たらインデックスが使われていない
```

## よくある誤解・落とし穴

- **左端プレフィックス則を忘れる**: 複合インデックス`(A, B)`はAだけの検索には使えるが、Bだけの検索には使えない
- **カーディナリティが低い列のインデックス**: `is_active`（trueかfalse）などはむしろフルスキャンの方が速いことも。プランナが自動判断するが意識は必要
- **インデックス列に関数を適用する**: `WHERE lower(email) = 'foo'`はインデックスを使えない。関数インデックス`CREATE INDEX ON users(lower(email))`が必要
- **NULLの扱い**: PostgreSQLはNULLもインデックスに含む（MySQLは含まない）。NULL検索でもインデックスが効く

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **FastAPI → Neonの等値検索**: `WHERE user_id = $1`は必ずインデックスを張る。外部キー列はデフォルトで張られないので手動で追加
- **ページネーション**: `LIMIT/OFFSET`は大量データで遅化する。`WHERE id > $cursor LIMIT 20`のカーソル方式でインデックスを最大活用
- **Cloud Runの注意点**: インスタンス起動直後はPlannerの統計が古いことがある。本番ではNeonのコネクションプーリング（PgBouncer）越しに`ANALYZE`を適宜実行
- **複合インデックスの設計**: `(user_id, created_at)`のように「等値条件のカラムを先、範囲・ソートのカラムを後」に配置するのが基本セオリー
