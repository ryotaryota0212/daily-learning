# ヒープとプライオリティキュー

## 概要

- ヒープは「親が子より常に優先度が高い（or 低い）」という緩い順序制約だけを持つ完全二分木。
- 全要素を並べ替えずに「最小/最大だけ」を高速に取り出したい場面に最適な構造。
- タスクスケジューラ、ダイクストラ法、上位N件抽出（Top-K）、イベント駆動シミュレーションなど応用範囲が広い。
- 完全二分木なので配列だけで実装でき、ポインタ管理が不要な点もBSTより扱いやすい理由。

## 仕組みの要点

- 配列のインデックス `i` に対し、親は `(i-1)//2`、左の子は `2i+1`、右の子は `2i+2` で計算できる（ポインタ不要）。
- **挿入**: 配列の末尾に追加 → 親と比較しながら上に浮かせる（sift-up / bubble-up）。
- **取り出し**: 根（最小or最大）を返し、末尾要素を根に移動 → 子と比較しながら下に沈める（sift-down / heapify）。
- 完全二分木なので高さは常に `O(log n)`。これが挿入・取り出しの計算量を支配する。
- 「ソート済み」ではない点に注意。兄弟同士の大小関係は保証されない。根だけが最小（or最大）。

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|---|---|
| 最小値の参照（peek） | O(1) |
| 挿入（push） | O(log n) |
| 取り出し（pop） | O(log n) |
| 配列からヒープ構築（heapify） | O(n)（n回のsift-downではなくボトムアップで構築するため） |
| 任意要素の検索 | O(n)（ヒープは検索に向かない） |

- ソート済み配列・BSTと違い「全体順序」は持たないため、k番目の値を知りたいだけならヒープが最速。
- ヒープソートは O(n log n) だが、配列ベースの実装でも安定ソートではない。

## コード例（Python: 上位K件を効率よく抽出）

```python
import heapq

def top_k(nums: list[int], k: int) -> list[int]:
    # サイズkの最小ヒープを維持し、より大きい値が来たら入れ替える
    heap = nums[:k]
    heapq.heapify(heap)  # O(k)
    for n in nums[k:]:
        if n > heap[0]:
            heapq.heapreplace(heap, n)  # pop+push を1回の操作で
    return sorted(heap, reverse=True)

# 全要素をソートする O(n log n) より、O(n log k) で済む
print(top_k([5, 1, 9, 3, 7, 2, 8], k=3))  # [9, 8, 7]
```

## よくある誤解・落とし穴

- 「ヒープ = ソート済みデータ構造」という誤解。根以外の順序は未定義。
- `heapq` はデフォルトで**最小ヒープ**。最大ヒープが欲しい場合は値を反転（`-x`）して入れるのが定石。
- 優先度が同じ要素のタイブレークを考慮しないと、`(priority, item)` のタプル比較で `item` 同士が比較不能エラーになることがある→ `(priority, counter, item)` のように一意なシーケンス番号を挟むのが安全。
- ヒープ内の要素を直接書き換えても自動で再整列されない。更新には削除→再挿入、または「遅延削除（lazy deletion）」パターンが必要。

## 実務での使いどころ

- FastAPI のバックグラウンドジョブで優先度付きタスクキューを自前実装する際、Redis のソート済みセット（ZSET）の代わりに軽量な単一プロセス内キューとして `heapq` が使える。
- Cloud Run のようなスケールアウト環境では、ヒープの状態はインスタンス内メモリに閉じるため、複数インスタンス間でジョブ優先度を共有したい場合は Redis ZSET や Cloud Tasks のような外部キューに切り出すのが安全（ヒープはあくまで単一プロセス最適化の道具）。
- Neon（Postgres）でクエリ結果から「直近のスコア上位N件」を取得する処理は、SQL側で `ORDER BY ... LIMIT N` に任せた方が良いことが多いが、アプリ側でストリーミング集計しながら上位Kを保ちたい場合（例: ログをリアルタイムに読みながら異常値Top10を検出）にはヒープが効く。
