# B-Treeインデックスの仕組みと計算量

## 概要

B-TreeはRDBMSのインデックス実装で最も広く使われるデータ構造。PostgreSQL（Neon含む）のデフォルトインデックス型。
ディスクI/Oを最小化する設計になっており、`WHERE`・`ORDER BY`・`BETWEEN`・`JOIN`の性能に直結する。
「インデックスを貼れば速くなる」だけでなく、**なぜ速くなるか・いつ効かないか**を理解することで設計の判断軸が生まれる。

---

## 仕組みの要点

### 木構造の基本

```
              [30 | 60]               ← ルートノード
             /    |    \
       [10|20] [40|50] [70|80]        ← 内部ノード
      /  |  \    ...
[1..9][11..19][21..29]                ← リーフノード（実データへのポインタ）
```

- **ノード = ディスクの1ページ（通常8KB）**。1回のI/OでN個のキーを読める
- リーフノード同士は**双方向リンクリスト**で連結 → 範囲検索が効率的
- 木の高さは低く保たれる（100万行でも高さ3〜4程度）

### 検索・挿入・削除の流れ

- **検索**: ルートから比較を繰り返しリーフまで降りる。高さ分のI/Oで完了
- **挿入**: リーフに追加。ノードが溢れたら**分割（スプリット）**して親に伝搬
- **削除**: キー削除後、ノードが少なすぎたら**再分配または統合**

### B+ Tree（PostgreSQLの実際の実装）

- B-Treeの変種。実データへのポインタは**リーフのみ**に格納
- 内部ノードはルーティング専用 → 各ノードにより多くのキーを詰められる
- 範囲スキャンはリーフのリストを辿るだけで完結

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 | 備考 |
|------|--------|------|
| 検索 | O(log n) | nはレコード数、底はノードの分岐数（大きい） |
| 挿入 | O(log n) | スプリット発生時も償却O(log n) |
| 削除 | O(log n) | 統合発生時も同様 |
| 範囲検索 | O(log n + k) | kは結果件数 |
| 順スキャン | O(n) | インデックスオンリースキャンで高速 |

- 分岐数が大きいほど木が浅くなりI/O回数が減る（これがB-Treeの核心）
- シーケンシャルアクセスはランダムアクセスより数十〜数百倍速い

## コード例（PostgreSQL）

```sql
-- インデックス作成
CREATE INDEX idx_users_email ON users(email);

-- 複合インデックス（順序が重要）
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);

-- 実行計画でインデックスの利用確認
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE user_id = 42 AND created_at > '2026-01-01';

-- インデックスの状態確認
SELECT indexname, idx_scan, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'orders';
```

## よくある誤解・落とし穴

- **左端一致の原則**: 複合インデックス`(a, b, c)`は`WHERE a=?`や`WHERE a=? AND b=?`には効くが、`WHERE b=?`単独では効かない
- **低カーディナリティへの適用**: `is_active`（true/false 2種）にインデックスを貼っても、テーブルの半分が対象なら全件スキャンの方が速い
- **NULLの扱い**: PostgreSQLのB-TreeはNULLを格納する。`IS NULL`検索でもインデックスが使える
- **書き込み性能への影響**: インデックスが多いほどINSERT/UPDATE/DELETEが遅くなる。不要なインデックスは削除する
- **HOT Update**: 同一ページ内で更新が完結する場合、インデックス更新をスキップする最適化。インデックス列を不必要に更新しないことが重要

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **外部キー列には必ずインデックス**: `JOIN`や`WHERE foreign_key = ?`が多発する列（例: `user_id`）は忘れず作成
- **作成日時の範囲検索**: `created_at`への単独インデックスは頻出。`(user_id, created_at)`の複合にするとより効果的
- **`EXPLAIN ANALYZE`を習慣化**: Neonのコンソールまたはpsqlで実行計画を確認し、`Seq Scan`が出たらインデックス漏れを疑う
- **Cloud RunのCold Start対策**: コネクション確立コストはコネクションプーリング（pgBouncer等）で吸収。クエリ自体はインデックスで高速化
- **Neonのブランチ機能活用**: 本番DBのブランチを作り、インデックス追加の実行計画変化を安全に確認してから本番適用できる
