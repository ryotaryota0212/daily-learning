# グラフの基本（表現方法・BFS・DFS）

## 概要

グラフは「ノード（頂点）」と「エッジ（辺）」で構成されるデータ構造で、ネットワーク・依存関係・経路探索など現実の多くの問題をモデル化できる。ソーシャルグラフ、パッケージの依存解決、最短経路計算など実務での応用は幅広い。BFS・DFSはグラフ探索の2大基本アルゴリズムで、これを理解することがトポロジカルソート・ダイクストラ法など応用アルゴリズムへの入口になる。

---

## 仕組みの要点

### グラフの種類
- **有向グラフ (Directed)**: エッジに向きあり（A→Bだが B→Aではない）。依存関係、URLリンクなど
- **無向グラフ (Undirected)**: エッジ双方向。SNSの友達関係など
- **重み付きグラフ**: エッジに数値（距離・コスト）あり。最短経路問題に使う
- **DAG (有向非循環グラフ)**: 閉路なし。タスクの依存解決に多用

### 表現方法

**隣接リスト (Adjacency List)**
```
{
  A: [B, C],
  B: [D],
  C: [D],
  D: []
}
```
- メモリ: O(V + E)　← 疎なグラフに有利
- エッジ存在確認: O(degree)　← 遅い

**隣接行列 (Adjacency Matrix)**
```
  A B C D
A 0 1 1 0
B 0 0 0 1
C 0 0 0 1
D 0 0 0 0
```
- メモリ: O(V²)　← 密なグラフ向き
- エッジ存在確認: O(1)　← 速い

**実務では隣接リストがデフォルト**（ほとんどのグラフは疎）

---

### BFS（幅優先探索）

- キューを使い、近い順に探索する
- **最短ホップ数**（重みなし）を求めるのに適切
- 処理順: 探索 → キューに追加 → 順番に処理

```python
from collections import deque

def bfs(graph, start):
    visited = set([start])
    queue = deque([start])
    while queue:
        node = queue.popleft()
        print(node)
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append(neighbor)
```

### DFS（深さ優先探索）

- スタック（または再帰）を使い、深く潜ってから戻る
- サイクル検出・トポロジカルソート・連結成分の列挙に適切

```python
def dfs(graph, node, visited=None):
    if visited is None:
        visited = set()
    visited.add(node)
    print(node)
    for neighbor in graph[node]:
        if neighbor not in visited:
            dfs(graph, neighbor, visited)
```

## 計算量・パフォーマンス特性

| 操作 | 隣接リスト | 隣接行列 |
|------|-----------|---------|
| BFS / DFS | O(V + E) | O(V²) |
| エッジ追加 | O(1) | O(1) |
| エッジ確認 | O(degree) | O(1) |
| メモリ | O(V + E) | O(V²) |

- V = 頂点数、E = エッジ数
- 疎グラフ（E << V²）: 隣接リストが有利
- 密グラフ（E ≈ V²）: 隣接行列でも可

---

## よくある誤解・落とし穴

1. **visited管理を忘れる** → 無限ループ。BFS/DFSともに必須
2. **BFSで最短経路が取れると思い込む** → 重み付きグラフにはダイクストラ法が必要
3. **再帰DFSのスタックオーバーフロー** → 頂点数が多い（数万〜）場合は反復DFSに変える
4. **有向グラフと無向グラフの混同** → 隣接リスト構築時に双方向追加するかを意識する
5. **DFSでの発見順と終了順の区別** → トポロジカルソートでは終了順（post-order）が重要

## 実務での使いどころ

### FastAPI + Neon + Cloud Run スタックとの関連

- **API依存の可視化**: 複数のマイクロサービスや外部APIコール間の依存を有向グラフで表現し、循環依存（デッドロック候補）をDFSで検出できる
- **Cloud Runサービスの起動順序制御**: サービス間の依存をDAGで管理し、トポロジカルソートで起動順を決定する
- **Neon（PostgreSQL）の外部キー依存**: テーブルのFK関係をグラフにすると、マイグレーション順や削除順を安全に決定できる（循環外部キーはデータ設計上のバグ）
- **ルート探索・レコメンデーション**: ユーザー→商品→タグのような関係をグラフで持ち、BFSで「N度以内の関連アイテム」を取得するパターンはよく使われる
