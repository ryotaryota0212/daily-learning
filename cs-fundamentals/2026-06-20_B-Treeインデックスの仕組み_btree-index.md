# B-Treeインデックスの仕組みと計算量

## 概要

データベースの検索を高速化する最重要構造。PostgreSQL（Neon含む）のデフォルトインデックスはB-Tree。
「なぜインデックスを貼ると速くなるか」を理解することで、効果的な貼り方・貼りすぎの弊害が分かる。
フルスキャンが O(n) なのに対し、B-Treeで O(log n) になる理由を掴む。

---

## 仕組みの要点

### B-Treeの構造

```
          [30 | 60]              ← ルートノード
         /    |    \
    [10|20] [40|50] [70|80]     ← 内部ノード
    /  |  \  ...               ← リーフノード（実データへのポインタ）
```

- **ノード** = ディスクの1ページ（通常8KB）に収まるよう設計
- **次数 t** = 各ノードが持てるキー数の上限。t=100なら1ノードに最大100キー
- **高さが低い** = ディスクI/Oが少ない。100万行でも高さ3〜4程度
- リーフノードは **双方向リンク** でつながっており、範囲検索が効率的

### 検索の流れ

1. ルートノードをメモリに読み込む
2. キーを二分探索で比較し、子ノードへ降りる
3. リーフに到達したらデータのrow IDを取得
4. heap（実データ）からタプルを取得

### 挿入の流れ

1. 検索と同じ手順でリーフを特定
2. リーフに空きがあればそのまま挿入
3. ノードが満杯 → **分割（split）** してキーを親に押し上げ
4. ルートが分割されると木の高さが1増える（高さ増加はまれ）

### 削除の流れ

- リーフから削除 → 必要に応じて **マージ** または **再分配**
- PostgreSQLはVACUUM時に不要ページを回収

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 | 備考 |
|------|--------|------|
| 検索 | O(log n) | nはレコード数 |
| 挿入 | O(log n) | 分割があっても定数回 |
| 削除 | O(log n) | マージがあっても定数回 |
| 範囲検索 | O(log n + k) | kは結果件数 |
| フルスキャン | O(n) | インデックス未使用時 |

- 1億行でも log₂(100,000,000) ≈ 27。ディスクアクセス数は高さ分（数回）のみ
- **カーディナリティ低い列**（bool, ステータス等）はインデックス効果が薄い

## コード例（PostgreSQL / Neon）

```sql
-- インデックス作成と実行計画確認
CREATE INDEX idx_users_email ON users(email);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE email = 'test@example.com';

-- 出力例（インデックス使用）
-- Index Scan using idx_users_email on users
--   Index Cond: (email = 'test@example.com')
--   Buffers: shared hit=3  ← ディスクアクセス3回（高さ3のB-Tree）

-- 複合インデックス（順序が重要）
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);
-- user_id単体の検索にも使える。created_at単体には使えない
```

## よくある誤解・落とし穴

- **インデックスは多いほど良い** → 誤り。INSERT/UPDATE/DELETEのたびにインデックスも更新。書き込みが多いテーブルでは過剰なインデックスが逆効果
- **複合インデックスの列順を無視する** → `(a, b)` インデックスは `WHERE a=?` には効くが `WHERE b=?` のみでは効かない
- **インデックスを貼れば必ず使われる** → オプティマイザがフルスキャンの方が速いと判断することがある（少量データ、低カーディナリティ）
- **NULL はインデックスに含まれない** → PostgreSQLはNULLもインデックスに含む（MySQLと異なる）

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neon（PostgreSQL）** は B-Tree デフォルト。`WHERE`, `ORDER BY`, `JOIN ON` に使う列にインデックスを貼る
- FastAPIのエンドポイントで遅いクエリが出たら `EXPLAIN ANALYZE` で Index Scan か Seq Scan かを確認
- Cloud Run はリクエストごとにコールドスタートあり。コネクションプーリング（PgBouncer / asyncpg）と組み合わせることでディスクI/Oを抑制
- 複合インデックスで `(user_id, created_at DESC)` のように設計すると、ユーザー別の最新N件取得が O(log n + N) で済む
- `VACUUM` を定期実行しないと削除済みタプルがB-Treeに残りパフォーマンス劣化（Neonはauto-vacuumデフォルトON）
