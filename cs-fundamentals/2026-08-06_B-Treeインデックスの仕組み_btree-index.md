# B-Treeインデックスの仕組みと計算量

## 概要

B-Treeは、PostgreSQL・MySQL等のRDBMSが標準で使うインデックス構造。ディスクI/Oを最小化するために設計された多分木で、テーブルの行を高速に検索・範囲スキャンできる。「インデックスを貼れば速くなる」の裏側を理解することで、どこに貼るべきか・なぜ効かないかを判断できる。

---

## 仕組みの要点

### 構造
- **ノード** = ディスクの1ページ（PostgreSQLは8KB）
- **内部ノード**：検索キーと子ノードへのポインタを保持
- **リーフノード**：実際のキー値 + ヒープ上の行位置（TID）を保持
- リーフノード同士は双方向リンクで接続（範囲スキャンに使われる）

```
         [30 | 60]             ← 内部ノード（ルート）
        /    |    \
  [10|20] [40|50] [70|80]     ← リーフノード（行へのポインタを持つ）
     ↔        ↔        ↔      ← 双方向リンク
```

### 検索の流れ
1. ルートから開始、キーと比較して子ノードへ降りる
2. リーフに到達したらTIDでヒープから行を取得
3. 深さはほぼ一定（数百万行でも高さ3〜4程度）

### 挿入の流れ
1. リーフを探して挿入
2. ノードが満杯なら**スプリット**（ページを2分割して親に伝播）
3. ルートがスプリットされると木の高さが1増える

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 検索 | O(log n) |
| 挿入 | O(log n) |
| 削除 | O(log n) |
| 範囲スキャン | O(log n + k)  ※k=結果件数 |

- **ディスクアクセス数 ≒ 木の高さ**（通常3〜4回）
- フィルレート（各ノードの充填率）が低いと無駄なI/Oが増える

## コード例（SQL）

```sql
-- インデックス作成
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_orders_created_at ON orders(created_at);

-- 複合インデックス：左端のカラムから使われる
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);

-- 実行計画確認（PostgreSQL）
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE user_id = 42 AND created_at > '2026-01-01';
-- Index Scan → Buffers hit: N  でキャッシュ状況も確認できる
```

## よくある誤解・落とし穴

- **低カーディナリティ列には効かない**：`status` が3種類しかないなら全件の1/3を返すのでSeqScanの方が速いことも
- **複合インデックスは順序が重要**：`(user_id, created_at)` は `user_id` 単体の検索には使えるが `created_at` 単体には使えない
- **`LIKE '%keyword%'` はインデックスを使えない**：前方一致 `LIKE 'foo%'` のみ有効。全文検索にはGIN/GiSTを使う
- **書き込みのオーバーヘッド**：インデックスが多いほどINSERT/UPDATE/DELETEが遅くなる。不要なインデックスは削除する
- **NULLは格納される**：PostgreSQLはNULLをインデックスに含めるが、`IS NULL` 検索でインデックスが使われるかは状況次第

## 実務での使いどころ

**FastAPI + Neon (PostgreSQL) + Cloud Run スタックとの関連**

- **Neon**はサーバーレスPostgreSQL。コールドスタート時のページキャッシュが空のため、インデックスの深さ（= ディスクI/O回数）がレスポンスに直結する
- FastAPIのエンドポイントで `WHERE user_id = ?` のようなフィルタが頻出するなら、そのカラムにインデックスを必ず貼る
- `EXPLAIN ANALYZE` をローカルやNeonのコンソールで実行し、`Seq Scan` が出たら貼るインデックスを検討する
- Cloud RunはリクエストごとにDBコネクションを張り直す可能性があるため、コネクションプール（PgBouncer等）と組み合わせてI/Oコストを下げる
