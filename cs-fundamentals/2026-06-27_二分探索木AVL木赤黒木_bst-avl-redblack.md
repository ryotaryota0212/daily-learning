# 二分探索木・AVL木・赤黒木の基本と計算量

## 概要

二分探索木（BST）とその発展形（AVL木・赤黒木）は、**動的な順序付きデータ**を扱う基本構造。
データベースのインデックス（B-Tree）・言語ランタイムの辞書・OSのプロセス管理など至るところで使われている。
ハッシュテーブルと対比して「順序を保ちながら検索・挿入・削除を O(log n) に保てる」点が最大の価値。
FastAPIのルーティング内部やPostgreSQLのインデックス設計を理解する土台になる。

---

## 仕組みの要点

### 二分探索木（BST）の基本

- **不変条件**: 各ノードについて「左部分木 < ノード ≦ 右部分木」
- 検索: ルートから比較して左右に降りるだけ
- 挿入: 検索と同じ経路の末端に追加
- **問題点**: 入力が昇順・降順だとリスト状に退化 → O(n) に劣化

```
例: [3, 1, 4, 2] を挿入
    3
   / \
  1   4
   \
    2
```

### AVL木（高さ平衡BST）

- **平衡条件**: 各ノードで |左高さ - 右高さ| ≦ 1
- 挿入・削除後に「回転」操作で平衡を回復（左回転・右回転・二重回転）
- **特徴**: 常に高さ ≦ 1.44 log₂(n) → 厳密な平衡

```
右偏りが崩れたとき「左回転」:
    x              y
     \    →       / \
      y           x   z
       \
        z
```

- 読み取り多め・書き込み少ないユースケースで有利（高さが低い分、検索が速い）

### 赤黒木

- **色付き**: 各ノードが赤か黒
- **5つの制約**（主要なもの）:
  1. ルートは黒
  2. 赤ノードの子は黒（赤が連続しない）
  3. どのパスも同じ数の黒ノードを通る
- AVL木より「ゆるい」平衡 → 回転回数が少なく**書き込みが速い**
- C++ `std::map`、Java `TreeMap`、Linux カーネルのプロセス管理に採用

---

## 計算量・パフォーマンス特性

| 操作     | BST（平均） | BST（最悪） | AVL木    | 赤黒木   |
|----------|-------------|-------------|----------|----------|
| 検索     | O(log n)    | O(n)        | O(log n) | O(log n) |
| 挿入     | O(log n)    | O(n)        | O(log n) | O(log n) |
| 削除     | O(log n)    | O(n)        | O(log n) | O(log n) |
| 空間     | O(n)        | O(n)        | O(n)     | O(n)     |

- AVL木 vs 赤黒木: **読み込み多い → AVL**、**書き込み多い → 赤黒木**
- ハッシュテーブルとの違い: BSTは **範囲検索・順序走査** が O(k) でできる（ハッシュは O(n)）

## コード例

```python
# シンプルなBST検索
class Node:
    def __init__(self, val):
        self.val = val
        self.left = self.right = None

def search(root: Node, target: int) -> bool:
    if root is None:
        return False
    if target == root.val:
        return True
    if target < root.val:
        return search(root.left, target)
    return search(root.right, target)

# Pythonの標準ライブラリ: sortedcontainers
from sortedcontainers import SortedList
sl = SortedList([3, 1, 4, 1, 5])
sl.add(2)
print(sl.irange(2, 4))  # 範囲検索: SortedKeyList内の2〜4
```

## よくある誤解・落とし穴

- **「BSTなら常にO(log n)」は誤り**: 平衡が保証されるのはAVL/赤黒木だけ。素のBSTは入力順によって退化する
- **削除が一番難しい**: 子が2つあるノード削除は「中順後継ノード（inorder successor）」への置換が必要。実装バグが起きやすい
- **インオーダー走査で昇順列挙できる**: 左→自分→右の順で走査すると自然に昇順になる
- **スレッドセーフでない**: 並行アクセスにはロックまたはConcurrentSkipListMapなど別の構造が必要
- **実務でゼロから実装することは稀**: `sortedcontainers`・`heapq`・DBインデックスを使う。ただし計算量を理解しないと使い方を誤る

## 実務での使いどころ

### FastAPI + Neon + Cloud Run スタックとの関連

- **PostgreSQLのインデックス（B-Tree）**: `CREATE INDEX` で作られるB-TreeはBSTの発展系。`WHERE id > 100 AND id < 200` のような範囲クエリが速いのはBSTの特性そのもの
- **ソート済みデータへの効率的アクセス**: Neonで `ORDER BY created_at` のクエリを発行するとき、`created_at` にインデックスがあればB-Treeをスキャンするだけ
- **API のレート制限実装**: タイムスタンプ付きリクエスト履歴をSortedListで管理すると、時間窓内のカウントが O(log n) で取れる
- **Cloud Run のオートスケール判定**: コンテナのメトリクスをヒープ（ヒープもBSTの応用）で管理するケースがある

### 判断指針

| 用途                   | 選択肢                              |
|------------------------|-------------------------------------|
| キーの存在確認だけ     | ハッシュテーブル（O(1)）            |
| 範囲検索・順序走査     | BST系 or DBインデックス             |
| 優先度付き取り出し     | ヒープ（次回のトピック）            |
| 大量データの永続化     | PostgreSQL B-Tree インデックス      |
