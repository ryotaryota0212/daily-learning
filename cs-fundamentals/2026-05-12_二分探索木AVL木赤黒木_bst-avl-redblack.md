# 二分探索木・AVL木・赤黒木の基本と計算量

## 概要

二分探索木（BST）は「左 < 親 < 右」の順序を保ちながらデータを管理するツリー構造。検索・挿入・削除がすべて木の高さ O(h) で完了する。しかし偏った挿入で高さが O(n) になる欠陥がある。これを解決したのが自己平衡木（AVL木・赤黒木）。RDBMSのB-Treeインデックスの原型であり、言語標準ライブラリ（Java TreeMap、C++ std::map）の内部実装でもある。「なぜ sorted dict が O(log n) なのか」を理解する基盤。

---

## 仕組みの要点

### 二分探索木（BST）

- 各ノードは `left < node.val < right` を満たす
- **検索**: ルートから比較しながら左右に降りる → O(h)
- **挿入**: 検索と同じ経路の末尾に追加 → O(h)
- **削除**: ノードが子を2つ持つ場合は「中順後継者（右部分木の最小値）」と入れ替えて削除
- **弱点**: 昇順データを挿入すると一直線になり h = n → O(n) に劣化

```
挿入: 5, 3, 7, 1, 4 の場合
        5
       / \
      3   7
     / \
    1   4   ← バランスが取れている

挿入: 1, 2, 3, 4, 5 の場合
1
 \
  2
   \
    3  ← 線形リストと等価（最悪ケース）
```

### AVL木

- **条件**: 各ノードで `|左の高さ - 右の高さ| ≤ 1`
- 挿入・削除後に条件違反が起きたら**回転（rotation）**で修正
- 回転の種類: 右回転 / 左回転 / 左右回転 / 右左回転（4パターン）
- 回転のたびに高さ情報を更新するコストがある
- **特徴**: 検索が多いワークロードに向く（赤黒木より厳密なバランス）

```
左回転の例:
  A               B
   \             / \
    B     →     A   C
     \
      C
```

### 赤黒木

- **条件（5つのルール）**:
  1. 各ノードは赤か黒
  2. ルートは黒
  3. 赤ノードの子は必ず黒（赤が連続しない）
  4. どのノードからも葉（NIL）までの黒ノード数は等しい（黒高さ一定）
  5. 葉（NIL）は黒
- AVL木より条件が緩いため回転回数が少ない → **挿入・削除が速い**
- 高さ上限: 2 * log₂(n+1)（AVL木より少し高くなりうる）
- **特徴**: 書き込みが多いワークロード向き。Linux のプロセス管理（CFS スケジューラ）にも使用

## 計算量・パフォーマンス特性

| 操作 | BST（平均） | BST（最悪） | AVL木 | 赤黒木 |
|------|------------|------------|-------|--------|
| 検索 | O(log n)   | O(n)       | O(log n) | O(log n) |
| 挿入 | O(log n)   | O(n)       | O(log n) | O(log n) |
| 削除 | O(log n)   | O(n)       | O(log n) | O(log n) |
| 回転コスト | - | - | O(log n) 回まで | O(1) 回まで |
| バランス | 保証なし | 保証なし | 厳密 | 緩め |

- **AVL木の回転**: 挿入で最大1回、削除で O(log n) 回の回転が必要
- **赤黒木の回転**: 挿入・削除ともに最大3回（色の変更は多いが安価）
- 空間計算量: どちらも O(n)（各ノードに色 or 高さ情報を1ビット追加）

## コード例（Python: BST の検索・挿入）

```python
class Node:
    def __init__(self, val):
        self.val = val
        self.left = self.right = None

class BST:
    def __init__(self):
        self.root = None

    def insert(self, val):
        def _insert(node, val):
            if not node:
                return Node(val)
            if val < node.val:
                node.left = _insert(node.left, val)
            elif val > node.val:
                node.right = _insert(node.right, val)
            return node
        self.root = _insert(self.root, val)

    def search(self, val):
        node = self.root
        while node:
            if val == node.val: return True
            node = node.left if val < node.val else node.right
        return False
```

## よくある誤解・落とし穴

- **「BSTは常にO(log n)」は誤り** — 平均ケースの話。ランダムデータなら O(log n) に近いが、ソート済みデータは O(n)
- **AVL木が常に赤黒木より速いわけではない** — 検索ヘビーなら AVL、挿入・削除ヘビーなら赤黒木が有利
- **赤黒木の実装は複雑** — 色のルール違反を修正する「リバランス」は4パターン×挿入削除でケースが多い。実務では標準ライブラリを使う
- **Pythonの `sortedcontainers.SortedList` はスキップリスト** — AVL/赤黒木ではなく別の自己平衡構造。O(log n) は同じ
- **削除の「中順後継者」忘れ** — 子が2つのノード削除時、単純に削除するとBST条件が崩れる

## 実務での使いどころ

### FastAPI + Neon + Cloud Run スタック との関連

- **Neon（PostgreSQL）のインデックス**: B-Treeインデックスは赤黒木を多分木に拡張したもの。`CREATE INDEX` の計算量の根拠を理解できる
- **範囲クエリの効率**: `WHERE created_at BETWEEN ...` が速いのは B-Tree が中順巡回で連続値を効率的に返せるから（ハッシュインデックスは等値比較のみ）
- **FastAPI のルーティング**: パスパラメータのマッチングに内部でトライ木（ツリー構造）を使うフレームワークがある
- **Cloud Run の自動スケーリング**: コンテナのメトリクス管理にプライオリティキュー（ヒープ）が使われるが、順序付きデータの管理全般に自己平衡木の概念が応用される
- **ローカル開発での応用**: `sortedcontainers.SortedDict` を使うことで「ソート済みの辞書」を O(log n) で維持できる。時系列データのインメモリ管理に有用
