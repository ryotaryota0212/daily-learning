# B-Treeインデックスの仕組みと計算量

## 概要

RDBMSのインデックスで最も広く使われるデータ構造。O(log N)の検索・挿入・削除を保証し、ディスクI/Oを最小化するよう設計されている。「なぜインデックスを貼るだけで検索が速くなるのか」「なぜ全カラムに貼ってはいけないのか」を理解するための核心。Neon(PostgreSQL)でのクエリ最適化に直結する知識。

---

## 仕組みの要点

### B-Treeの構造

- **多分岐の平衡木**: 2分木ではなく1ノードに多数のキーを持つ。木の深さが浅くなりディスクI/Oを削減
- **ページ単位**: PostgreSQLはデフォルト8KBのページ単位でディスク読み書き。1ノード≒1ページ
- **常にバランス**: 全リーフが同じ深さ → 最悪でもO(log N)を保証

### 実際はB+Tree

```
          [30 | 60]          ← 内部ノード（キーのみ）
         /    |    \
    [10|20] [40|50] [70|80]  ← リーフ（実データへのポインタ）
       ↔       ↔      ↔      ← リーフ同士は連結リスト
```

- 内部ノード: キーと子ポインタのみ（データなし）→ 1ページに多くのキーが入る
- リーフノード: 実データ（ヒープポインタ）を保持
- リーフ同士が連結リスト → **範囲検索が効率的**（B-Treeとの最大の違い）

### 検索の流れ

1. ルートノード（通常キャッシュ済み）から開始
2. キーを比較して子ノードへ降りる（各ステップでディスクI/O 1回）
3. リーフノードでヒープポインタを取得 → 実テーブルのレコードにアクセス
4. 1億行でも深さは4〜5程度（各ノードに数百キーが入るため）

### 挿入・削除

- **挿入**: リーフにキー追加 → ページが溢れたら「分割（スプリット）」して親に伝播
- **削除**: キー削除 → ページが過疎になったら隣接ノードと「マージ」
- スプリット/マージはルートまで伝播することがある（まれ）

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 検索（等値） | O(log N) |
| 検索（範囲） | O(log N + K)　K=結果件数 |
| 挿入 | O(log N) |
| 削除 | O(log N) |
| フルスキャン | O(N) |

## コード例（PostgreSQL）

```sql
-- インデックス作成
CREATE INDEX idx_users_email ON users(email);

-- 実行計画確認（Index Scan か Seq Scan か）
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'test@example.com';
-- → "Index Scan using idx_users_email"
-- → "Buffers: shared hit=3"  ←ページアクセス数≒木の深さ

-- 複合インデックス（Leftmost Prefix ルール）
CREATE INDEX idx_orders_uid_date ON orders(user_id, created_at);
SELECT * FROM orders WHERE user_id = 1 AND created_at > '2026-01-01'; -- ✅ 効く
SELECT * FROM orders WHERE created_at > '2026-01-01';                  -- ❌ 効かない

-- 部分インデックス（サイズ削減）
CREATE INDEX idx_active_orders ON orders(user_id) WHERE status = 'active';
```

## よくある誤解・落とし穴

- **「インデックスは多いほど良い」**: 挿入・更新・削除のたびにインデックスも更新。書き込みが多いテーブルでは逆にボトルネック
- **「低カーディナリティに貼る」**: bool型や性別など値の種類が少ないカラムはヒット率が高くフルスキャンより遅くなる場合も
- **「WHERE句に使えばOK」**: 関数適用するとインデックスが効かない
  - ❌ `WHERE DATE(created_at) = '2026-01-01'`
  - ✅ `WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'`
- **「複合インデックスの順序は関係ない」**: Leftmost Prefix ルールにより先頭カラムから順に使われる。順番が重要

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neon(PostgreSQL)**: 外部キー結合カラム・WHERE頻出カラムはインデックス有無を必ず確認。`EXPLAIN ANALYZE`でSeq Scanが出たら要検討
- **スロークエリ調査**: Neonのクエリ統計（`pg_stat_statements`）でボトルネックを特定 → インデックス追加で解消できるケースが多い
- **部分インデックス**: 「アクティブなレコードだけ」など条件付きインデックスでサイズと更新コストを削減
- **Cloud Run + コネクションプーリング**: I/O削減効果を最大化するにはPgBouncer/Supavisorとの組み合わせが有効。インデックスでディスクI/Oを減らし、プーリングでコネクション確立コストを減らす
