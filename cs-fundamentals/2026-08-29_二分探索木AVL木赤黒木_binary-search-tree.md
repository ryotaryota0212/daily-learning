# 二分探索木・AVL木・赤黒木の基本と計算量

## 概要

二分探索木（BST）は「左 < 親 < 右」という規則で数値を整理する木構造。この規則があることで、探索・挿入・削除を平均O(log n)で実現できる。ただし、入力が偏ると木が偏って最悪O(n)に劣化する。AVL木・赤黒木はその問題を「自動で木のバランスを保つ」ことで解決した発展形。実務ではデータベースのインデックスやOSのプロセス管理テーブル（Linux CFS）に赤黒木が使われており、「なぜO(log n)が保証されるか」を理解することがDB・OSのボトルネックを読む力につながる。

---

## 仕組みの要点

### 二分探索木（BST）

- 各ノードが「左の子 < 自分 < 右の子」を満たす木
- **探索**：ルートから比較して左右に降りていくだけ
- **挿入**：探索と同じ経路で空きスポットを探してノードを追加
- **削除**：削除するノードが子を持つ場合は「中順後継（右部分木の最小値）」で置き換える
- **問題**：昇順でデータを挿入すると木が右に一直線になり、高さがn→O(n)に劣化

```
昇順挿入の例:
1
 \
  2
   \
    3    ← ほぼ連結リスト。探索がO(n)
     \
      4
```

### AVL木

- 各ノードで「左右の部分木の高さの差（バランス因子）が±1以内」を保証
- 挿入・削除のたびに**回転操作**（左回転・右回転・左右回転・右左回転）で木を整形
- 高さが常にO(log n)に保たれるため、全操作がO(log n)保証
- 厳格にバランスを保つため**挿入・削除のコストが高い**。読み取りが多いシナリオ向き

```
右回転のイメージ:
    z              y
   /              / \
  y       →      x   z
 / \                 /
x   T3              T3
```

### 赤黒木

- 各ノードを「赤」か「黒」に塗り、5つのルールで色の不変条件を維持
  1. ノードは赤か黒
  2. ルートは黒
  3. 葉（NILノード）は黒
  4. 赤ノードの子は必ず黒
  5. どの葉からルートまでの経路も同じ数の黒ノードを持つ
- これらの条件から「最長経路 ≤ 2 × 最短経路」が証明でき、高さはO(log n)
- AVL木より回転が少なくて済む → **挿入・削除が速い**。実装がトレードオフで選ばれる
- JavaのTreeMap、LinuxカーネルのスケジューラCFSが赤黒木を採用

## 計算量・パフォーマンス特性

| 操作 | BST（平均） | BST（最悪） | AVL木 | 赤黒木 |
|------|------------|------------|-------|--------|
| 探索 | O(log n)   | O(n)       | O(log n) | O(log n) |
| 挿入 | O(log n)   | O(n)       | O(log n) | O(log n) |
| 削除 | O(log n)   | O(n)       | O(log n) | O(log n) |
| 空間 | O(n)       | O(n)       | O(n)  | O(n) |

- **AVL木**: 回転が多い分、読み取り偏重ワークロードで有利（木の高さが厳密に最小）
- **赤黒木**: 書き込みが多いワークロードで有利。高さの保証はAVLより緩いが実用上十分

## コード例（Python: BST の基本）

```python
class Node:
    def __init__(self, val):
        self.val = val
        self.left = self.right = None

class BST:
    def __init__(self):
        self.root = None

    def insert(self, val):
        def _ins(node, val):
            if not node:
                return Node(val)
            if val < node.val:
                node.left = _ins(node.left, val)
            elif val > node.val:
                node.right = _ins(node.right, val)
            return node
        self.root = _ins(self.root, val)

    def search(self, val):
        node = self.root
        while node:
            if val == node.val:
                return True
            node = node.left if val < node.val else node.right
        return False
```

## よくある誤解・落とし穴

- **「BSTは常にO(log n)」は誤り**。挿入順によって木が偏るため、最悪O(n)になる。ランダムな入力でも期待値としてO(log n)になるだけ
- **「AVL木と赤黒木はどちらも同じ」は誤り**。AVL木は高さをより厳密に制約するため、探索は速いが挿入・削除のコストが高い
- **「回転はO(n)の操作」は誤り**。1回の回転はポインタの付け替えだけなのでO(1)
- **削除の実装**：「中順後継」を使うパターンだけでなく「中順先行（左部分木の最大値）」を使う実装もある。テキストによって違うので混乱しやすい
- **Pythonのsortedcontainersライブラリ**は内部的にソート済みリストで実装されており、赤黒木ではない（ベンチマークで誤解されやすい）

## 実務での使いどころ

### FastAPI + Neon + Cloud Runスタックとの関連

- **NeonのBツリーインデックス**：PostgreSQLが内部で使うBツリーはBSTの多分岐版。`=`, `<`, `>`, `BETWEEN` クエリがO(log n)になる理由が理解できる
  ```sql
  -- このクエリがO(log n)で動く理由はBツリーの構造から
  SELECT * FROM orders WHERE created_at BETWEEN '2026-01-01' AND '2026-12-31';
  ```
- **インデックスの設計判断**：挿入が多いテーブルはインデックスの再バランスコストが高い。赤黒木の知識があると「なぜ過剰なインデックスが書き込みを遅くするか」が説明できる
- **FastAPIでのソート済みデータ構造**：Python標準の`sortedcontainers.SortedList`やheapq（ヒープ）と組み合わせてリアルタイムランキングAPIを実装するとき、平衡木の計算量保証の意味がわかる
- **Cloud Runのスケールアウト**：リクエスト数のトラッキングなどでO(log n)の挿入・探索が必要な場合、辞書（ハッシュテーブル）で十分なケースとBSTが必要なケースを区別できる（範囲クエリが必要かどうか）
