# B-Treeインデックスの仕組みと計算量

## 概要

B-TreeはPostgreSQLやMySQLなどほぼすべてのRDBMSがデフォルトで使うインデックス構造。  
「なぜINDEXを張ると速くなるか」「なぜ複合インデックスの順序が重要か」を理解する土台。  
Neonを使うプロジェクトでクエリが遅いとき、実行計画を読んで改善できる力に直結する。

---

## 仕組みの要点

### B-Treeとは
- **Balanced Tree（バランス木）**の一種。全リーフノードが同じ深さ
- 各ノードに複数のキーを持てる（二分木との違い）
- ディスクI/Oを最小化するため、1ノード＝1ページ（通常8KB）に設計

### ノード構造
```
[内部ノード]  10 | 30 | 50
              ↓    ↓    ↓    ↓
            [1-9][11-29][31-49][51-...]  ← 子ノード（またはリーフ）
```

- **内部ノード**: キーと子ポインタのみ保持
- **リーフノード**: キー＋実データのポインタ（ヒープタプルへのctid）を保持
- **双方向リンク**: リーフ同士が繋がっており、範囲スキャンが高速

### 検索の流れ（`WHERE age = 25`）
1. ルートノードを読み込む（1 I/O）
2. キー比較で子ノードへ降りる（深さ分のI/O）
3. リーフに到達 → ctidでヒープを読む（1 I/O）

### 挿入の流れ
1. 挿入位置のリーフを見つける
2. リーフに空きがあれば追加
3. **空きがなければ分割（スプリット）**: ノードを2つに分け、中央キーを親へ昇格
4. 親も満杯なら再帰的に分割 → ルートまで波及する場合あり

## 計算量・パフォーマンス特性

| 操作 | 計算量 | 備考 |
|------|--------|------|
| 検索（等値） | O(log n) | 木の高さ分のI/O |
| 範囲検索 | O(log n + k) | k=ヒット件数。リーフ横断が速い |
| 挿入 | O(log n) | スプリット発生時もO(log n) |
| 削除 | O(log n) | アンダーフロー時は兄弟から借用or統合 |

**木の高さの目安**: n=100万行、1ノード=200キー → 高さ≒3〜4層。ほぼどんな規模でもI/Oは数回。

## コード例（PostgreSQLの実行計画確認）

```sql
-- インデックス作成
CREATE INDEX idx_users_age ON users(age);

-- 実行計画確認
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE age = 25;

-- 出力例（抜粋）
-- Index Scan using idx_users_age on users
--   Index Cond: (age = 25)
--   Buffers: shared hit=4  ← 4ページ読んだ（木の高さ相当）

-- 複合インデックス（順序が重要）
CREATE INDEX idx_users_age_name ON users(age, name);
-- WHERE age = 25 AND name = 'Alice'  → 使われる
-- WHERE name = 'Alice'               → 使われない（先頭キーから一致必須）
```

## よくある誤解・落とし穴

- **「インデックスは多いほど良い」は誤り**  
  → 挿入・更新時にB-Treeも更新されるので書き込みコストが増加

- **左端カラム一致の原則を忘れる**  
  → 複合インデックス `(a, b, c)` は `WHERE b = 1` では使えない（aが先頭）

- **低カーディナリティ列へのインデックスは逆効果になることがある**  
  → `WHERE is_active = true` が全行の90%ならSeqScanの方が速い。プランナが判断するが、統計が古いと誤判断

- **インデックスオンリースキャンを活用できていない**  
  → SELECT列がすべてインデックスに含まれると、ヒープアクセス不要になり大幅に速くなる（covering index）

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neonはpostgres互換** → `EXPLAIN ANALYZE`がそのまま使える。スロークエリをローカルのpsqlで調査可能
- **Cloud Runはコールドスタートがある** → コネクションプールが効くが、初回クエリが重いとタイムアウトしやすい。よく使うクエリにインデックスを張ってI/O削減
- **複合インデックスの設計**: FastAPIのフィルタ条件（`user_id`, `created_at`など）をWHERE句に使うなら `(user_id, created_at)` の順で複合インデックスを作る
- **Neonのブランチ機能でインデックス実験**: 本番データのブランチを作り、`EXPLAIN ANALYZE`でインデックス追加の効果を安全に検証できる
