# 二分探索木・AVL木・赤黒木の基本と計算量

## 概要

二分探索木（BST）は「左 < 親 < 右」の順序不変条件を持つ木構造で、探索・挿入・削除を効率的に行える。
ただし偏りが生じると最悪 O(n) に退化するため、AVL木・赤黒木のような**自己平衡木**が実務で使われる。
Pythonの `sortedcontainers`、C++ の `std::map`、Java の `TreeMap` はすべて赤黒木ベース。
DB のインデックス設計やメモリ内のランキング処理を理解するうえで不可欠な基礎。

---

## 仕組みの要点

### 二分探索木（BST）

- 各ノードが `左サブツリー < ノード値 < 右サブツリー` を満たす
- 探索: ルートから比較しながら左右に降りる
- **問題点**: 昇順に挿入すると右方向にしか伸びず「連結リスト」と同じ形になる

```
挿入順: 1, 2, 3, 4, 5
1
 \
  2
   \
    3   ← 最悪ケース: 高さ = n
```

### AVL木

- 各ノードで「左右の高さの差（バランス因子）≤ 1」を強制維持
- 挿入・削除の都度、**回転（rotation）** で木を修正
  - 左回転 / 右回転 / 左右二重回転 / 右左二重回転 の4パターン
- 高さは常に O(log n) を保証

```
不均衡を検出したら回転:
    z              y
   / \           /   \
  y   T4  →    x     z
 / \          / \   / \
x   T3       T1 T2 T3 T4
```

### 赤黒木

- 各ノードを**赤か黒**に色付けし、5つの性質を維持:
  1. 全ノードは赤か黒
  2. ルートは黒
  3. 赤ノードの子は必ず黒（赤が連続しない）
  4. 任意のノードからリーフまでの黒ノード数は等しい（黒高さ）
  5. リーフ（NIL）は黒
- AVL木より**回転回数が少ない**（挿入は最大2回転）→ 書き込み多用途に向く
- 高さは最大 2·log(n+1)

---

## 計算量・パフォーマンス特性

| 操作     | BST（平均） | BST（最悪） | AVL木    | 赤黒木   |
|----------|-------------|-------------|----------|----------|
| 探索     | O(log n)    | O(n)        | O(log n) | O(log n) |
| 挿入     | O(log n)    | O(n)        | O(log n) | O(log n) |
| 削除     | O(log n)    | O(n)        | O(log n) | O(log n) |
| 空間     | O(n)        | O(n)        | O(n)     | O(n)     |

- **AVL木**: 探索が多い → より厳密に高さを抑えるため有利
- **赤黒木**: 挿入・削除が多い → 回転コストが低いため有利
- どちらも最悪ケースで O(n) になる純粋 BST より安全

## コード例（Python: BST の基本操作）

```python
class Node:
    def __init__(self, val):
        self.val = val
        self.left = self.right = None

class BST:
    def __init__(self):
        self.root = None

    def insert(self, val):
        def _ins(node, v):
            if not node:
                return Node(v)
            if v < node.val:
                node.left = _ins(node.left, v)
            elif v > node.val:
                node.right = _ins(node.right, v)
            return node
        self.root = _ins(self.root, val)

    def search(self, val):
        node = self.root
        while node:
            if val == node.val: return True
            node = node.left if val < node.val else node.right
        return False
```

## よくある誤解・落とし穴

- **「BSTは常に速い」** → 挿入順が偏ると O(n)。本番では必ず自己平衡木を使う
- **「AVL木は赤黒木より速い」** → 探索特化なら正しいが、書き込みが多ければ赤黒木が優位
- **「ハッシュテーブルで代替できる」** → ハッシュテーブルは順序を持たない。範囲クエリ（a ≤ x ≤ b）や昇順イテレーションが必要な場面では BST 系が不可欠
- **回転の実装ミス**: 子ポインタの付け替え漏れがバグの温床。実務では検証済みライブラリを使うこと

## 実務での使いどころ

### FastAPI + Neon + Cloud Run スタックとの関連

| 場面 | 具体例 |
|------|--------|
| **Neon (PostgreSQL) のインデックス** | B-Tree インデックスは BST 系の考え方を多次元に拡張したもの。`CREATE INDEX` が内部的に平衡木を構築している（→ 次回トピック26で詳解） |
| **APIのランキング・ソート済みセット** | Redisの `ZADD/ZRANGE` はスキップリスト（平衡木の近似）。スコア順の取得が O(log n) |
| **FastAPIのルートマッチング** | フレームワーク内部でルートをトライ木（Trie）や辞書順ツリーで管理するケースがある |
| **メモリ内キャッシュ** | 有効期限つきキャッシュをプライオリティキュー（ヒープ）や BST で実装する際に原理を理解していると実装・デバッグが早い |

平衡木の「なぜ O(log n) が保証されるか」を理解しておくと、DBの `EXPLAIN ANALYZE` でインデックススキャンのコスト見積もりを直感的に読めるようになる。
