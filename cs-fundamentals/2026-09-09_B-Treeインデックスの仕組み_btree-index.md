# B-Treeインデックスの仕組みと計算量

## 概要

RDBMSが高速検索を実現する根幹がB-Treeインデックス。PostgreSQL（Neon含む）のデフォルトインデックス型であり、フルスキャンとの差が何百倍にもなる局面を支える。「なぜインデックスがあると速いのか」「どういうクエリでは効かないのか」を原理から理解することで、クエリチューニングの判断力が身につく。

---

## 仕組みの要点

### データ構造

```
          [30 | 70]              ← ルートノード
         /    |    \
   [10|20] [40|60] [80|90]      ← 内部ノード（キーのみ）
   /  |  \   ...
[葉] [葉] [葉]                  ← 葉ノード（キー＋実データへのポインタ）
```

- **多分木**：各ノードが複数のキーと子ポインタを持つ（2分木より広い）
- **葉ノード**は双方向リンクでつながっており、**範囲スキャン**が効率的
- **バランス保証**：すべての葉が同じ深さ → 検索が常にO(log n)
- ノードサイズ = ディスクの**ページサイズ（通常8KB）** に合わせて設計
  - ディスクI/Oを最小化するための設計思想

### 検索の流れ

1. ルートから比較を繰り返し、対象キーのある葉ノードへ降りる
2. 葉ノードでキーを見つけ、ヒープ（テーブル本体）のタプルポインタを取得
3. ヒープからタプルを読み込む（**インデックスオンリースキャン**の場合は省略可）

### 挿入・削除

- 挿入でノードが溢れた（overflow）→ **分割（split）** して親に昇格
- 削除でノードが空きすぎた（underflow）→ **マージ**か**再分配**
- どちらも木の高さを一定に保つ自己バランス操作

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 検索（点検索） | O(log n) |
| 範囲検索 | O(log n + k)　※k = 結果件数 |
| 挿入 | O(log n) |
| 削除 | O(log n) |
| フルスキャン | O(n) |

- **n = 1億行**でも木の高さは約4〜5段（log₁₀₀(1億) ≈ 4）
- 1ノードに格納できるキー数が多いほど木が浅くなる → ページサイズが重要

## コード例（PostgreSQL / SQL）

```sql
-- インデックス作成
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 実行計画の確認
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM orders WHERE user_id = 42;

-- 複合インデックス（左端の列から順に使われる）
CREATE INDEX idx_orders_user_created 
  ON orders(user_id, created_at DESC);

-- インデックスオンリースキャンを活用（カバリングインデックス）
CREATE INDEX idx_orders_cover 
  ON orders(user_id) INCLUDE (status, total);
```

## よくある誤解・落とし穴

- **低カーディナリティ列へのインデックスは無効**  
  `is_active`（true/false）にインデックスを張っても、半分のデータを読むならフルスキャンの方が速い場合がある

- **複合インデックスは順序が命**  
  `(user_id, created_at)` のインデックスは `WHERE created_at = X` では使えない（左端の原則）

- **LIKE検索の落とし穴**  
  `LIKE 'foo%'` は使える。`LIKE '%foo'` は使えない（先頭ワイルドカード）

- **インデックスが使われない関数適用**  
  `WHERE DATE(created_at) = '2026-01-01'` → インデックス不使用  
  `WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'` → 使用可

- **インデックスの書き込みコスト**  
  INSERT/UPDATE/DELETE でもインデックスの更新が走る。不要なインデックスは書き込みを遅くする

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neon は PostgreSQL 互換** → B-Treeインデックスの挙動は標準と同じ
- FastAPI のエンドポイントで `user_id` や `created_at` でフィルタするクエリが多い → 複合インデックス `(user_id, created_at DESC)` を検討
- `EXPLAIN ANALYZE` の出力で `Seq Scan` が出たらインデックスの追加を検討、`Index Scan` が出ていれば機能している
- Neon のブランチ機能でステージング環境にインデックスを先に適用してパフォーマンス比較が容易
- Cloud Run はサーバーレスでコールドスタートがあるため、接続プールとインデックスの両方で**クエリ単体の実行時間**を削ることが重要
