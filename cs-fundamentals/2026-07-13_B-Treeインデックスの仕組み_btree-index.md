# B-Treeインデックスの仕組みと計算量

## 概要

B-TreeはRDBMS（PostgreSQL、MySQLなど）のデフォルトインデックス構造。
クエリの高速化に「とりあえずインデックスを貼る」だけでなく、**なぜ速くなるか・遅くなるか**を理解することで、実行計画の読み方やインデックス設計の判断力が上がる。
特にNeon（PostgreSQL互換）を使う個人開発では、テーブルが大きくなってからのクエリ劣化を防ぐ基本知識。

---

## 仕組みの要点

### B-Treeの構造

```
              [30 | 60]              ← ルートノード
            /     |     \
      [10|20]  [40|50]  [70|80]     ← 内部ノード
      /  |  \   ...      ...
   [5] [15] [25] ...               ← リーフノード（実データ or ROWIDへのポインタ）
```

- **ノード** = ディスクの1ページ（PostgreSQLは8KB）
- **リーフノード** = ソート済みキー + ヒープページへのポインタ (ctid)
- **内部ノード** = 子ノードへの経路情報のみ（データを持たない）

### 検索の流れ（`WHERE id = 42`）

1. ルートから開始し、キーと比較して左/中/右の子ノードへ進む
2. リーフに到達したらポインタを使い、ヒープページから実行を取得
3. ディスクI/Oはツリーの高さ分だけ（高さ ≈ log_b(N)、b=分岐数≈数百）

### B-Tree vs 二分探索木の違い

| 項目 | BST | B-Tree |
|------|-----|--------|
| 分岐数 | 2 | 数百（ページサイズに依存）|
| 高さ | O(log₂N) | O(log_b N) ← bが大きいので低い |
| ディスクI/O | 多い | 少ない（=高速）|
| 狙い | メモリ上 | ディスク上の効率化 |

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 検索 | O(log N) |
| 挿入 | O(log N)（ノード分割が起きても同じオーダー）|
| 削除 | O(log N)（再バランシング含む）|
| 範囲スキャン | O(log N + K)（K = 取得件数）|

- **Nの増加に対して高さはほぼ増えない**: 1億行でも高さ4〜5程度
- **範囲クエリに強い**: リーフノードは双方向リンクリストで繋がっており、`BETWEEN` や `ORDER BY` が効率的

## コード例（PostgreSQL）

```sql
-- インデックス作成
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 実行計画で確認
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 123;

-- 複合インデックス（左端の列から使われる）
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);

-- これは使われる（左端のuser_idを含む）
SELECT * FROM orders WHERE user_id = 123 AND created_at > '2026-01-01';

-- これはインデックスが使われない（左端を飛ばしている）
SELECT * FROM orders WHERE created_at > '2026-01-01';
```

## よくある誤解・落とし穴

- **「インデックスは常に速い」は誤り**: 取得行数が多い場合（全体の5〜10%超）、シーケンシャルスキャンの方が速いことがある
- **低カーディナリティ列は効果薄**: `status` (値が3種類のみ) などはインデックスを貼っても恩恵が小さい
- **`LIKE '%foo%'` はインデックス不使用**: 前方一致（`'foo%'`）は使えるが、中間・後方一致は使えない
- **複合インデックスの列順が重要**: `(a, b)` のインデックスは `WHERE a=1` には使えるが `WHERE b=1` だけでは使えない（先頭列の原則）
- **書き込みコストも発生する**: インデックスが多いとINSERT/UPDATE/DELETEが遅くなる。不要なインデックスは定期的に見直す

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **外部キー列には必ずインデックスを**: `user_id`, `post_id` などJOINで使う列。PostgreSQLは外部キー制約でも自動作成されない
- **`EXPLAIN ANALYZE` を開発中に習慣化**: Neonのコンソールかpsqlで実行計画を確認。`Seq Scan` が出たらインデックス追加を検討
- **Cloud Runのコールドスタート × N+1クエリ**: 遅いクエリはCloud Runのタイムアウトにも響く。インデックスで1クエリを速くする方が根本解
- **Neon Autoscaleとの相性**: 接続数が少ないサーバーレス環境では、インデックスで1クエリあたりのI/Oを減らすことが特に重要
- **マイグレーション時の注意**: 本番データが多い場合、`CREATE INDEX CONCURRENTLY` でロックを回避する
