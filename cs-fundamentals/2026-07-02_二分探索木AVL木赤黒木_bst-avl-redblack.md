# 二分探索木・AVL木・赤黒木の基本と計算量

## 概要

二分探索木（BST）は「左 < 根 < 右」の順序を保つ木構造。検索・挿入・削除をすべて O(log n) で行える理想的な構造だが、入力次第で偏って O(n) に劣化する。AVL木・赤黒木はそれを防ぐ「自己平衡型BST」。実務では直接使うよりも、PostgreSQL の B-Tree インデックスや Python の `sortedcontainers`、Java の `TreeMap` の内部実装として登場する。「ソート済み状態を保ちながら高速に検索・挿入・削除したい」場面で本質的な価値を発揮する。

---

## 仕組みの要点

### 二分探索木（BST）

- **制約**: 任意のノード N に対して `左部分木のすべてのキー < N.key < 右部分木のすべてのキー`
- **検索**: 根から「探したい値 < 現在ノード → 左へ、> → 右へ」を繰り返す
- **挿入**: 検索と同じ経路をたどり、空の場所に置く
- **削除**: 子が0個→そのまま削除、1個→付け替え、2個→「右部分木の最小値（中順後継者）」と交換してから削除
- **弱点**: ソート済みデータを順に挿入すると一直線の連結リストになり O(n) に退化

```
挿入順: 3, 1, 4, 1, 5, 9 の場合
       3
      / \
     1   4
          \
           5
            \
             9
← これはまだ良いケース。1,2,3,4,5 と入れると右に連なる
```

### AVL木

- BSTに「各ノードの左右の高さの差（バランス因子）を常に -1, 0, +1 に保つ」制約を追加
- 挿入・削除後に違反が生じたら **回転操作**（左回転・右回転・二重回転）で修正
- **左回転**: 右の子を自分の位置に上げ、自分が左の子になる
- 最悪でも高さが O(log n) に保たれる → 検索・挿入・削除すべて O(log n) 保証

### 赤黒木

- AVL木より緩い平衡条件（「赤いノードが連続しない」「根から葉までの黒ノード数が等しい」など5つのルール）を使う
- 回転回数が少なく **挿入・削除が速い**（最大2回の回転）
- AVL木は検索が少し速いが、挿入・削除が多いユースケースでは赤黒木が有利
- Linux カーネルのスケジューラ（CFS）、C++ の `std::map`、Java の `TreeMap` に使用

## 計算量比較

| 操作     | BST（最良）| BST（最悪）| AVL木     | 赤黒木    |
|----------|-----------|-----------|----------|----------|
| 検索     | O(log n)  | O(n)      | O(log n) | O(log n) |
| 挿入     | O(log n)  | O(n)      | O(log n) | O(log n) |
| 削除     | O(log n)  | O(n)      | O(log n) | O(log n) |
| 空間     | O(n)      | O(n)      | O(n)     | O(n)     |

- AVL木は赤黒木より高さが低い（より厳密に平衡）→ 検索が若干速い
- 赤黒木は挿入・削除時の回転が少ない → 書き込み多用途に向く

## コード例（Python: シンプルなBST実装）

```python
class Node:
    def __init__(self, key):
        self.key = key
        self.left = self.right = None

class BST:
    def __init__(self):
        self.root = None

    def insert(self, key):
        def _insert(node, key):
            if node is None:
                return Node(key)
            if key < node.key:
                node.left = _insert(node.left, key)
            elif key > node.key:
                node.right = _insert(node.right, key)
            return node
        self.root = _insert(self.root, key)

    def search(self, key):
        node = self.root
        while node:
            if key == node.key:
                return True
            node = node.left if key < node.key else node.right
        return False
```

実務で自己平衡が必要な場合は `sortedcontainers.SortedList`（内部はB-Tree風）を使う。

---

## よくある誤解・落とし穴

- **「BSTはO(log n)」は保証ではない**: 入力がソート済みだと O(n) に退化する。面接でよく問われる
- **AVL木の回転が複雑**: 二重回転（左右回転・右左回転）の向きを混同しやすい。「どのノードが不均衡か」を先に特定する
- **赤黒木 = 「なんとなく高速」ではない**: 検索のみなら AVL木の方が速い。書き込みが多い場合に赤黒木が優位
- **削除が一番難しい**: BST削除の「2つの子を持つケース」を正確に実装できるかが実力の試金石

## 実務での使いどころ（FastAPI + Neon + Cloud Runスタック）

- **Neon（PostgreSQL）のインデックス**: B-Tree インデックスは赤黒木の考え方を応用した多分木。`EXPLAIN ANALYZE` でインデックスが効いているか確認する際、背後の原理を知っていると実行計画が読みやすい
- **FastAPIのルーティング**: 多くのWebフレームワークは内部でトライ木（プレフィックス木）を使うが、BST的な発想（範囲検索、順序保証）はレンジクエリ最適化の発想と共通
- **ソート済み集合が必要な場面**: ランキング・スコアボードの実装で「上位K件を高速に取り出す」には優先度付きキュー（ヒープ）かBSTが適切。Redisの `ZSET`（ソート済みセット）は内部でスキップリスト＋ハッシュテーブルを使い同様の問題を解く
