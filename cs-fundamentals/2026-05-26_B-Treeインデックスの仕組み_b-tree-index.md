# B-Treeインデックスの仕組みと計算量

## 概要

B-Tree（Balanced Tree）は、PostgreSQL・MySQL・SQLiteなど主要RDBMSのインデックス実装の核心。  
インデックスの有無で検索が O(N) → O(log N) に変わる理由を知れば、クエリのボトルネックを自力で特定・解消できる。  
Neonを使うFastAPIアプリでも、テーブル設計とインデックス設計の判断に直結する知識。

---

## 仕組みの要点

### B-Treeの構造

```
         [30 | 70]                ← ルートノード
        /    |    \
  [10|20] [40|50|60] [80|90]     ← 内部ノード
  /  |  \              |   \
[葉] [葉] [葉]        [葉] [葉]  ← リーフノード（実データへのポインタ）
```

- **ノード** = ディスクの1ページ（通常8KB）に収まるよう設計
- **リーフノード**：実際の行へのポインタ（または主キーの値）を持つ
- **内部ノード**：検索を絞り込むキー値のみ持つ
- 全リーフが同じ深さ → 「Balanced（平衡）」が保証される

### 検索の動き（例：値=45を探す）

1. ルート `[30|70]` を読む → 30<45<70 なので中央の子へ
2. `[40|50|60]` を読む → 40<45<50 なので左の子へ
3. リーフで45を発見 → そのポインタで行データを取得

**ディスクI/Oはツリーの深さ回数だけ**。100万行でも深さ≈20なので20回のI/Oで到達。

### インデックス付き vs フルスキャン

| 操作 | フルスキャン | B-Treeインデックス |
|------|-------------|-------------------|
| 検索（=） | O(N) | O(log N) |
| 範囲検索（BETWEEN） | O(N) | O(log N + 結果件数) |
| ソート（ORDER BY） | O(N log N) | O(結果件数)※ |

※インデックス列でのORDER BYはインデックスが既にソート済みのため追加ソート不要。

### 挿入時のノード分割（Split）

- ノードが満杯になると**2つに分割**し、中央値を親ノードへ押し上げる
- 最悪ケースでルートまで連鎖分割 → O(log N) の書き込みコスト
- これが**インデックスが多いと書き込みが遅くなる理由**

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 点検索 | O(log N) |
| 範囲検索 | O(log N + K)　K=結果件数 |
| 挿入 | O(log N) |
| 削除 | O(log N) |
| 空間 | O(N) |

- **実際の深さ**：1000万行で高さ4〜5程度（1ノードに数百キーが入るため）
- ランダム挿入はページ分割を多発させ**フィルファクター**（ページ使用率）が下がる

## コード例（PostgreSQL / Neon）

```sql
-- インデックス作成
CREATE INDEX idx_users_email ON users(email);

-- 複合インデックス（順序が重要：左端から使われる）
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);

-- 実行計画の確認
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 42 AND created_at > '2026-01-01';
-- Index Scan が出ればインデックス使用中
-- Seq Scan が出ればフルスキャン

-- インデックスが使われない典型例（関数適用）
-- NG: WHERE DATE(created_at) = '2026-01-01'
-- OK: WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
```

## よくある誤解・落とし穴

- **「インデックスを貼れば必ず速くなる」は誤り**  
  - 件数が少ないテーブル・選択率が低い列（例：boolean）はSeq Scanの方が速い
  - PostgreSQLオプティマイザがインデックスを無視することもある

- **複合インデックスの列順**  
  - `(user_id, created_at)` は `WHERE user_id=?` には使えるが `WHERE created_at=?` だけでは使えない
  - 左端プレフィックスの法則：最も絞り込める列を左に

- **インデックスと関数**  
  - `WHERE LOWER(email) = ?` はインデックスを使えない → 関数インデックスで解決  
  - `CREATE INDEX idx_email_lower ON users(LOWER(email));`

- **NULL値**  
  - PostgreSQLはNULLをB-Treeインデックスに含める（`IS NULL` 検索でも使える）  
  - MySQLはNULLをインデックスに含めない（挙動が異なる）

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neon = PostgreSQL**：B-Treeが全テーブルのデフォルトインデックス実装
- FastAPIのリストAPIで `ORDER BY created_at DESC LIMIT 20` → `created_at` のインデックスが必須
- ユーザー認証で `WHERE email = ?` → `email` のUNIQUEインデックスがないと全スキャン
- `EXPLAIN ANALYZE` をローカルのNeonブランチで実行 → 本番影響ゼロで計画確認可能
- Cloud RunはスケールアウトするためDB接続数が増える → インデックスでクエリ時間を短縮し接続を早期解放することが重要
