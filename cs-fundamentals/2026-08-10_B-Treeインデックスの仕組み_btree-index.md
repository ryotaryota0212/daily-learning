# B-Treeインデックスの仕組みと計算量

## 概要

B-Tree（バランス木）は、RDBMSのインデックス実装において最も広く使われるデータ構造。PostgreSQL（Neon含む）のデフォルトインデックス型。
ディスクI/Oを最小化するよう設計されており、テーブルのフルスキャンを避けて特定行への高速アクセスを実現する。
「なぜインデックスを貼るべき列があるのか」「複合インデックスの順序はなぜ重要か」を理解するための基礎。

---

## 仕組みの要点

### 基本構造

```
                 [30 | 60]           ← ルートノード
                /    |    \
          [10|20] [40|50] [70|80]   ← 内部ノード
          /  |  \  ...              ← 葉ノード（実データへのポインタ）
```

- **ルートノード**: 木のエントリポイント、常にメモリに乗せる
- **内部ノード**: キーと子ノードへのポインタを持つ（データなし）
- **葉ノード**: キー + ヒープ（テーブル実データ）へのポインタを保持
- **葉ノードは双方向リンク**: 範囲スキャン（`BETWEEN`、`>`）が効率的に動く理由

### 検索の流れ（例: `WHERE age = 45`）

1. ルートノードを読む → `45 > 30` かつ `45 < 60` → 中央の子へ
2. 内部ノード `[40|50]` → `45 > 40` かつ `45 < 50` → 対応する子へ
3. 葉ノードで `age=45` のヒープポインタを取得 → テーブル行を読む

### 挿入とページ分割

- 葉ノードが満杯 → **ページ分割**（Split）が発生
- 中央値が親ノードに昇格し、分割後の2ノードが子になる
- 最悪ケースはルートまで伝播 → 木の高さが1増える
- 頻繁な挿入・削除はページ断片化を引き起こし、`VACUUM`/`REINDEX`が有効

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 検索 | O(log n) |
| 挿入 | O(log n) |
| 削除 | O(log n) |
| 範囲スキャン | O(log n + k) ※k=結果件数 |

- **高さは低い**: ノードあたり数百〜数千キーを持てるため、数億行でも高さ4〜5程度
- **ディスクI/O = 木の高さ**: 1クエリのI/O回数が予測可能
- **キャッシュ効果**: 上位ノードはほぼ常にメモリに乗っているため実質的なI/Oはさらに少ない

## コード例（PostgreSQL）

```sql
-- インデックス作成
CREATE INDEX idx_users_age ON users(age);

-- 複合インデックス（順序重要: 左端から使われる）
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);

-- 実行計画でインデックス使用を確認
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 42 AND created_at >= '2026-01-01';
-- "Index Scan using idx_orders_user_date" が出れば使われている

-- 部分インデックス（条件を絞ることでサイズ削減）
CREATE INDEX idx_active_users ON users(email)
WHERE status = 'active';
```

## よくある誤解・落とし穴

- **全カラムにインデックスを貼れば速くなる → NG**
  - 挿入・更新・削除のたびにB-Treeを更新するオーバーヘッドが増える
  - ストレージも増加し、`autovacuum`の負荷も上がる

- **複合インデックスの列順を間違える**
  - `(user_id, created_at)` は `WHERE user_id = ?` に使えるが、`WHERE created_at = ?` 単独では使われない
  - 左端の列から順に一致する場合だけ有効（左端原則）

- **`LIKE '%xxx'` の前方一致でないケースはインデックス不使用**
  - `LIKE 'xxx%'` はインデックスを使えるが、`LIKE '%xxx'` は使えない（先頭が不定なため木を辿れない）

- **型キャストで暗黙に無効化される**
  - `WHERE age = '30'`（文字列で整数カラムを検索）は関数適用扱いとなりインデックスが使われないことがある

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neonは PostgreSQL 互換**: B-Treeインデックスの挙動はそのまま適用できる
- **よく使うクエリの `WHERE` 句・`JOIN` 条件を確認し、インデックスを設計する**
  - 例: `users.email`（ログイン時の検索）、`tasks.user_id`（タスク一覧取得）
- **`EXPLAIN ANALYZE` を Cloud Run ログ or Neon コンソールで定期確認**
  - `Seq Scan` が出ていたらインデックス追加のサイン
- **Neonのブランチ機能でインデックス追加のテストが可能**: 本番DBに影響なく試せる
- **Cloud Run はリクエストごとにコネクションが増えやすい**: コネクション数を抑えて `pg_stat_user_indexes` でインデックス使用率を監視する
