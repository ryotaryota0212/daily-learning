# B-Treeインデックスの仕組みと計算量

## 概要

B-Tree（Balanced Tree）はPostgreSQL・MySQLなどRDBMSのデフォルトインデックス構造。
ディスクI/Oを最小化するよう設計されており、大量データでも検索・挿入・削除がO(log n)で動作する。
「なぜインデックスを貼ると速いのか」「どの列にインデックスを貼るべきか」を理解する基盤になる。

---

## 仕組みの要点

### 構造

```
          [30 | 60]           ← ルートノード
         /    |    \
   [10|20] [40|50] [70|80]   ← 内部ノード
   /↓↓\   /↓↓\   /↓↓\
 リーフ   リーフ   リーフ      ← 実データへのポインタ
```

- **ノード** = ディスクの1ページ（PostgreSQLは8KB）
- **ルート** → **内部ノード** → **リーフ**の3層構造が典型
- リーフノードは双方向リンクリストで連結（範囲検索に使う）
- 各ノードにキーを複数格納 → 木の高さを抑える（100万行でも高さ4〜5程度）

### 検索の流れ（`WHERE id = 42`）

1. ルートノードをメモリに読み込む
2. キー比較で次のノードへポインタをたどる
3. リーフに到達したらヒープ（実テーブル）のRowIDを取得
4. ヒープから実データを読む（テーブル参照が発生）

### 挿入・削除

- **挿入**: リーフに空きがあればそこへ追加。満杯なら **ページ分割** (split) が起きて親ノードにキーが昇格
- **削除**: ページが半分以下になると **マージ** or **再バランス**
- 分割・マージによって常にバランスを保つ → 高さが均一

---

## 計算量・パフォーマンス特性

| 操作 | 計算量 |
|------|--------|
| 検索（完全一致） | O(log n) |
| 範囲検索 | O(log n + k)　※k=結果件数 |
| 挿入 | O(log n) |
| 削除 | O(log n) |
| フルスキャン | O(n) ← インデックス使われない場合 |

- **n** = インデックス対象の行数
- 1ノードに数百キー格納できるのでlog底が大きく、実質的には数回のI/Oで済む

## コード例（PostgreSQL）

```sql
-- インデックス作成
CREATE INDEX idx_users_email ON users(email);

-- 複合インデックス（左端の列から使われる）
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);

-- 実行計画確認
EXPLAIN ANALYZE
  SELECT * FROM orders WHERE user_id = 1 AND created_at > '2025-01-01';

-- インデックスサイズ確認
SELECT pg_size_pretty(pg_relation_size('idx_orders_user_created'));
```

## よくある誤解・落とし穴

- **「全列にインデックスを貼れば速い」** → 挿入・更新のたびにインデックス更新コストが発生。書き込み多いテーブルは逆効果
- **複合インデックスの列順** → `(user_id, created_at)` は `WHERE user_id = ?` に使えるが `WHERE created_at = ?` だけでは使えない（左端の法則）
- **低カーディナリティ列** → `is_deleted`（true/false）のような列にインデックスを貼ってもオプティマイザはシーケンシャルスキャンを選ぶ場合がある
- **LIKE検索の前方一致以外** → `WHERE name LIKE '%田%'` はインデックスを使えない（前方一致 `'田%'` はOK）
- **インデックスオンリースキャン** → `SELECT`する列がインデックスに含まれる場合、ヒープアクセスを省略できる（カバリングインデックス）

## 実務での使いどころ（FastAPI + Neon + Cloud Run）

- **Neon（PostgreSQL）** のデフォルトインデックスはB-Tree。主キー・外部キーは自動作成される
- **FastAPIのフィルタリングAPI** で `WHERE user_id = ?` や `WHERE created_at BETWEEN ? AND ?` を使うなら複合インデックスを設計する
- **EXPLAIN ANALYZEの読み方**: `Index Scan` ならインデックス使用中、`Seq Scan` なら未使用。`actual rows` と `rows` の乖離が大きければ統計情報が古い (`ANALYZE` を実行)
- **Cloud Run（スケールアウト）** でコネクションが多くなると、インデックスなしのクエリがボトルネックになりやすい → スロークエリログで早期発見
- **Neonのブランチ機能** を使えば、インデックス追加の影響をステージング環境で `EXPLAIN` 比較して確認してからマージできる
