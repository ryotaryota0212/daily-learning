# B-Treeインデックスの仕組みと計算量

## 概要

B-Tree（Balanced Tree）はRDBMSが最も広く使うインデックス構造。PostgreSQL（Neon）のデフォルトインデックスもB-Tree。
ディスクI/Oを最小化するために設計されており、「なぜ全件スキャンより速いか」「なぜ複合インデックスの列順が重要か」を理解する鍵になる。
クエリの実行計画を読む・インデックスを設計するすべての場面で前提知識となる。

---

## 仕組みの要点

### 構造

```
         [30 | 70]            ← ルートノード
        /    |    \
  [10|20] [40|50|60] [80|90]  ← 内部ノード
  ↓↓↓      ↓↓↓↓↓      ↓↓↓    ← リーフノード（実データのポインタ）
```

- **ノード** = ディスク上の1ページ（PostgreSQLは8KB）
- **次数 t**：各ノードが持てるキーの最大数を規定。t=2なら最大3キー
- **リーフノード**：実際の行ポインタ（ctid）を持つ。双方向連結リストで横断可能
- **内部ノード**：キーと子ノードへのポインタのみ。データは持たない

### 検索の流れ

1. ルートノードをディスクから読む（1 I/O）
2. キーを二分探索 → 次の子ノードへ（1 I/O）
3. リーフに到達するまで繰り返す
4. リーフからctidでヒープ（実テーブル）を読む

**ポイント**：木の高さ = I/O回数。1億行でも高さ≒4〜5なので4〜5回で見つかる

### 挿入・削除

- **挿入時にノードが満杯**→ノード分割（スプリット）が発生し、親へキーが昇格
- **削除後にキーが少なすぎ**→兄弟ノードから借りるか、ノードをマージ
- これらの操作が「バランス」を保つ（木の高さが偏らない）

### なぜB-TreeがB+Treeと呼ばれる場合があるか

RDBMSが使うのは厳密には **B+Tree**（B-Treeの変種）:
- リーフだけが実データポインタを持つ
- リーフが双方向連結 → 範囲スキャン（BETWEEN, ORDER BY）が高速

## 計算量・パフォーマンス特性

| 操作 | 計算量 | 補足 |
|------|--------|------|
| 検索 | O(log n) | nはインデックスエントリ数 |
| 挿入 | O(log n) | 分割があっても償却O(log n) |
| 削除 | O(log n) | マージを含む |
| 範囲スキャン | O(log n + k) | kは結果件数。リーフ横断が効く |

- ノード1つが数百キーを持てる → 木の高さが低く保たれる（I/O効率が良い）
- 1億行: 高さ≒4、10億行: 高さ≒5（対数の威力）

## コード例

```sql
-- インデックス作成とEXPLAIN ANALYZEで実行計画確認
CREATE INDEX idx_orders_user_created
    ON orders (user_id, created_at DESC);

-- このクエリはIndex Scanを使える（複合インデックスの左端から合致）
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 42
  AND created_at > NOW() - INTERVAL '30 days'
ORDER BY created_at DESC;

-- Index Scanが出れば成功。Seq Scanなら別の原因を調査
-- Bitmap Index Scan: 中間件数で出る。Heapからのランダム読みをバッチ化
```

## よくある誤解・落とし穴

- **「インデックスは多いほど良い」**→ 挿入・更新・削除のたびにインデックスも更新。書き込みが重くなる
- **「先頭列を飛ばした複合インデックスは使われる」**→ 原則使われない。`(user_id, created_at)` で `created_at` だけの検索はSeq Scan
- **「低カーディナリティ列にインデックス」**→ 例：`status`が3種類ならフルスキャンと大差ない。PostgreSQLはコストベースで判断してインデックスを使わないことがある
- **「NULLはインデックスに入らない」**→ PostgreSQLはNULLもB-Treeに格納する（MySQLと異なる）。`IS NULL` 検索でもインデックスが使える
- **「インデックス列に関数を使うと効かない」**→ `WHERE LOWER(email) = 'foo'` はインデックス対象外。関数インデックスで解決: `CREATE INDEX ON users (LOWER(email))`

## 実務での使いどころ

**FastAPI + Neon（PostgreSQL） + Cloud Run スタックとの関連**

- **Neon の Serverless 接続**：コールドスタート後の最初のクエリでSeq Scanが起きると遅延が目立つ。よく叩くエンドポイントのWHERE句は必ずインデックスを貼る
- **複合インデックスの設計**：`WHERE user_id = ? ORDER BY created_at DESC` のような「絞り込み + ソート」パターンに `(user_id, created_at DESC)` を作ると Index Only Scan が効いてヒープアクセスを省ける
- **`EXPLAIN ANALYZE` を習慣に**：FastAPIのエンドポイントが遅いときにまず実行計画を確認。`Seq Scan on large_table` が見えたらインデックス追加を検討
- **Neon のオートサスペンド中の肥大化防止**：不要なインデックスはストレージコストになる。`pg_stat_user_indexes` でスキャン数を確認して未使用インデックスを削除する
- **ページング**：`OFFSET` は大きくなるほど遅い（先頭からスキャン）。`WHERE id > last_id` のカーソルページングにすると Index Scan で一定速度を保てる
